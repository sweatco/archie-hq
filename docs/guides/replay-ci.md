# Production replay on pull requests

Opened, updated, reopened or ready PRs request an evaluation through GitHub's normal `pull_request` workflow. Resolve merge conflicts first; GitHub does not dispatch that event for conflicted PRs. First-time fork contributors may also need GitHub's separate approval to run the intake. The request check only acknowledges the request. After intake completes, **Production replay** is the separate PR status that stays pending until an owner or maintainer approves and the evaluation finishes.

The default-branch controller resolves the PR through GitHub's API and shows an immutable tuple in its plan job summary: PR, base/head repositories and revisions, trusted harness revision, encrypted and plaintext corpus SHA-256, and the complete model/configuration plus its hash. Review that summary and the candidate code before approving the `production-replay` environment. A changed base/head or closed PR invalidates the approval; restart the request to evaluate the new tuple. Per-PR concurrency also cancels older evaluation jobs.

After approval, one trusted harness compares both actual runtime revisions on the same deterministic sample of up to **five whole sessions** and ten component fixtures per arm. The fixed smoke configuration uses Haiku, low effort, 64 SDK turns per input and a ten-minute timeout per session arm. The initial inventory's selected five sessions contain seven inputs and 31 recorded calls, with maxima of eight calls per input and 15 per session; these caps provide room for the complete selected histories. They are fixed before inference, without retries or adjustment to obtain a pass. Review the workload bounds again when replacing the frozen corpus.

Replay checks required execution, delivery, access and recorded-tool coverage gates. It does not automatically judge factual accuracy or usefulness. The full private snapshot stays frozen; sampling bounds PR cost without truncating stored sessions or individual session histories. The numeric summary reports both full-corpus and selected-session counts. Model cost and latency are observations from one serial trial per arm, not statistically established improvements. Full-corpus local comparisons remain available through the runner; no scheduler is added. See [Replay evaluation](replay-evaluation.md) for the capture and runner contract.

## Activate once, with repository admin approval

These files prepare the workflow; they do not create environments, upload data or activate paid inference. Before making **Production replay** a required check, verify that the unmodified baseline completes the frozen sample’s recording coverage. The controller must first land on the default branch. GitHub only dispatches this `workflow_run` controller from that branch.

1. Create the `production-replay` environment in repository Settings → Environments. Add required reviewers who have the repository **maintain** or **admin** role. Turn off administrator bypass. Preventing self-review is optional. The controller fails closed if the environment is missing or lacks required reviewers; after the gate it independently verifies the real approval history and approver's current role. A bypass with no approval does not authorize replay.
2. Prepare and review a sanitized full session snapshot locally. It must use `archie-session-capture/v1`; sanitization does not make internal transcripts public. Freeze the exact UTF-8 JSON bytes and compute their SHA-256.
3. Prepare the complete encrypted corpus with the local command below. It compresses all snapshot bytes and encrypts them using Node's AES-256-GCM with a fresh random 32-byte key and nonce. It writes the encrypted file and a mode-0600 key file, refuses overwrites, and prints neither key nor corpus. Keep the key file outside the checkout. Review and version only `.github/replay/corpus.enc` with the trusted harness. Set the repository Actions variable `REPLAY_CORPUS_SHA256` to the exact plaintext digest and the **environment secret** `REPLAY_CORPUS_KEY` to the base64 key file's contents. This avoids GitHub's 48 KB secret limit without shrinking the corpus. The controller independently pins the encrypted file's digest before approval and checks both digests before inference.
4. Add a dedicated, spend-limited Anthropic key as the **environment secret** `REPLAY_ANTHROPIC_API_KEY`. Do not add production Slack, GitHub connector, AWS or other runtime credentials. The workflow fixes all replay configuration fields in `.github/workflows/replay.yml`; review changes to those limits together with cost and corpus selection.
5. Open or update a test PR, review the plan summary, and approve its environment job. Verify that only the numeric projection appears publicly and that the separate **Production replay** status reflects the actual evaluation. After this activation check, require both that status and **branches to be up to date before merging** in branch protection. Commit statuses attach to the head SHA: a base advance after success otherwise leaves the older comparison green. Refresh the PR branch and obtain a new evaluation for the new base.

Run preparation only after the local snapshot has been approved, using private paths for plaintext and key:

```sh
mkdir -p .github/replay
node tools/replay/ci.ts encrypt /PRIVATE/snapshot.json .github/replay/corpus.enc /PRIVATE/replay-key.txt
shasum -a 256 /PRIVATE/snapshot.json
```

The encrypted envelope is a version marker, 12-byte nonce, 16-byte authentication tag and gzip ciphertext. The version marker is authenticated as additional data. Decryption and parsing fail closed on a wrong key, tampering, digest mismatch or invalid capture. The plaintext size limit is 64 MiB. The prepared workflow intentionally has no corpus file or key until those separate data-handling steps are approved.

Use a fresh intake run to retry. Re-running the privileged controller is rejected so an old environment approval cannot silently authorize another attempt. When initially landing the harness, an older base revision may lack the runtime interfaces used by the fixtures; the result is unsupported or failed, never a passing evaluation. Use the next PR after the runtime contract has landed to validate both arms.

## Privacy and execution boundary

No PR code, artifacts or caches are used before approval. The intake has no permissions and executes no checkout. The controller checks the upstream workflow's identity, repository, event and head SHA; forks with an empty `pull_requests` hint require one unique match through GitHub's paginated open-PR API. After approval and again immediately before opening the corpus/model calls, it rechecks the current PR revisions, environment protection, approval history and exact configuration.

Approval authorizes that exact candidate code to read a private corpus and use an inference key. Recorded-tool restrictions protect the normal runtime path; they do **not** sandbox malicious JavaScript. Review the entire candidate dependency/runtime change accordingly. Installs disable lifecycle scripts and receive a small environment without the corpus key, inference key, GitHub token or Actions output paths. Runtime children receive the inference key only for the session comparison; the corpus decryption key stays in the trusted parent process. Checkout credentials are not persisted. Candidate execution has a read-only Actions token at the job level; only the separate reporting jobs can write commit statuses.

This is a public repository. Nothing uploads the corpus, raw JSON results, Evalite reports, traces, model responses, tool outputs or child/install logs. These are private runner files, discarded at cleanup; failed commands emit a fixed generic message. Public summaries are rebuilt from an allowlist of finite numeric totals and fixed status enums. The approved plan contains public source revisions/configuration and corpus digests. The status reporter runs trusted code separately, rechecks PR freshness and never evaluates the candidate. Status writes serialize per head SHA and reject an older controller after a newer request owns the status, even when both source revisions are identical. Unsupported setup, incomplete pairs, recorded-tool divergence, runner/report failures and failed gates all prevent success.

The local tests mock GitHub's APIs and exercise approval roles, fork mapping, configuration/revision races, completeness and privacy projection. They do not prove GitHub's live environment protection or provider behavior. No live CI result is claimed until the activation run succeeds.
