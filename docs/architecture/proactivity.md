# Proactive observation

Proactive observation ships with `ARCHIE_PROACTIVITY_MODE=off`. Shadow mode collects and analyses public activity without sending proactive messages. Live delivery requires an exact, human-reviewed policy evaluation and explicit owner approval. Production usefulness remains a rollout requirement; synthetic tests cannot establish it.

## Integration

Public Slack activity enters a bounded background intake queue before ordinary task-routing filters. Collection does not create tasks. Mentions, edits and engaged-thread replies continue through existing routing independently of background network calls. Explicit `initiative …` commands in the configured owner's verified DM are consumed as controls.

Observations are an independent subsystem under `src/proactivity/`. Its `observation-tools` MCP server exposes `search_observations`, `read_observation`, `list_open_matters` and `read_matter` through `api.ts` and `recall.ts`. The PM receives explicit discovery guidance when these tools attach. Tools accept no channel or recipient override; they use the task's persisted destination, with the same unambiguous destination derivation for legacy tasks. They work when knowledge memory is disabled or unavailable. `search_memory`, profiles, entities and completed-task extraction retain their knowledge-memory responsibilities and flags.

Public tasks can retrieve observations from their own source channel. Only the configured owner's verified DM can retrieve open matters or combine observations across sources that owner can currently access. Private task summaries and profiles do not enter background analysis. Retrieval rechecks source access; already loaded PM context retains the existing session limitations described in [memory](memory.md).

Background analysis receives structured public evidence and no PM session, shell, repository writer or unrestricted MCP tools. A human request in a proactive thread still creates or resumes an ordinary task, with an inline evidence brief and optional `initiative_origin` metadata. Owner-approved proposal starts use the narrow task handoff described below.

| Boundary | Implementation and responsibility |
|---|---|
| Collection | `collection.ts` reconciles public sources, refreshes known threads and repairs coverage. `slack.ts` verifies audiences and wraps bounded API calls. |
| Decisions and scheduling | `service.ts` coordinates extraction, investigation and notification eligibility; `decisions.ts` defines deadline checks, evidence identity and reason codes. |
| Persistence | `store.ts` owns the SQLite transaction boundary; four focused operation groups in `persistence/` protect attention/controls, requests, learning/evaluation and replay lifecycles. Cohort freezing, policy activation, evaluation linking, reflection provenance and collection completion commit their coordinated writes together. Callers receive no raw database handle and execute no SQL. |
| Recall | `api.ts`, `recall.ts` and `tools.ts` authorize task-bound reads independently of knowledge memory. |
| Learning | `learning.ts`, `cohort.ts` and `replay.ts` propose and evaluate changes through the production decision path. |
| Task starts | `handoff.ts` verifies the owner and evidence; only `task-adapter.ts` calls the normal task-creation runtime. |
| Runtime | `runtime.ts` assembles dependencies, consumes owner controls and drains admitted intake, reads, approval operations and reconciliation before closing SQLite. |

## Configuration and storage

Node 24 or later is required when enabled. `ARCHIE_PROACTIVITY_MODE=off|shadow|live` defaults off. `ARCHIE_PROACTIVITY_OWNER` is an internal human Slack ID. Extraction defaults to `claude-haiku-5-5`; investigation defaults to `claude-sonnet-5-5`. The gateway accepts only explicitly priced model routes and verifies account availability during initialization. Knowledge-memory flags do not enable or disable observation storage.

Initiative owns one SQLite database for changing source revisions, evidence links, attention, work scheduling, billing reservations, the outbox, learning and approved task handoffs. A source edit can invalidate observations, matters and unsent deliveries atomically; paid admission and notification admission also remain transactional. Knowledge memory continues to own Markdown profiles, entities and task summaries. Neither store initializes or resets the other.

State remains at `WORKDIR/initiative/state.sqlite`, bound to the Slack team and initiative owner. SQLite uses WAL, full durability and FTS5. All schema creation and upgrades live in `persistence/migrations.ts`; model, learning and service constructors never create tables. Schema 8 upgrades the published v4 database in one transaction: v5 centralizes previously lazy auxiliary tables, v6 adds decisions, coverage causes and task handoffs, v7 adds compact analysis signatures, and v8 adds handoff card synchronization/retry state with a partial index over unsynchronized cards. Identity checks precede commit; failures roll back and newer schemas are rejected. Operator exports, explanations and proposal listings open read-only and require an explicit startup/migrate upgrade instead of silently migrating. Its location protects observation and operational state from the Markdown knowledge-store reset lifecycle. It remains inaccessible through the PM filesystem sandbox. Back up the database with a SQLite-aware backup or after a clean stop; copying a live database without its WAL is insufficient. Restore only into the same workspace and owner configuration.

First successful activation establishes the observation watermark. Restarts preserve it. There is no historical import. A new reply may retrieve its older parent as bounded context. Source revisions, tombstones, processing generations and coverage gaps distinguish new evidence from duplicates. Every refresh also revalidates a previously fetched older parent; it does not import the older thread history. Coverage gaps must remain visible until collection proves them repaired. Archie-authored messages preserve provenance and cannot independently establish a new observation. An edit or deletion of an Archie message already used as context invalidates dependent state.

Human source changes invalidate derived observations, attention state and pending notifications. Host-controlled generation checks reject stale model results. The scheduler holds a persisted ownership lease, while individual jobs have fenced leases and generations. Rescheduling preserves a running investigation and keeps newer work after its completion.

## Operation

The scheduler drains up to 32 due jobs per minute within a 45-second drain window; a running analysis has its own five-minute bound. Routine extraction is hourly. New or substantively reopened matters get their first investigation in that extraction cycle; existing next checks and human snoozes remain authoritative. A known future deadline schedules a check 15 minutes before it, then at the deadline; overdue checks recur hourly instead of spinning. Ordinary checks recur daily. Snoozes remain authoritative, resolved/dismissed matters stop, and active PM work suppresses investigation. Check timing is separate from business-hour delivery. These rules apply after extraction has identified the matter; hourly extraction and backlog can delay the first observation. Thread refresh jobs are event-driven and continue only while pagination is incomplete. Active matters get fresh thread checks before investigation or delivery. A compact signature of current source generations, coverage, policy/configuration, deadline phase and reminder feedback reuses unchanged no-help/already-notified analysis after that refresh. No raw snapshot is copied into this cache. Extraction groups dirty threads by source channel and carries consolidated state across bounded context parts. A completed reconciliation clears repaired access/pagination gaps; unknown-history, overflow, missing-parent and omitted-thread coverage remain visible until actually repaired. Matters retain supporting evidence, inferred versus explicit ownership/deadlines, resolution, snooze and dismissal state. There is no two-week expiry or automatic service pause. Day 14 is a reporting checkpoint, not an operating limit.

Notifications are limited to a weekday 09:00 digest of at most five items plus two additional interventions per day, Monday–Friday, 09:00–18:00 Europe/Lisbon. Delivery is bound to the verified owner DM or the original public discussion. Pending deliveries recheck evidence, controls, policy and active PM work. Canonical sets of immutable citation revisions prevent reordered or repeated citations from producing another nudge; a new deadline phase, agreed reminder or changed evidence can permit one. Source versions are checked again in the enqueue/admission transaction, including after asynchronous recipient lookup. The outbox reserves notification slots atomically. A timed-out or interrupted send remains uncertain and is reconciled by its outbound Slack metadata; it is never blindly sent again.

Owner controls currently include `initiative status`, `mute`/`unmute`, `pause`/`resume`, `stop`/`start`, and `handled`, `later`, `not useful` or `stop following` followed by a matter ID. Single-matter messages also offer owner-only Slack buttons bound to the delivery record. Other users cannot operate these controls. `later` wakes at the next weekday 09:00. Mute blocks new delivery; pause aborts new analysis; stop cancels queued analysis and pending delivery while preserving intake, accounting and reconciliation responsibilities.

The daily ceiling is $200 on Europe/Lisbon calendar days. Routine work uses at most $150; priority checks can use the remaining $50. Every paid request reserves a conservative maximum before dispatch. SDK retries are disabled and explicit model retries must receive new admission. Complete billable usage settles a reservation conservatively; missing usage leaves liability outstanding. Unsettled liability consumes capacity across possible execution days. Settled debits do not reopen already-consumed allowance, and prior-day refunds do not accumulate. Exhaustion defers paid work until capacity returns automatically. A known pricing overrun is accounted in full and prevents further unverified paid admission.

At most four model execution slots can be outstanding, with batches using at most three so direct checks retain capacity. Reflection and replay use asynchronous batches with persisted semantic steps. Execution slots and financial liability have distinct lifecycles; a safely terminal attempt can release its slot while its full unresolved reservation remains charged against the daily ceiling.

Model rates were checked against [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing) on 2026-10-20. Haiku's higher input tier and conservative cache-write pricing bound reservations. Provider usage priced conservatively is not presented as an exact invoice total.

## Provider recovery

Batch intent, charge, local `custom_id` and a hash binding the provider endpoint/credential are durable before submission. Known provider IDs are polled. A lost create response or process exit during submission uses the installed SDK's supported batch listing and result stream to correlate the persisted `custom_id`; there is no blind resubmission. Discovery reads at most 20 metadata entries per page, persists its cursor, downloads at most three result streams per poll and inspects at most 1,000 entries per stream. The runtime bounds combined polling to 45 seconds. Listing is provider-workspace scoped, so discovery may inspect unrelated result entries; unmatched payloads are not retained or supplied to models. A dedicated provider workspace reduces that scan surface.

Provider-confirmed ended batches enter `retrieving`: their logical execution slots are free while unavailable usage/results remain a financial liability. Result polling continues while within the provider's retention. Unknown submissions retire only after the lifecycle window and a complete listing containing no possibly running candidate, never on a timer alone. The complete-list requirement is deliberately conservative: unrelated running batches can delay retirement. Retired replay attempts remain explicit failures in their frozen cohort, not missing denominator entries or automatic paid retries.

The API documents a 24-hour batch lifecycle and 29-day result availability. Authoritative errored/canceled/expired individual results settle at zero; successful results settle only with complete usage. Missing or expired results never imply a refund. Credential rotation and unbound legacy attempts require an operator to confirm the original provider workspace and run `bind-provider`; this changes correlation authority, not financial accounting. `reconcile-batch` can recover an identified terminal provider batch, including a retired attempt. Ambiguous liability remains visible in `initiative status`. See [Anthropic batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing) and the [operator commands](../guides/initiative-operations.md).

## Inspecting a decision

`read_matter` in the verified owner DM includes the current matter, current source snapshot and a bounded explanation: the last 20 distinct decisions, reason codes and plain explanations, evidence IDs/hashes, next check, applicable policy, request/charge references, delivery states, recent human feedback and related proposal-to-task transitions. Repeated identical decisions do not create an archive of redundant entries. The local `explain` command exports the same diagnostic state to a mode-600 file. Source bodies remain in the existing evidence store; diagnostics do not create another raw-message archive. New reads recheck source permissions and validity after awaited authorization; already-loaded PM context has the same session-revocation limitation as other evidence.

## Reviewed learning and development handoff

Daily reflection proposes small changes to ranking, context selection and reminder wording. It uses forward-collected episodes and explicit feedback, including acknowledgements from the separate development loop. Reflection records every supplied training source, including related context and inherited provenance. Training channels are excluded from evaluation; complete human topic sets for every training and evaluation thread provide a second holdout boundary. A stop changes the responsibility epoch so late results cannot create policies, proposals or completed replay cases under a new responsibility.

Episodes are captured before extraction, including threads that produce no matters. An evaluation case preserves the production source group, recorded clock, bounded related-source read surface, prior attention and delivery history, manual controls, active PM state and already consumed notification slots. Its source bodies are referenced by exact revisions rather than copied into a second raw-message archive.

Before candidate predictions, an operator freezes the first chronological non-overlapping source groups and their human urgency, actionability and topic labels. The immutable manifest binds every case, source input, candidate/base policy, owner/model configuration, responsibility epoch, rubric and decision implementation. At least 100 distinct held-out threads are required, including 20 urgent and 20 non-actionable. Every frozen case must complete; missing results, failed steps, coverage gaps and deleted or expired source material cannot disappear from the denominator.

Replay runs the production extraction, reconciliation, context selection, first-check investigation and delivery checks on isolated SQLite state, with recorded source reads and simulated Slack sends. A zero-matter result is a completed no-action case and can count as an urgent miss. Missing semantic model steps are submitted through the real budget gateway; replay restarts from the original source and clock after their batch results arrive. It never advances time to make a deferred job due. This tests the decision on recorded evidence at that clock; it does not claim to simulate later unobserved discussion.

The baseline uses base-policy extraction and a deterministic title/detail brief instead of model-generated help. Both strategies share the ordinary digest; evaluation compares additional messages under the same chronological two-per-day interruption allowance. Human labels assess every candidate and baseline draft separately, and identify the actionable threads each message covers. Usefulness counts admitted messages; urgency misses count uncovered urgent threads. A candidate must improve usefulness, add no urgent misses, and have zero reported scope, authority, stop or budget violations.

After building, use the local operator commands:

```bash
node dist/cli/initiative.js <database> <team-id> export <policy-id> before.json
node dist/cli/initiative.js <database> <team-id> cohort <policy-id> ground-truth.json
# The running subsystem advances batch replay during its minute ticks.
node dist/cli/initiative.js <database> <team-id> export <policy-id> after.json
node dist/cli/initiative.js <database> <team-id> evaluate <policy-id> message-labels.json report.json
node dist/cli/initiative.js <database> <team-id> proposals proposals.json
node dist/cli/initiative.js <database> <team-id> ack <proposal-id> <issue-url> filed
```

The ground-truth file contains `training: [{episode, threads: [{channel, thread, topics: [...]}]}]` and `groups: [{episode, threads: [{channel, thread, topics: [...], urgent, actionable}]}]`. Supply all topics for every training thread, including related context. Use the exported chronological group order without skipping cases. Inherited training labels remain fixed.

After every replay case finishes, the message-label file contains the exported `cohort` ID and `messages: [{episode, strategy, draft, useful, covers, violation}]`. `strategy` is `candidate` or `baseline`; `draft` is the exported content hash; `covers` lists covered actionable thread keys as `channel:thread`. Label every exported message exactly once. The simulator adds urgent misses caused by no output or withheld notification slots. Do not substitute model-generated or synthetic labels for the human rollout review.

The owner previews a candidate with `initiative policy <policy-id>` in the verified DM and activates it with `initiative approve <policy-id> <evaluation-id>`. Offline commands cannot activate policies. Approval rechecks current source access, input availability and exact versions. Code or owner/model configuration changes invalidate delivery approval on restart. Raw-input cleanup can invalidate an unfinished cohort; it cannot silently substitute excerpts and reuse an old prediction. Expired/deleted inputs also purge dependent replay content. Initial approval checks every fresh training input, including uncited sources. Inherited topic provenance may survive source cleanup only through the already owner-approved base proof; resupplying that episode to reflection makes it fresh input again. `initiative rollback <policy-id>` restores a previously approved version when its implementation/configuration still matches. Base guidance without a passing approval never grants live delivery.

### Owner-approved Start task

A capability proposal can be presented once per current version through the ordinary owner notification outbox and its interruption caps. It shows the repository, intended result and supporting source links. Before the owner clicks **Start task**, it explicitly says that the resulting ordinary task uses normal Archie task budgeting, outside the $200/day background allowance. Presentation and reflection cannot start a task. Collection, analysis and evaluation continue to use the background allowance.

The action binds a sent delivery to the exact canonical proposal version. The host verifies the configured human owner, actual owner DM, repository configuration, current permitted source revisions and bounded complete source refresh. Another user, bot message, forged ID or stale action cannot grant approval. The first durable handoff records actor, time, version, evidence identity, task ID, destination and task-budget responsibility before any task preparation. Duplicate clicks and retries use that same identity.

`Task.prepare()` writes full correlation, fixed destination and the bounded untrusted brief together in the first atomic metadata write, with status `preparing`. Startup recovery and ordinary message delivery cannot run that state. After a final source check, `startPrepared()` durably transitions to `in_progress`/`ready` before enqueueing. Recovery can therefore resume a fully authorized task after a crash before enqueue/acknowledgement without inventing another task or losing its brief. Transient source failures stay retryable. If source versions actually change during preparation, the task remains inert and the handoff is marked stale; use a fresh proposal or the normal mention workflow rather than retrying stale authority.

The adapter calls the existing PM task runtime; normal edit-mode and external-action permissions still apply. Starting a task does not file a GitHub issue, authorize a push/merge/release, or grant the observer a shell. Replies in the resulting proposal discussion continue the linked task through ordinary Slack routing. Archie-authored output cannot independently establish source evidence or authorize another start.

Approved tasks expose a message-only `post_to_user` bound to their one persisted owner-DM conversation; the incompatible public-post tool is absent. Runtime checks reject forged targets and inconsistent metadata after reload, while ordinary tasks keep existing behavior. An approved task must deliver its initial PM reply through the bound messaging path before `report_completion` may park it silently; a completion message can supply that reply. Only a confirmed PM send sets the durable marker, never plain assistant text or a system notice. Card consumption follows durable approval: serialized edits replace Start with pending status and then confirmed activation plus the owner-thread link, retaining the proposal and budget context. Edits have their own bounded lease/retry state and never gate task activation. Recovery inspects only due unsynchronized cards, including activated handoffs whose final Slack edit failed. Replayed callbacks neither launch another task nor post duplicate confirmation replies.

Task runtime state and proposal outcome remain separate. `completed`/`report_completion` means parked and may mean clarification, approval or budget/time waiting. Status exposes these waiting reasons; activation or parking never marks a feature successful. Only an explicit owner `initiative outcome` acknowledgement with a repository artifact URL and acceptance result records `implemented`, `released` or `rejected`. An implemented feature remains distinct from a released feature. These records are owner-acknowledged evidence, not independently verified artifact checks; only acknowledged outcomes can feed development feedback into reflection. The offline `ack` command supports `filed`/`implementing` for an external development workflow, preserves the feature intent and cannot declare completion. See the [operator guide](../guides/initiative-operations.md).


## Verification and rollout limits

The architecture/reliability refinement is verified as a local patch on published baseline `2f84ec6a47a39c0fc5d680ec935b1a8e095f9d8f`; that baseline's green CI alone does not validate the refinement. The [verification receipt](../guides/initiative-verification.md) records the exact implementation fingerprint, commands/results, migration and crash probes, declared workload and live integration limits.

The synthetic workload covers 40 public channels, 240 threads, eight long threads, root edits, pagination and eight hours of minute ticks. It measures production collection, SQLite, model admission, extraction and investigation with fake Slack/provider boundaries. It does not measure real network latency, Slack rate limits, paid model invoices or nudge usefulness. First extraction under that burst takes up to 74 minutes; a deadline cannot benefit from the due-check policy until its matter has been extracted. Known due checks in this envelope are at most one tick late. Longer threads retain the newest 200 messages and report omissions, rather than claiming complete understanding.

No live initiative activation, real Slack Start task callback, notification delivery or forward usefulness evaluation has been performed for this refinement. Collect and label real forward evidence in shadow mode before requesting delivery approval. Existing approvals bind the complete decision implementation and configuration, including the relocated persistence and new decision modules; this change requires a fresh matching review. Day 14 remains a reporting checkpoint only. Manual controls and the spending ceiling continue afterward without automatic service pause or expiry.
