# Proactive observation

Proactive observation ships with `ARCHIE_PROACTIVITY_MODE=off`. Shadow mode collects and analyses public activity without sending proactive messages. Live delivery requires `mode=live` and the configured owner enabling `initiative delivery on` in their verified DM. Learning, reflection and behavioral adaptation are deferred to a separate stacked change and are absent from this release. Production usefulness remains a rollout requirement; synthetic tests cannot establish it.

## Integration

Public Slack activity enters a bounded background intake queue before ordinary task-routing filters. Collection does not create tasks. Mentions, edits and engaged-thread replies continue through existing routing independently of background network calls. Explicit `initiative …` commands in the configured owner's verified DM are consumed as controls.

Observations are an independent subsystem under `src/proactivity/`. Its `observation-tools` MCP server exposes `search_observations`, `read_observation`, `list_open_matters` and `read_matter` through `api.ts` and `recall.ts`. The PM receives explicit discovery guidance when these tools attach. Tools accept no channel or recipient override; they use the task's persisted destination, with the same unambiguous destination derivation for legacy tasks. They work when knowledge memory is disabled or unavailable. `search_memory`, profiles, entities and completed-task extraction retain their knowledge-memory responsibilities and flags.

Public tasks can retrieve observations from their own source channel. Only the configured owner's verified DM can retrieve open matters or combine observations across sources that owner can currently access. Private task summaries and profiles do not enter background analysis. Retrieval rechecks source access; already loaded PM context retains the existing session limitations described in [memory](memory.md).

Background analysis receives structured public evidence and no PM session, shell, repository writer or unrestricted MCP tools. A human request in a proactive thread still creates or resumes an ordinary task, with an inline evidence brief and optional `initiative_origin` metadata. Owner-approved proposal starts use the narrow task handoff described below.

| Boundary | Implementation and responsibility |
|---|---|
| Collection | `collection.ts` reconciles public sources, refreshes known threads and repairs coverage. `slack.ts` verifies audiences and wraps bounded API calls. |
| Decisions and scheduling | `service.ts` coordinates extraction, investigation and notification eligibility; `decisions.ts` defines deadline checks, evidence identity and reason codes. |
| Persistence | `store.ts` owns the SQLite transaction boundary; focused persistence operations protect attention/controls, requests and historical evidence retention. Collection completion, source invalidation, delivery admission and task approval commit coordinated writes together. Callers receive no raw database handle and execute no SQL. |
| Recall | `api.ts`, `recall.ts` and `tools.ts` authorize task-bound reads independently of knowledge memory. |
| Task starts | `handoff.ts` verifies the owner and evidence; only `task-adapter.ts` calls the normal task-creation runtime. |
| Runtime | `runtime.ts` assembles dependencies, consumes owner controls and drains admitted intake, reads, approval operations and reconciliation before closing SQLite. |

## Configuration and storage

Node 24 or later is required when enabled. `ARCHIE_PROACTIVITY_MODE=off|shadow|live` defaults off. `ARCHIE_PROACTIVITY_OWNER` is an internal human Slack ID. Extraction defaults to `claude-haiku-5-5`; investigation defaults to `claude-sonnet-5-5`. The gateway accepts only explicitly priced model routes and verifies account availability during initialization. Knowledge-memory flags do not enable or disable observation storage.

Initiative owns one SQLite database for changing source revisions, evidence links, attention, work scheduling, billing reservations, the outbox and approved task handoffs. Historical learning tables remain inert for compatibility and retention. A source edit can invalidate observations, matters and unsent deliveries atomically; paid admission and notification admission also remain transactional. Knowledge memory continues to own Markdown profiles, entities and task summaries. Neither store initializes or resets the other.

State remains at `WORKDIR/initiative/state.sqlite`, bound to the Slack team and initiative owner. SQLite uses WAL, full durability and FTS5. All schema creation and upgrades live in `persistence/migrations.ts`; model and service constructors never create tables. Schema 9 upgrades the published v4 database in one transaction: v5 centralizes previously lazy auxiliary tables, v6 adds decisions, coverage causes and task handoffs, v7 adds compact analysis signatures, and v8 adds handoff card synchronization/retry state with a partial index over unsynchronized cards. Version 9 separates delivery enablement from learned-policy approval, retains the previous policy identity as `deferred_policy` when applicable, selects baseline decisions and queues fresh extraction without deleting old outbox or paid work. Old reflection jobs remain stored but are not claimed. Historical learning proposals without an investigation origin cannot create a new approval; existing approved handoffs retain recovery. Identity checks precede commit; failures roll back and newer schemas are rejected. Operator explanations and proposal listings open read-only and require an explicit startup/migrate upgrade instead of silently migrating. Its location protects observation and operational state from the Markdown knowledge-store reset lifecycle. It remains inaccessible through the PM filesystem sandbox. Back up the database with a SQLite-aware backup or after a clean stop; copying a live database without its WAL is insufficient. Restore only into the same workspace and owner configuration.

First successful activation establishes the observation watermark. Restarts preserve it. There is no historical import. A new reply may retrieve its older parent as bounded context. Source revisions, tombstones, processing generations and coverage gaps distinguish new evidence from duplicates. Every refresh also revalidates a previously fetched older parent; it does not import the older thread history. Coverage gaps must remain visible until collection proves them repaired. Archie-authored messages preserve provenance and cannot independently establish a new observation. An edit or deletion of an Archie message already used as context invalidates dependent state.

Human source changes invalidate derived observations, attention state and pending notifications. Host-controlled generation checks reject stale model results. The scheduler holds a persisted ownership lease, while individual jobs have fenced leases and generations. Rescheduling preserves a running investigation and keeps newer work after its completion.

## Operation

The scheduler drains up to 32 due jobs per minute within a 45-second drain window; a running analysis has its own five-minute bound. Routine extraction is hourly. New or substantively reopened matters get their first investigation in that extraction cycle; existing next checks and human snoozes remain authoritative. A known future deadline schedules a check 15 minutes before it, then at the deadline; overdue checks recur hourly instead of spinning. Ordinary checks recur daily. Snoozes remain authoritative, resolved/dismissed matters stop, and active PM work suppresses investigation. Check timing is separate from business-hour delivery. These rules apply after extraction has identified the matter; hourly extraction and backlog can delay the first observation. Thread refresh jobs are event-driven and continue only while pagination is incomplete. Active matters get fresh thread checks before investigation or delivery. A compact signature of current source generations, coverage, policy/configuration, deadline phase and reminder feedback reuses unchanged no-help/already-notified analysis after that refresh. No raw snapshot is copied into this cache. Extraction groups dirty threads by source channel and carries consolidated state across bounded context parts. A completed reconciliation clears repaired access/pagination gaps; unknown-history, overflow, missing-parent and omitted-thread coverage remain visible until actually repaired. Matters retain supporting evidence, inferred versus explicit ownership/deadlines, resolution, snooze and dismissal state. There is no two-week expiry or automatic service pause. Day 14 is a reporting checkpoint, not an operating limit.

Notifications are limited to a weekday 09:00 digest of at most five items plus two additional interventions per day, Monday–Friday, 09:00–18:00 Europe/Lisbon. Delivery is bound to the verified owner DM or the original public discussion. Pending deliveries recheck evidence, controls, policy and active PM work. Canonical sets of immutable citation revisions prevent reordered or repeated citations from producing another nudge; a new deadline phase, agreed reminder or changed evidence can permit one. Source versions are checked again in the enqueue/admission transaction, including after asynchronous recipient lookup. The outbox reserves notification slots atomically. A timed-out or interrupted send remains uncertain and is reconciled by its outbound Slack metadata; it is never blindly sent again.

Owner controls currently include `initiative status`, `delivery on`/`off`, `mute`/`unmute`, `pause`/`resume`, `stop`/`start`, and `handled`, `later`, `not useful` or `stop following` followed by a matter ID. Single-matter messages also offer owner-only Slack buttons bound to the delivery record. Other users cannot operate these controls. `later` wakes at the next weekday 09:00. Mute blocks new delivery; pause aborts new analysis and blocks new delivery; stop cancels queued analysis and pending delivery while preserving intake, accounting and reconciliation responsibilities.

The daily ceiling is $200 on Europe/Lisbon calendar days. Routine work uses at most $150; priority checks can use the remaining $50. Every paid request reserves a conservative maximum before dispatch. SDK retries are disabled and explicit model retries must receive new admission. Complete billable usage settles a reservation conservatively; missing usage leaves liability outstanding. Unsettled liability consumes capacity across possible execution days. Settled debits do not reopen already-consumed allowance, and prior-day refunds do not accumulate. Exhaustion defers paid work until capacity returns automatically. A known pricing overrun is accounted in full and prevents further unverified paid admission.

At most four model execution slots can be outstanding. Existing batch attempts still count toward that limit, but this release submits no new reflection or replay batches. Extraction groups source threads into bounded direct requests; selective investigation uses the same allowance. Execution slots and financial liability have distinct lifecycles; a safely terminal attempt can release its slot while its full unresolved reservation remains charged against the daily ceiling.

Model rates were checked against [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing) on 2026-10-20. Haiku's higher input tier and conservative cache-write pricing bound reservations. Provider usage priced conservatively is not presented as an exact invoice total.

## Provider recovery

Historical batch intent, charge, local `custom_id` and a hash binding the provider endpoint/credential remain durable. The retained batch code only reconciles already submitted work; it cannot submit new batches or apply learning results. Known provider IDs are polled. A lost create response or process exit during submission uses the installed SDK's supported batch listing and result stream to correlate the persisted `custom_id`; there is no blind resubmission. Discovery reads at most 20 metadata entries per page, persists its cursor, downloads at most three result streams per poll and inspects at most 1,000 entries per stream. The runtime bounds combined polling to 45 seconds. Listing is provider-workspace scoped, so discovery may inspect unrelated result entries; unmatched payloads are not retained or supplied to models. A dedicated provider workspace reduces that scan surface.

Provider-confirmed ended batches enter `retrieving`: their logical execution slots are free while unavailable usage/results remain a financial liability. Result polling continues while within the provider's retention. Unknown submissions retire only after the lifecycle window and a complete listing containing no possibly running candidate, never on a timer alone. The complete-list requirement is deliberately conservative: unrelated running batches can delay retirement. Retired attempts retain their unresolved liability and are never retried as new paid work.

The API documents a 24-hour batch lifecycle and 29-day result availability. Authoritative errored/canceled/expired individual results settle at zero; successful results settle only with complete usage. Missing or expired results never imply a refund. Credential rotation and unbound legacy attempts require an operator to confirm the original provider workspace and run `bind-provider`; this changes correlation authority, not financial accounting. `reconcile-batch` can recover an identified terminal provider batch, including a retired attempt. Ambiguous liability remains visible in `initiative status`. See [Anthropic batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing) and the [operator commands](../guides/initiative-operations.md).

## Inspecting a decision

`read_matter` in the verified owner DM includes the current matter, current source snapshot and a bounded explanation: the last 20 distinct decisions, reason codes and plain explanations, evidence IDs/hashes, next check, applicable policy, request/charge references, delivery states, recent human feedback and related proposal-to-task transitions. Repeated identical decisions do not create an archive of redundant entries. The local `explain` command exports the same diagnostic state to a mode-600 file. Source bodies remain in the existing evidence store; diagnostics do not create another raw-message archive. New reads recheck source permissions and validity after awaited authorization; already-loaded PM context has the same session-revocation limitation as other evidence.

## Task suggestions

The existing bounded investigation can return one scoped task suggestion alongside its resolution/help assessment. It names a configured repository, intended result and supplied human evidence IDs. Host code verifies the allowlist, cited evidence, current source generations, matter state and owner access before recording a versioned proposal. This adds no scheduled proposal generator or extra model call. Suggestions use the same durable outbox, interruption slots, audience checks and source refresh as nudges. No `LearningService`, training episode, replay cohort or learned-policy approval is required.

### Owner-approved Start task

A capability proposal can be presented once per current version through the ordinary owner notification outbox and its interruption caps. It shows the repository, intended result and supporting source links. Before the owner clicks **Start task**, it explicitly says that the resulting ordinary task uses normal Archie task budgeting, outside the $200/day background allowance. Presentation and investigation cannot start a task. Collection and investigation continue to use the background allowance.

The action binds a sent delivery to the exact canonical proposal version. The host verifies the configured human owner, actual owner DM, repository configuration, current permitted source revisions and bounded complete source refresh. Another user, bot message, forged ID or stale action cannot grant approval. The first durable handoff records actor, time, version, evidence identity, task ID, destination and task-budget responsibility before any task preparation. Duplicate clicks and retries use that same identity.

`Task.prepare()` writes full correlation, fixed destination and the bounded untrusted brief together in the first atomic metadata write, with status `preparing`. Startup recovery and ordinary message delivery cannot run that state. After a final source check, `startPrepared()` durably transitions to `in_progress`/`ready` before enqueueing. Recovery can therefore resume a fully authorized task after a crash before enqueue/acknowledgement without inventing another task or losing its brief. Transient source failures stay retryable. If source versions actually change during preparation, the task remains inert and the handoff is marked stale; use a fresh proposal or the normal mention workflow rather than retrying stale authority.

The adapter calls the existing PM task runtime; normal edit-mode and external-action permissions still apply. Starting a task does not file a GitHub issue, authorize a push/merge/release, or grant the observer a shell. Replies in the resulting proposal discussion continue the linked task through ordinary Slack routing. Archie-authored output cannot independently establish source evidence or authorize another start.

Approved tasks expose a message-only `post_to_user` bound to their one persisted owner-DM conversation; the incompatible public-post tool is absent. Runtime checks reject forged targets and inconsistent metadata after reload, while ordinary tasks keep existing behavior. An approved task must deliver its initial PM reply through the bound messaging path before `report_completion` may park it silently; a completion message can supply that reply. Only a confirmed PM send sets the durable marker, never plain assistant text or a system notice. Card consumption follows durable approval: serialized edits replace Start with pending status and then confirmed activation plus the owner-thread link, retaining the proposal and budget context. Edits have their own bounded lease/retry state and never gate task activation. Recovery inspects only due unsynchronized cards, including activated handoffs whose final Slack edit failed. Replayed callbacks neither launch another task nor post duplicate confirmation replies.

Task runtime state and proposal outcome remain separate. `completed`/`report_completion` means parked and may mean clarification, approval or budget/time waiting. Status exposes these waiting reasons; activation or parking never marks a feature successful. Only an explicit owner `initiative outcome` acknowledgement with a repository artifact URL and acceptance result records `implemented`, `released` or `rejected`. An implemented feature remains distinct from a released feature. These records are owner-acknowledged evidence, not independently verified artifact checks; no outcome activates a learner or changes behavior in this release. The offline `ack` command supports `filed`/`implementing` for an external development workflow, preserves the feature intent and cannot declare completion. See the [operator guide](../guides/initiative-operations.md).


## Verification and rollout limits

The historical [refinement verification](../guides/initiative-verification.md) describes its exact earlier patch and remains unchanged. The local release-split receipt records current branch identities and checks separately. Automated checks exercise collection through ordinary investigation, suggestion, owner approval and a real Task runtime with simulated Slack/provider boundaries. They also cover absent evaluation, delivery enablement, shadow mode, source changes/access loss, repeated evidence, controls, uncertain sends, historical-state migration and provider liability recovery.

The real owner-click verification on the preserved pre-split patch delivered one private ACK, consumed its card and retained one task after an authenticated replay. That proves the bounded transport/task path on that exact patch. It does not establish organic eligibility, production activation, usefulness, completed repository work or delivery on this changed split. R1 (inactivity-cache phase), R2 (earlier-deadline rescheduling) and R3 (provider-discovery progress) remain open; R3 still applies to historical recovery. Splitting the release does not close them.
