# Proactive Slack assistance

Archie observes accessible public Slack activity, keeps track of open matters and offers useful help. It can suggest repository work, but only the responsible employee's **Start task** action creates a normal task. Observation uses its own database and works independently of knowledge memory. Reflection, evaluation and self-evolution are deferred to PR #361.

## Sources and storage

`ARCHIE_PROACTIVITY_MODE` alone controls new proactive behavior: `off` skips the subsystem, `shadow` collects and analyzes without new proactive messages, and `live` permits eligible delivery. Startup requires Node 24+, an authenticated Slack workspace and available, explicitly priced model routes. There is no administrator identity, startup DM or separate delivery switch. Extraction defaults to `claude-haiku-5-5`; investigation uses `claude-sonnet-5-5`.

Collection starts at the first successful enablement and preserves that watermark across restarts. There is no backfill, auto-joining, mailbox, private-channel or DM observation. A new public reply may fetch its older parent for context, without importing the older discussion. Bot messages cannot establish commitments or success by themselves. Slack content is evidence, never authorization.

`WORKDIR/initiative/state.sqlite` holds source revisions, observations, matters, jobs, charges, deliveries, feedback and approved task handoffs. It is bound to the Slack workspace, outside the PM's filesystem sandbox and separate from the Markdown knowledge store. SQLite uses WAL and full durability. Back up with SQLite-aware tooling or after a clean stop; a live database copy without its WAL is incomplete.

Edits, deletions and access loss invalidate dependent evidence and unsent messages in a transaction. Processing generations reject stale model results. A process lease and fenced job leases prevent concurrent workers from applying the same work. Missing history, overflow and incomplete pagination remain visible coverage gaps until collection repairs them.

Schema creation belongs to `persistence/schema.ts`. New installations create schema 12; restarts preserve evidence, watermark, approvals, deliveries and charges. There are no upgrade migrations. Older schemas, unknown nonempty databases, wrong workspaces and newer schemas are rejected without changing their data. Archived test databases belong with their original binaries and evidence.

## Analysis and delivery

The scheduler drains at most 32 due jobs per minute within a 45-second drain window; a running analysis has a five-minute bound. Extraction runs hourly and drains pending work between those runs. It processes each thread independently, with at most 6,000 source characters per model request as well as the existing input limit. Findings carry across parts of a long thread; validated parts survive interruptions. Completed threads are applied immediately, so an invalid result cannot hold back unrelated discussions. Bot-only context needs no model call. Investigation refreshes sources before assessing resolution, useful help or one scoped task suggestion in the same model call.

Failed threads are deferred using the existing thread schedule. Three recorded model responses without usable cached output exhaust the unchanged extraction request; further checks wait for new evidence or a changed extraction request without buying the same failure again. The existing request ledger supplies the count, including citation failures after provider completion. Unknown usage retains its reservation. This does not pause collection or other threads, and adds no tables or migrations.

The model identifies responsibility only from explicit human commitments or assignments, using the author's Slack ID or an explicit mention in cited evidence. A direct request for feedback assigns the review to the mentioned person, without implying acceptance or approval of the proposal or spending. CCs and incidental mentions do not establish responsibility. Unknown responsibility stays unknown; participation never supplies a default. Before private delivery, Slack must verify an active internal human and their source-channel membership. Only channel access checks update shared source eligibility; failed employee lookups suppress private assistance without invalidating a valid public discussion.

The model extracts a deadline as a local date, clock time and IANA timezone; host code resolves the instant. Missing date/time/zone, invalid dates, nonexistent spring-forward times and ambiguous fall-back times remain an unknown deadline. The host never silently shifts a time or chooses one occurrence of a repeated time.

New or reopened matters get an immediate check after extraction. Future deadlines get a check 15 minutes before the deadline and at the deadline; overdue matters recur hourly, others daily. Earlier source deadlines advance checks. Human snoozes and dismissals survive extraction. Human activity resets the two-business-day inactivity check for public follow-ups. Active ordinary tasks suppress intervention. The initial extraction and its backlog can delay when Archie first notices a matter.

Unchanged evidence, coverage, configuration, deadline phase, inactivity phase and reminder feedback reuse the previous analysis. Canonical citation sets suppress repeat nudges; changed evidence, a new deadline phase or an agreed reminder can permit another. Cancelling a never-sent nudge clears its notified cache. Sent and uncertain messages retain duplicate protection.

Delivery permits one weekday 09:00 digest of up to five owned matters and two other interventions per destination per day, during 09:00–18:00 Europe/Lisbon. It requires live mode and current source, audience and task checks. Private nudges, digests and task suggestions go to the verified responsible employee. Public help revives the original source thread under the existing inactivity rules, with no recipient or buttons, regardless of matter responsibility. It remains available if an optional private task suggestion cannot verify its employee. There are no new group DMs or fallback DMs. Public replies cannot expose evidence from another channel. The outbox reserves slots transactionally. Interrupted sends remain uncertain and are reconciled using Slack metadata; they are never blindly retried.

Each employee can give feedback on their own matters and inspect their own proposals from their verified DM. Private buttons are visible only to the saved intended recipient, with the same checks enforced server-side. Public messages have no controls. Stop following dismisses that matter without suppressing other employees in the discussion. There is no automatic pause or expiry. Day 14 reports activity and feedback; it does not prove usefulness.

Nudges are short Slack replies with a useful next step; numeric citations stay in structured evidence. Daily digests use matter titles and source links without copying internal analysis details or buying another model call. Existing pending drafts are not rewritten by a code update and still need review before enabling live delivery.

## Background spending

The ceiling is $200 per Lisbon calendar day: routine extraction can use $150; all matter investigations can use the existing priority reserve up to the shared $200 ceiling, regardless of responsibility. The allowance is workspace-wide, not per employee. Each attempt, including explicit retries, reserves a conservative maximum before dispatch. Complete usage settles the reservation; missing usage remains a liability across possible execution days. Old refunds do not accumulate allowance. A pricing overrun is charged in full and blocks further admission until pricing is checked. Exhaustion defers work without pausing the service. At most four background requests can run concurrently.

The base uses direct model requests only. Complete usage settles charges; an interrupted call or incomplete usage keeps its reservation because the provider may have executed it. There is no refund by age. Persistent unknown usage may require external accounting evidence. The base does not store provider credential fingerprints. Prices were checked on 2026-10-20 against [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing).

## Recipient-approved tasks and recall

Investigation may suggest an allowed repository, intended result and current human evidence. Cards use the same outbox, interruption limits and freshness checks as nudges. Before approval they explain that normal task budgeting applies outside the $200 background allowance. A bounded presentation cursor prevents invalid or deferred history from blocking new suggestions.

Suggestion identity uses the repository, stable matter and all current human context in its work thread, independently of model citation selection. Additional cited sources still receive freshness and audience checks. Rewording or citation order does not create another candidate or change its first accepted scope. Fresh human work-thread evidence, another matter or another repository can create a new candidate/version requiring its own approval; an old approval never authorizes the changed scope. Only current unapproved suggestions are eligible for presentation, without a separate filing status.

**Start task** verifies the saved intended employee, their actual DM, current matter responsibility, sent card, exact proposal version, configured repository and fresh accessible source context. A responsibility change invalidates old actionable cards and unsent private deliveries; it never transfers an existing approval. Durable approval records one task identity before preparation; repeated callbacks reuse it. `Task.prepare()` atomically stores its approval, fixed destination and untrusted brief with status `preparing`. That state cannot run. A final source check precedes `startPrepared()`, which records activation before enqueueing. Recovery resumes interrupted authorized work; changed sources leave preparation inert. A transient lookup failure defers approval until source access recovers; channel access loss also requires normal extraction to revalidate the matter. Shadow mode continues valid existing private-card approvals, approved/prepared handoff recovery and their card edits; off mode skips initiative recovery. Activated ordinary tasks retain their normal lifecycle in every mode. Existing edit-mode and external-action approvals still apply.

Approved tasks reply through message-only `post_to_user`, bound to their saved approving employee's DM conversation. Forged targets or inconsistent destination metadata fail closed. Before silent completion, the initial PM reply must receive a confirmed Slack timestamp; assistant text, failed sends and system notices do not satisfy it. Ordinary tasks keep their existing routing and completion behavior.

Complete cited messages, source links and revision IDs are saved in the task's existing read-only shared folder as `proposal-evidence.md`. The short brief contains the approved outcome and points the PM to that file, which it can read in sections using `Read`. Evidence is written before the prepared metadata; a failed write leaves no runnable task, and retries preserve an already prepared snapshot. File contents remain untrusted evidence, and reading them grants no additional permission.

After approval, the card replaces Start with **Starting…**, then **Task started · Open task**. Card edits have separate serialization, leases and durable retries, so a slow edit cannot block activation or overwrite the final state. Recovery handles at most ten due cards per minute. Inspect a linked task with `initiative proposal <id>`. Running, waiting, stopped and parked states do not establish that repository work is implemented or released. This release does not add a separate issue-filing or outcome-recording workflow.

Task-bound observation tools check source access and audience independently of knowledge memory. Public tasks see only their own channel. DM tasks resolve the actual internal human recipient and recheck that person's membership for each public source. Matter explanations are limited to that recipient's own matters; approved tasks also verify that the recipient matches their saved actor. `read_matter` includes current sources, the last 20 distinct decision explanations, next checks, charges, deliveries, feedback and task handoffs. Reads check validity again after awaited authorization. Already-loaded PM context has the same revocation limitation as other evidence.

See [verification and limits](../guides/initiative-verification.md). Local or simulated checks do not authorize activation or establish usefulness.
