# Voice

> Source of truth: `src/voice/` — one module: the conversation, and the Recall transport that carries it. The sections below describe what is built; **Open questions** and **Parked, with reasons** at the end are the named exceptions — known gaps and deliberately deferred work, not implemented behaviour.

Archie can join a live voice meeting — Zoom, Meet or Teams, via Recall.ai — as an ordinary participant: it listens to each speaker separately, answers aloud when addressed, in English or Russian, roughly nine hundred milliseconds after the room goes quiet, and binds the meeting to the task that asked for it so the room's speech and the PM's own work can reach each other. It leaves the same way a person would, too, saying goodbye before it goes, whether the room asked it to, the PM ended things directly, or it is simply the last one left.

## The mistake this corrects

Everything used to land in `src/connectors/voice/`, and that was the wrong shelf. Slack and GitHub are connectors because they are *places Archie is reachable*. Voice is not a place, it is a modality — the medium a conversation happens through, independent of who carries the packets.

That folder was mixing three kinds of thing: the Recall integration itself (the API client, the browser page rendered as the bot's camera, the HTTP and WebSocket routes), capabilities (speech-to-text, text-to-speech, comprehension — vendor-swappable, useful to any way of carrying audio), and domain logic (room silence, the owe flag, the attributed transcript — belonging to voice itself). Those three are now separate files rather than separate folders, all under `src/voice/`.

Separate folders is what the first correction tried, and it went one step too far: the Recall half was moved out to `src/connectors/recall/`, held apart from `src/voice/` by a rule that nothing under the medium may import a connector. That boundary was maintained for a second transport — a Telegram call, a SIP leg — that does not exist, and it charged rent for the wait: every call that had to cross it went through a registered function pointer instead of an import, for two halves that ship, mount and are configured together and are meaningless apart. They are one module again. A second transport is a good reason to split, once one exists; the seam it would want is `VoiceTransport` in `types.ts`, which is a type rather than a folder boundary, and splitting then is a file move rather than a design.

This same principle is what later decided a second question — what to call the *channel* a meeting occupies on a task. See "One meeting, one task" below.

## The shape

```
src/voice/
  the conversation, which knows only that it has a transport:
    meeting.ts          room silence, the owe flag, the transcript, the standing context
    comprehension.ts    was it addressed? what is worth saying? what can Archie find out?
    deepgram.ts         Deepgram Flux: listening
    soniox.ts           Soniox: speaking
    written.ts          the task's written exchange, as a turn sees it
    capabilities.ts     what Archie can find out, summarised once at join
    types.ts            VoiceTransport, AudioSink, Participant, MeetingHost, RosterEntry, WrittenLine

  Recall — Zoom, Meet and Teams via Recall.ai — which is what implements that transport:
    connector.ts        the mount: the HTTP and WebSocket routes, the live-meeting map, the teardown funnel
    recall.ts           Recall's REST API: create the bot, chat, leave, read its status ledger
    audio-out.ts        the page Recall's browser renders as the bot's camera, and the sink that feeds it
    channel-delivery.ts whether a message at a `recall` channel reaches a room, and what to say if not
    pm-tools.ts         join_recall_meeting / leave_recall_meeting

  task-binding.ts       the seam to a task, used by both: the live-meeting registry (process-local),
                        the durable channel record (metadata.json), the host that writes to both
```

`meeting.ts` still names no platform: it is handed a `VoiceTransport` and an `AudioSink` (`types.ts`) and never learns how they are connected, which is what makes a phone call the same interface as a Zoom room rather than a second implementation of the conversation. What changed is that the type is the whole boundary — no import rule underneath it, and no indirection to keep the two sides from reaching each other.

Two registration points reach outward, both at mount: the `recall` channel's deliverer and renderer (`registerChannelDeliverer`, in `src/tasks/channel-delivery.ts` — one call registers both, so a connector cannot wire up delivery and forget how its channel reads) and the PM-tools factory (`registerConnectorPmTools`, in `src/agents/connector-tools.ts`, handed a closure over this mount's own start and stop). Neither `src/tasks/task.ts` nor `src/agents/spawn.ts` names Recall as a result; they look a function up by kind and hand it the work (the rendering half lives in `src/agents/channel-render.ts`, read the same way).

It is called `recall` rather than `zoom` deliberately. Recall reaches Meet and Teams as well; a direct Zoom SDK integration would be a different sibling.

**A phone call is the N=1 case of this design, not a harder one.** A single bidirectional audio stream with no per-participant separation is exactly room silence with one participant: one turn-detection stream, and that speaker's turn state is the room's floor. Nothing in the conversation logic assumes more than one participant, and a test pins it. Outbound calling — Archie ringing someone — is then the same interface with the call originated rather than answered.

**`Participant.id` is an opaque string, not Recall's own integer.** It was typed as a number once, with the conversation keying its per-speaker state on it, which a SIP leg or an SDK with opaque string ids could not have satisfied without inventing one. Recall's integers are stringified where its frames are parsed, and the type carries the rule: compare it and key on it, never parse or order by it. The Recall side has its own tests, too (`src/voice/__tests__/` covers the client, the output hub and the mount), which nothing did while every test exercised conversation code; the properties they pin are the ones that cost a live meeting, `output_media` in the create body first among them.

The connector is optional and config-gated: it mounts only when `RECALL_API_KEY`, `DEEPGRAM_API_KEY`, `SONIOX_API_KEY`, `CEREBRAS_API_KEY` and `ARCHIE_PUBLIC_URL` are all set, in the same conditional-mount style as Slack and GitHub, and costs nothing to leave off. Registration is what makes that gating reach all the way to the PM's tool surface, not just the HTTP routes: a deployment where this function never runs never calls `registerConnectorPmTools`, so the PM in that deployment never sees `join_recall_meeting` at all — absent, rather than present and answering "not configured" at call time. `mountRecallConnector` runs synchronously to completion in `main()` before task recovery (and therefore before any agent can spawn) reaches the first line that could use it, so there is no boot-order window where the tool exists for some spawns and not others.

## One meeting, one task

A meeting has a one-to-one connection with a task. **The meeting does not create the task** — the task already exists, in the thread where someone asked Archie to join, and the meeting attaches to it: the PM calls `join_recall_meeting` with a meeting URL, on the task it is already running. For now one thread hosts one meeting, which keeps the connection genuinely one-to-one, and a second `join_recall_meeting` on a task that already has a live meeting is refused for exactly that reason.

The task already has a structure for durable channels — a `channels` map and a `default_channel` in the shared `metadata.json` — and a meeting now uses it, as a `RecallChannel`: linked and active the moment the meeting starts, marked `ended` the moment it stops, never removed. That reverses a decision recorded in an earlier version of this document, and it is worth saying why, since the reasoning that held then genuinely does not hold now.

The earlier argument was that registering a live meeting there would mean teaching three delivery branches and the context renderer about a new channel kind, for state that dies with the process regardless of where it is written down. Both halves turned out to be avoidable rather than structural. **Teaching three delivery branches** assumed every channel kind has to become one more hand-written `if` in `Task.postToUser` — the actual fix is a delivery seam instead: a small registry (`src/tasks/channel-delivery.ts`) mapping a channel kind to a function that delivers a message on it, which a connector plugs into once, at mount. `task.ts` dispatches through it for any kind it does not natively handle (Slack and CLI stay as direct branches, since they already exist and work) and never learns what `recall` is *for* — it looks up a deliverer by kind and hands the message over, exactly the same way for every kind that ever registers one. **State that dies with the process** conflated two different lifetimes that turn out to need keeping apart. The *live meeting handle* — the audio streams, the open sockets, the `Meeting` closure itself — genuinely cannot survive a restart, and stays exactly where it always has: an in-process registry in `src/voice/task-binding.ts`, keyed by taskId, forgotten the moment the meeting or the process ends. The *channel record* is different: durable metadata about somewhere Archie has been reachable, the same category of fact a Slack thread already is, and there was never a real reason for it to die with the process just because the thing it describes might.

This matters more than it first looks, because of `metadata.json`'s own write model: it is written whole with no lock, so the channel record can go stale — a crash between the live handle disappearing and the record being marked `ended` can leave it saying a meeting is still active when it is not. That staleness is harmless by construction. The record's job was never to prove a meeting is live; it only has to route a post to the right place. Whether the meeting is actually there is decided at delivery time, by the Recall connector's own deliverer (`src/voice/channel-delivery.ts`), which checks the live registry itself and answers "that meeting has ended — the room has already dispersed" when it finds nothing — the same, already-correct outcome a genuinely-ended meeting produces, reached the same way. A post to any `recall` channel — live, ended, or left stale by a crash — always reaches that deliverer, which is what actually decides and explains the outcome; there is no path where a missing or ambiguous record falls through to generic task code that has to explain what a meeting is, because task code never removes the record and never inspects what it means.

The channel kind is named `recall`, not `voice`, for the same reason `slack` is named for Slack rather than for "chat" — it is the same principle "The mistake this corrects" opens with, applied a second time: a meeting is a place Archie is reachable, and that place is Recall, which also reaches Meet and Teams. A future Telegram call would add a `telegram` kind of its own, alongside a `telegram` channel deliverer and whatever tool starts one. The same registration pattern covers the PM's own tool surface: `join_recall_meeting` and its counterpart `leave_recall_meeting` are both contributed by the Recall connector at mount (`registerConnectorPmTools`, alongside the channel deliverer), not built into `comms-tools` — so `spawn.ts` never names Recall, and a deployment with no Recall connector configured never registers either tool at all. The PM there does not see them and get told no; it never sees the tools, which is the stronger property, and worth treating as the default expectation for anything a connector contributes rather than a detail.

The channel key is what makes a stale answer safe — see "Voice is an agent, with tools" below for what it replaces. Each meeting mints its own key (`recall:<session_id>`, where `session_id` is Recall's bot id), and because the record is kept rather than removed, a task that has hosted several meetings carries one `recall` channel per meeting, live or long over, the same way it keeps every Slack thread it has ever had — the PM's own rendered context lists each of them (`Meeting (live)` / `Meeting (ended)`), rather than hiding history that genuinely happened. A wake-up tells the PM to answer through a *specific* channel key; if the PM is slow and a new meeting has since started on the same task, that key still resolves to the *old* record (never a fresh one, since keys are never reused), and the deliverer's own identity check — the live meeting's own session id against the record's — refuses to hand the answer to whichever meeting happens to be live *now*. `getLiveMeeting` alone, keyed only by taskId, would otherwise return exactly that: the wrong meeting, looking perfectly healthy.

Being asked in a thread is therefore still the simplest trigger, and the durable channel it supplies is always a `SlackChannel`, never a `RecallChannel` — `default_channel` is only ever assigned by the `??=` sites that already existed for Slack and CLI, and linking a meeting never touches it, by construction rather than by convention: the code path that links a `RecallChannel` has no line that could assign `default_channel` even by accident. A meeting never becomes the task's default channel.

Calendar-driven joining is a later question, and it is the *same* question wearing a different hat: however a meeting is requested is also where its summary belongs. Deciding one decides the other.

## The transcript is a file, not a publication

The transcript lives as an append-only file inside the task's folder, written as turns finalise. Not one file per task, though — one per **meeting**: each gets its own folder, named to mirror its channel key so the two are derivable from each other with no lookup — the channel key `recall:<session_id>` and the folder `shared/recall/<session_id>/` share the same session id, minted once when the meeting starts and never reused. Inside it, `transcript.log` is what the room heard, `exchange.log` (see "Two records, not one" below) is what Archie's voice and the PM said to each other about it, and `chat.log` is what Archie posted into the meeting's own chat rather than saying aloud. Three files, each the sole owner of one kind of content: nothing appears in two of them. A task that hosts several meetings over its life gets one sibling folder per meeting, the same way it already keeps one `RecallChannel` per meeting rather than a single record all of them share.

The path helpers and the appenders that write these files (`getMeetingPath`, `getMeetingTranscriptPath`, `getMeetingExchangeLogPath`, `getMeetingChatLogPath`, `appendMeetingTranscript`, `appendMeetingExchange`, `appendMeetingChat`) live in `src/tasks/persistence.ts`, beside the ones for `memory/`, `attachments/` and `artifacts/` — not in the Recall connector. That is deliberate, and worth being explicit about, since it looks at first glance like the same "core must not know what a meeting is" violation "The mistake this corrects" above warns against. It is not: that principle is about *dispatch* — `Task.postToUser` deciding what to do with a message by branching on the channel kind, which is exactly what the delivery seam (`src/tasks/channel-delivery.ts`) removed — not about where a path-building helper is defined. `persistence.ts` already names Slack's and GitHub's own shapes (`appendSlackMessage`, `appendGitHubEvent`); a meeting's files are one more of those, not a special case, and moving them into the connector would have made Recall the one channel whose persistence worked differently from every other.

`chat.log` exists for a narrower reason than the other two, and it is worth stating: the `CHAT:` half of a spoken answer leaves through the transport's chat channel and, before this file, was persisted **nowhere in the task** — not in the transcript (nothing said it), not in `exchange.log` (that is the consult trail with the PM), not in `knowledge.log` or `events.jsonl` (the medium's own writing reaches neither). Its only trace was the activation log under `voice-logs/`, a measurement corpus outside the task folder. So it is not a convenience copy of anything; without it those lines are simply gone.

A fourth file lives beside those three: `metadata.json`, facts about the occasion rather than what was said in it — platform, when Archie joined, when the meeting ended and for how long, and the roster Recall recorded — so an agent opening a finished meeting's folder knows what it was without reading `transcript.log` end to end. It mirrors the task's own `shared/metadata.json` in the way that matters: `getMeetingMetadataPath` sits beside the other path helpers in `persistence.ts`, and `writeMeetingMetadata` writes it whole, with no lock, the same write model `Task.save` already uses. Unlike the two append-only logs, most of the file is written exactly twice — once from `startMeeting`'s success path with whatever is known that early (the URL, the bot id, the instant Archie joined), once more from `endMeeting`'s teardown with whatever a best-effort fetch against Recall's own API found by then. One field breaks that pattern: the live participant roster is rewritten again on every join and leave in between, so a reader does not have to wait for the meeting to end to see who is in it — see "Presence, and when the room empties" below. That fetch is genuinely best-effort: Recall's roster and title are themselves async artifacts that may not be ready, the fetch itself can fail outright, and a platform may simply never supply a title at all. None of those three cases invents a value — every field the fetch could not supply stays `null`, which is what lets `null` mean exactly one thing throughout the file: not known, for whatever reason. `archie_joined_at` is named for what it actually is, deliberately never "when the meeting started" — Recall has no record of the latter, only of the bot's own status, and a room Archie joined late has already said things the transcript will never show. `email` is left off the roster entirely rather than modelled as an optional field: it only ever populates for a calendar-dispatched bot, and every bot here joins from a raw URL, so for this deployment it could never be anything but `null`. See [Task Persistence](./persistence.md) for the exact shape.

Not a published artifact. Publishing is a snapshot mechanism — something has to call it, so the shared copy is only ever as current as the last call, and a meeting that ends unexpectedly loses everything since. A plain file is current by construction, needs no publishing step, and survives a crash with everything up to that moment. It is the same reasoning that removed the second clock from the conversation model: do not maintain a copy when the original is free.

It being a file rather than prompt text is the point. An agent that needs to know what was said greps for it, instead of us guessing in advance which part of it was relevant.

Nor should there be a maintained summary of decisions. That is derived state, it goes stale, and it contradicts keeping this simple. The raw record is the context.

**What it records is what the room heard, not what Archie meant to say.** When an answer is cut off part-way, the delivered prefix — not the whole thing, and not nothing — is what belongs in the record, and that is what gets written, at sentence granularity. Getting the boundary right took a wrong turn first: the obvious source is a byte counter sampled at the moment each sentence is dispatched to the synthesizer, but dispatch happens the instant the text is handed over, routinely before the previous sentence has even finished arriving as audio — so a dispatch-time count can claim a sentence was heard in full when the room actually got half of it. The boundary is anchored on the audio side instead: Soniox opens one stream per sentence and knows the instant that stream's audio has actually finished being delivered, and that moment is checked against the room's own conservative confirmed-played watermark before a sentence counts as heard. That report is a requirement of the synthesizer contract rather than a capability to be tested for — `SpeechStream.say` in `types.ts` takes a per-sentence completion callback that is not optional — so a synthesizer with no per-sentence identity to report, such as Deepgram's Aura streaming a whole answer through one long-lived socket with coalescing flushes, could not sit behind this interface at all. Recording the confirmed prefix lets the next decision see exactly how much the room already heard and continue, rephrase or drop it, with no resume logic anywhere.

This is one recurring defect wearing different masks: the record claiming something the room did not hear. A mid-stream failure filed as chosen silence, a stalled synthesis filed as a complete answer, an interruption recording nothing of what was actually said — three different mistakes, the same fix every time it can be applied: make the record match what was actually heard, at whatever granularity that takes.

**The transcript is what was spoken in the room, and nothing else a reader could mistake for that.** A PM's answer and a consult question genuinely never reach this file — writing either in would falsify the record, reading later as though somebody in the room had said it, and persisting in the task folder as the meeting's history. The one thing that is written in without anyone having said it is a header line naming the meeting URL just joined, at the very start of the meeting's own `transcript.log` — logged under the reserved speaker `meeting`, a name no participant can have, so it cannot be mistaken for one. It used to also mark the boundary between successive meetings running together in one shared file; now that each meeting has its own folder there is no such boundary left to mark, and the line is kept purely as a header. Everything else reaching the voice agent — PM answers and consult questions among them — still has to arrive by some other route, and does.

## Every turn is prepared from the same context

A turn costs at most two model calls — the addressing gate on a candidate turn, and the speaking call once the room has gone quiet — and both read one context, assembled by one builder (`buildSpeakingUserMessage` in `comprehension.ts`). Two builders would be two versions of what the conversation is, drifting apart, and a gate reasoning over a different window from the answer behind it is worse than no gate. Only the *window* differs, and only for the addressing gate: it sees the last sixty seconds, because its prompt calls a false positive the worst thing Archie can do and a wider window only offers more chances to fire on an older mention of the name that was never aimed at us. Nothing sits between the gate and the answer: the speaking call reads the room and decides alone, in one streamed reply. It is also the only one of the two that asks for the model's native reasoning (`reasoning_effort`), which Cerebras returns on its own channel, wholly ahead of the first spoken token — so nothing has to be stripped back out of what is about to be said, and the reasoning is kept on the turn row rather than spoken or posted. Its tokens come out of the same completion budget as the answer, which is what sets that call's token cap.

Beyond `<transcript>` and `<consults>`, three standing blocks. Each is **absent rather than empty** when it has nothing in it — an empty `<participants>` asserts there is nobody in the room, which is a claim, whereas an absent one is silence — so a meeting that gets none of them sends byte-for-byte what it sent before any of them existed, which is what keeps the stored measurements in `tools/voice-cases/results/` comparable.

- `<participants>` — who is in the room, **including everyone who has never made a sound**. `meeting.ts` cannot work this out: its own participant map is populated from `onAudio` alone, and Recall sends nothing at all for a muted participant, so a room of four with three muted looked like a room of one. The roster that can is the connector's own, built off the same join and leave events `metadata.json`'s `live_participants` uses; it is pushed into the conversation through `Meeting.updateParticipants` at both those call sites, with the same snapshot, so the file and the prompt can never disagree about who is present. ~25 tokens for a room of four, ~80 for twelve.
- `<written>` — what reached Archie or the room **in writing rather than aloud**, from two sources that each own their content and neither of which is a copy of the other: the task's own written exchange (its Slack thread, or the CLI conversation on a task with no thread), and Archie's own posts into the meeting chat. Its own block, never folded into `<transcript>`, and that separation is load-bearing rather than tidy: `parseReply` keeps `CHAT:` text out of the spoken transcript precisely so Archie cannot come to believe it said what it only wrote, and merging the blocks would hand that belief back through the other door. ~1.7k tokens for a real task's actual thread, bounded at ~6.1k.
- `<capabilities>` — what Archie can go and find out, in plain language, so a turn can judge *can I find this out, and is it worth the wait?* Everything needed to answer that already exists in a deployment — the PM's roster, its skills' descriptions — and every word of it is unusable in a room: they name agent ids, skill names and the exact phrases that trigger them. So one model call at join rewrites it (`capabilities.ts`, prompt in `prompts/voice-capabilities.md`), and the summarising step is the point rather than an optimisation: it is the only thing between the machinery and a live microphone. **Two layers, not a list:** areas of work at the left margin, and under each, indented, the specific things that can be found out or done in it. The split is there because the block is read at two depths for two different questions — asked out loud "so what can you help us with?", only the areas are sayable, because speech is serial and reciting twenty capabilities costs the room the floor while transferring almost nothing; asked silently about something somebody just said, the specifics are what a real question can be matched against. A flat list of specifics served the second question and got recited for the first, which is what the restructuring fixed. Observed at 1,585 characters for this deployment — five areas and twenty specifics — measured off the block pinned in `tools/voice-cases/promptio.mjs`, which is the summariser's own output rather than a hand-written stand-in. No token figure is given here because none has been measured since the shape changed, and no ceiling either: what a larger deployment's two-layer block runs to is unmeasured.

**The written exchange is read fresh every turn rather than seeded at join, and that is a deliberate trade.** A copy seeded once can fall behind — a thread message arriving mid-meeting, an edit — and nothing about a stale copy says so; re-reading has nothing to go stale. It costs one local read of the task's own `events.jsonl`, which is where that exchange already lives as structured data rather than as prose a regex would have to scrape back apart. So there is no cache and no invalidation to get wrong. The one thing that *is* held is Archie's own chat posts, and only because nothing else records them at all (see `chat.log` above).

**The speaking call now reads the whole meeting, not three minutes of it.** It used to be windowed on the theory that older conversation was distractor text competing with the question being asked now; a real meeting does not bear that out — a question at minute fifty is routinely about something decided at minute five, and an agent that cannot see the decision either invents an answer or asks the room to repeat itself. The retained transcript is bounded at three hours as a backstop rather than a window, with the arithmetic against the model's context window written into the constant itself (`TRANSCRIPT_WINDOW_MS` in `meeting.ts`). Widening it is close to free in the only currency the room feels: time-to-first-byte is flat with input size, measured at +2.3ms per 1000 tokens with no correlation across 156 samples.

## Presence, and when the room empties

Participant join and leave events arrive on the same realtime socket that already carries audio — no second connection. Two questions used to be answered from them; only one is now.

The first is bookkeeping. `metadata.json` gains a `live_participants` field, rewritten on every join and leave from the moment the first participant arrives — well before the meeting ends, unlike everything else in the file (see "The transcript is a file, not a publication" above). An entry is closed rather than removed on leave, so someone who left part-way through the meeting still shows when they arrived and when they went, rather than simply vanishing from the record. This is deliberately not reconciled with `participants`, the roster Recall's own API supplies at teardown, and the two are allowed to disagree: `participants` is Recall's deduplicated final view, populated once, after the meeting is over, with no timestamps at all; `live_participants` is this connector's own presence-over-time record, live and best-effort, from the moment Archie joins. Merging them would mean inventing a rule for which one wins when they differ — a network blip producing two joins this connector sees as two entries but Recall's own dedup collapses into one, for instance — so both are kept instead: a reader who wants "was X ever here" can check either, and a reader who wants "when" has only `live_participants` to check. Archie's own join and leave never reach this field, filtered the same way it is absent from `participants`. See [Task Persistence](./persistence.md) for the exact shape.

The second is the meeting's own end — and this connector no longer decides it. **Recall pulls the bot out of an empty room itself**, on the `automatic_leave.everyone_left_timeout` set in the create-bot body (`recall.ts`); the engine's job is to notice and clean up after it. That timeout is sixty seconds rather than Recall's own two-second default, for exactly the reason a local grace period used to sit here: Zoom hands a rejoining participant a fresh id, so on the wire a reconnect is `leave(id1)` followed moments later by `join(id2)`, and in a two-person call that gap is a room with nobody left in it. Every ordinary cause reaches it — a dropped connection, "hold on, let me rejoin," a host restarting the meeting — and two seconds tears the bot down mid-conversation with no word said, waking the PM with a summary that reads as though the room had dispersed while people were still in it. Sixty covers a reconnect (~30–45s) and a deliberate rejoin.

Leave events still arrive, and are still recorded as above, but **nothing is inferred from them any more.** Three mechanisms here used to guess at an ending: a forty-five-second teardown armed when this connector's own roster emptied, a question put to Recall ten seconds after the audio socket closed, and a three-minute sweep of meetings that had gone quiet. All three were guesses at a fact Recall already held, and each was wrong in its own way. The roster's guess had been racing Recall's own two-second default for the whole time it existed, and would have lost. The socket's guess could never be more than a question, since "audio stopped arriving" is equally true of an ended call and a two-second network wobble. And the sweep was the only thing that noticed at all when Recall sent no leave event — in one live run a colleague left, no leave ever came, `left_at` stayed `null` in the metadata, and the sweep tore the meeting down at 11:47:48 for a call Recall's own bot record says ended at 11:44:43; the PM's summary reached the Slack thread three and a half minutes after everybody had gone, which the person waiting for it experienced as the summary simply not arriving.

**One signal replaces all three: a thirty-second poll of each live bot's own status ledger** (`STATUS_POLL_MS` in `connector.ts`). Each tick reads `status_changes[]` for every meeting in the live map and ends the ones Recall reports out of the call. Three statuses are read as proof: `call_ended` ("the bot has left the call"), `done` ("the bot has shut down", which can only follow leaving) and `fatal` (shut down on an error) — in all three Archie is out of that room and cannot return without another join, so nothing is protected by holding the meeting open. A terminal code anywhere in the ledger counts, not only its last entry: a bot never rejoins, so a later post-processing or breakout-room entry cannot un-end it. Everything else — the in-call statuses and any code Recall adds later alike — ends nothing. The set is closed over "certainly out" rather than open over "certainly in", because being wrong in the permissive direction ends a meeting that is still going, while being wrong in the other direction costs one poll interval. A failed request is logged and ends nothing, with the next tick asking again; a tick that finds the previous one still in flight does nothing at all, so a slow round of requests cannot stack behind itself.

What that costs is bounded, and worth naming rather than hiding: Recall's ledger lags its own audio by a couple of seconds — observed live, the audio socket closed at 11:44:40 and `call_ended` landed at 11:44:43 — so on the ordinary room-emptied path the PM's wake-up arrives up to about a minute and a half after the last person left: the sixty-second timeout, plus that lag, plus at most one poll interval. Paid, once, so that a rejoin is never read as the room dispersing.

Whichever way it is reached, ending runs through `endMeeting`, the one teardown funnel: the PM's own `leave_recall_meeting` tool, a spoken `LEAVE:` (see "Leaving the room" below), the DELETE route, process shutdown and the poll all go through it. It deletes the meeting from the live map synchronously before its first `await`, so whichever route gets there first, the rest find nothing to end. The recorded `meeting_ended_at` still prefers Recall's own `call_ended` status over the wall-clock instant `endMeeting` itself ran, falling back to that instant only if Recall's ledger never supplied one — when the room emptied is a different fact from Recall's own record of when the call ended, and the field keeps naming the latter.

Ending also now waits on whatever the room was in the middle of. `endMeeting` calls `Meeting.stop()`, which abandons any turn still in flight and then awaits it settling — bounded by that turn's own model-call timeout (fifteen seconds worst case), and silent, since the sink is already cut — before metadata is written and the PM is told the meeting is over. Without that wait, a turn that resumed after teardown was indistinguishable from one that had finished cleanly: the whole answer would be written to `transcript.log` as spoken, a `CHAT:` half posted into a room that had already dispersed, a `LEAVE:` acted on, and a `PM:` question sent to a PM that had, moments earlier, been told the meeting was over and handed its transcript to summarise.

## Voice is an agent, with tools

Not a medium with a model call bolted on, and not a session on the agent runtime either. **The distinction that matters is speed:** the agent runtime takes seconds per turn, and the voice loop gets first sound out in roughly nine hundred milliseconds, measured at the socket in `meeting.ts`. Everything the latency work bought depends on that loop staying tight and stateless.

The reconciliation is that **a tool call which returns instantly does not block a fast loop.** So voice runs its own loop, and that loop has tools.

Consulting the PM is one such tool. It resolves immediately — *the request has been sent, the answer will reach you later* — so Archie can say "I'll look into that" and the room carries on. The extra round trip is paid only on the turns that consult, which are exactly the turns where Archie was going to acknowledge and wait anyway, so it is invisible. Every consult is still numbered internally (`nextConsultId` in `meeting.ts`, combining a per-process meeting ordinal with a per-meeting sequence, so an id can never be mistaken for one from a different meeting even in the activation log) — but that id never reaches a tool schema any more. Correlation is the channel plus a cap of one instead: the PM answers through the ordinary `post_to_user`, targeted at this meeting's own channel key, and once an answer is confirmed to belong to *this specific meeting* (see the identity check above), there is exactly one question it can be an answer to — so `Meeting.deliverConsultAnswer` pairs it with that one, and the pairing is exact rather than a guess. It replaces a defect that was worse: naming an id and getting it right was the earlier design's entire job on every reply, and the failure mode when a caller got it wrong (or simply answered "whichever one is still outstanding") was a specific, confident answer landing on the wrong question — the LIFO defect ids were introduced to fix in the first place.

**At most one question may be outstanding at a time, and `routeConsult` enforces it.** This is what makes the pairing exact, and it was not always so: correlation used to be FIFO over however many questions were out at once, which is the right pairing only while the PM answers in the order it was asked. Answer two out of order and the second question's answer is filed under the first, rendered as that question's `A:` line, and read by the model as something that came back for this room — so it states it, confidently, as the answer to a question it does not answer. That is the D8 provenance failure the suite grades for, and a live room hit it. Nothing in the transport can fix it: the id `nextConsultId` mints never leaves the process, and `deliverConsultAnswer` takes text alone. One outstanding question removes the pairing decision altogether, which is the only mitigation that does not put an id back on a tool surface.

A second question written while one is outstanding is therefore **refused rather than queued or swapped in**, and it is refused *visibly*: a `warn` in the log, `pmDropped` on the turn's activation row (so the escalation rate computed from the corpus does not count questions that were never asked), and a row of its own in the consult exchange carrying a parenthesised `(not sent — …)` in place of an answer, which is the record the model itself reads every turn. It can raise the question again once the first one answers, and that is a decision it makes rather than something machinery does behind it. The alternatives are worse in a live room: queuing would send the question minutes later at a moment nobody chose, possibly after the room settled the matter itself, and would need a second place where a question can leave — the exact "exactly once, from one call site" property below; swapping the new question in for the outstanding one guarantees the mispairing rather than merely risking it, since the PM has already been asked the first question and its answer would land on the replacement. What refusal costs is real and worth naming: the room has usually just been told somebody is being asked, and for that second question nobody is. The trade is a question visibly not asked, against an answer confidently attached to the wrong question with nothing anywhere to notice it by.

When the PM has an answer it calls `post_to_user` with `target: { channel: "<this meeting's channel key>" }`, and the answer is delivered straight back into the meeting that asked — or, if that meeting has since ended, `post_to_user` relays the Recall connector's own note saying so, rather than delivering anything or reporting a silent success. The voice agent, on a genuine delivery, receives it and **narrates it in its own words** at the next quiet moment, because the thing that knows how to speak is the thing whose whole prompt is about speaking. The PM never talks into the meeting; it answers the agent. This is why PM output does not need a separate renderer, and why it must not be poured into the transcript — it is context for the agent, not something the room said.

**A question is not part of the answer's delivery and does not share its fate.** It never had the room as its destination, so nothing about what the room did or did not hear bears on whether it should be asked: a reply that consults the PM with nothing else worth saying is delivered exactly as if something had been spoken too, so is one whose spoken half never reaches the room and falls back to chat, so is one cut off part-way through being spoken, and so is one discarded whole because the room moved on while it was being written. The routing sits in one place for that reason — a `finally` around the whole speaking turn (`answerRoom` in `meeting.ts`), which is what makes a question reach the PM exactly once, on every outcome, rather than on whichever branches remembered to send it.

That last point was learned the expensive way. The interrupted case was originally left undelivered on purpose, reasoning that the debt survives an interruption, so the next quiet moment reconsiders the whole conversation and can ask again if it still needs to — and delivering it as well would risk the same question reaching the PM twice with two answers coming back, one of them stale. The reasoning does not survive contact with a real room. Barge-in is the ordinary case with several people on the call, so the shape being sacrificed was the common one, not an edge; the room has usually just been told that somebody is being asked; and nothing anywhere reports the drop, so the failure is invisible from both ends. The double-ask it was avoiding is the milder problem and is already mitigated: every turn is prepared with the consult trail in front of it, so a question already asked is visible as outstanding, and asking again is a decision the model makes rather than an accident. A question that was never asked leaves nothing for anybody to see.

**The risk to design against is over-escalation** — every question becoming a consult. That is a prompt problem, and the activation log records every question raised, which is enough to watch the rate before it becomes a habit.

### No longer framed as an external channel

Both wake-ups voice sends the PM — a live question, and a finished meeting's transcript — used to treat the meeting as a channel Archie could not vouch for. A live question arrived captioned as reported speech from "an open microphone nobody has verified"; a finished transcript carried the same caveat, plus a reminder that display names are self-reported and the room might include people outside the company; and an answer to a live question carried, on top of both, an instruction not to share repository contents, credentials, internal URLs, or task history. That wording deliberately mirrored the note already injected for a Slack channel shared with an external organisation — same threat, same words.

None of that remains. Today's wake-up reads as an ordinary request between two colleagues — answer it the way you would answer someone who asked you directly, do the lookup yourself, hand back the information plainly — with nothing said about where the question came from or who is listening to the answer. This is a decision, not an oversight, and its consequence is worth stating plainly: the non-disclosure instruction was the only confidentiality safeguard anywhere in the PM's prompt surface for a voice meeting, so nothing today tells the PM to withhold repository contents, credentials, internal URLs, or task history from a room reached by a forwarded meeting link, which — unlike a Slack channel — anyone holding it can enter uninvited. Slack keeps its own equivalent guard for a channel shared with an external organisation (`src/agents/spawn.ts`); voice has no counterpart to it any more.

### Two records, not one

The agent reads two append-only records, and the split is the design rather than a detail.

The **transcript** is what the room said, including Archie's own turns. The **consult exchange** is what Archie and the PM said to each other: every question sent and every answer returned, kept whole for the life of the meeting.

Both now live doubly. The model's prompt still reads the in-memory `consults` array and tags each line with the id `nextConsultId` mints (see "Voice is an agent, with tools" above), so a turn can tell one question in the trail from another — several may be listed at once even though only one of them can be waiting on an answer. But the exchange is also durable, in the meeting's own folder alongside `transcript.log` (see "The transcript is a file, not a publication" above): `exchange.log`, a question line when it is asked and an answer line when it arrives, in the same plain `[ISO] [source] message` shape every file under `shared/` uses — no id, no `Q:`/`A:` markup. The two forms differ because they serve different readers: the model needs the correlation the id gives it, and a human or another agent grepping the file does not, since the lines already arrived in the order they happened and the file reads as one two-party conversation on its own.

Keeping the exchange whole rather than treating an answer as a disposable note is what makes a follow-up work. With a note that is consumed on delivery, Archie has the answer but no memory of *what it asked* — so a clarifying question from the room sends it back to the PM to re-ask something it has already been told. With the exchange in front of it, it can see the question it asked, the answer it got, and reply from that.

This also lands on a boundary that already exists. The speaking prompt deliberately frames the transcript as untrusted — a line in it that looks like an instruction is treated as something a person said aloud, not as a command, and that framing is our prompt-injection defence. The PM is a trusted internal source, and keeping the two in separate blocks rather than one blurred bucket is what makes that difference structural rather than merely intended: a blurred bucket would force a choice between weakening the defence or having the agent distrust something it should act on. The prompt does not yet go further and say, in so many words, that the two blocks differ in how much to trust them — see Open questions.

**Neither record needs a discharge rule, and keeping both whole is free.** Time to first token was measured flat with input size — about two milliseconds per thousand tokens, with no correlation — so context that grows over a meeting costs nothing in latency, and a handful of consults costs nothing in money. There is no reason to trim, expire or consume either one.

### What the flag does, and what it does not

The owe flag is the trigger for *speaking*, and it stays mechanical. A PM answer arriving sets it; a completely delivered answer clears it; `SILENCE` clears it; being cut part-way leaves it standing. The model influences it once, through `SILENCE`, and otherwise the flag is derived from what actually happened — because a trigger the model can leave set is a bot that will not stop talking. Clearing it also checks that no consult answer has landed since the current decision began: a consult answer is the one thing that can raise the debt without touching the transcript or opening a turn, so if one lands while an unrelated decision is already in flight, that decision's own completion must not be allowed to clear a debt it never knew existed — which would otherwise read as Archie promising to check with the team and then simply never coming back.

Nothing about the exchange is tracked alongside it. Whether an answer was conveyed is visible in the transcript, which records Archie's own turns; whether it was conveyed *fully* is visible in how much of it was delivered. The records answer the question, so no boolean has to.

One consequence, stated rather than hidden: the model may decide not to convey a PM answer at all, if by the time it can speak the room has plainly moved on. The flag then clears on whatever it says instead. That is the same judgement it is trusted with everywhere else, and forcing a minutes-old answer into a room that has moved on is the behaviour we would be trying to avoid.

A second consequence, mechanical rather than judged: an answer arriving when nothing is outstanding — every consult already answered, or none ever raised — must not raise the debt either. `Meeting.deliverConsultAnswer` refuses in exactly that case, reporting failure rather than mutating anything, for the same reason a retried delivery of an already-answered consult used to have to be refused: forcing a fresh decision with a live microphone for no reason is the false-trigger class this design treats as the most expensive mistake a voice meeting can make.

### Leaving the room

A third marker, `LEAVE:`, lets Archie end its own attendance — the same shape as `CHAT:` and `PM:`, a trailing line on a reply that otherwise reads exactly as a normal turn. It takes effect only once the farewell in front of it has actually reached the room: `routeLeave` fires from exactly the branch of the speaking decision where a reply was spoken in full and nothing cut it short, so a goodbye that gets interrupted, or never reaches anyone's ears at all, leaves Archie in the room precisely as if it had never been said — the next quiet moment is free to reconsider the whole conversation, goodbye included, the same as anything else that gets cut off. Reaching this point calls `MeetingHost.leaveMeeting`, which calls `endMeeting` — the same funnel every other ending goes through (see "Presence, and when the room empties" above).

This is a different door from the PM's own `leave_recall_meeting` tool. That one is a direct request from the PM, with no farewell attached and no dependency on anything being heard — the PM decided to end the meeting, not the room's own conversation, and by the time the tool returns the bot is simply gone. `LEAVE:` is the room-initiated, spoken-first counterpart: reached only from inside the meeting's own turn, only after Archie has actually said goodbye.

## Events, and who reacts to them

The voice side emits facts and keeps the record. It does not interpret.

Three events go to the knowledge log through `appendMeetingEvent`: a meeting started, a meeting ended, and a question was put from the room to the PM. The first two point rather than carry — `recall/<sessionId>/` — because `knowledge.log` is read whole at the start of every PM turn, the same reasoning that already keeps room speech out of it, and the meeting URL belongs in `metadata.json`, not duplicated into a log an agent cannot selectively skip. The question is different: it carries its own text in full (`consult: <question> — recall/<sessionId>/exchange.log`), pointer included for whoever wants the eventual answer — the volume concern that keeps room speech out of this log does not apply to a single asked question, which is exactly the actionable content the log exists to surface. On meeting end, the PM is also sent a message telling it to go and look — the mechanism Archie already uses to wake an agent on a logged event. `appendMeetingEvent` also emits the same live `'message'` event every other inbound appender in `persistence.ts` emits (`appendCliMessage` is the clearest sibling) — it used to be the one appender of the nine sharing that shape which stayed silent on the event bus, which is why voice activity used to be invisible to a live CLI/SSE view; it is not any more.

The PM's side of the exchange is not a fourth event of that kind, but it does land in the same log — through the ordinary path every Slack or CLI reply already takes. `Task.postToUser`'s delivery seam (`deliverThroughSeam` in `src/tasks/task.ts`) reads the connector's own `delivered` flag, not the wording of its note, to decide whether the message is appended: a genuine delivery is logged with the channel's own key as its destination (stable and unique across every meeting the task has ever had, unlike the live/ended status `ChannelRenderer` renders for the PM's context block), and a delivery the connector reports as failed — the meeting already ended, or nothing was outstanding to answer — logs nothing, the same way a failed Slack post already logs nothing. Without this, the question a voice agent puts to the PM was durable and the PM's answer was not, an asymmetry between the two ends of one exchange rather than a deliberate property of either. The same two messages are also written whole to the meeting's own `exchange.log` (see "Two records, not one" above) — a second, meeting-scoped record of this one exchange, for a reader who wants that conversation on its own rather than mixed into the task's whole knowledge log.

**What to do about a finished meeting is the PM's business.** The reasonable default is a written summary — saved to a file, published as an immutable artifact, and delivered to the task's durable channel as a file rather than pasted into a chat message. What a summary should contain, what it should leave out, and how to deliver it is a skill's judgement (`recall-meetings`), not code in this module — keeping that judgement there means it can change without touching any of this. The connector should never summarise; it reports and keeps the record.

A PM woken by a finished meeting is in a different position from one woken by a Slack message — it has a transcript to read and a room that has already dispersed — so its wake-up prompt differs from the ordinary one.

## Open questions

**A PM already mid-task when a meeting ends.** Unresolved.

**Recurring meetings.** One task per occurrence is simpler; whatever needs to survive between them can go to the log. Not urgent.

**Consult quality is not yet in the corpus.** The activation log now shows that a question was raised and what became of the turn that raised it — spoken, silent, chat-only, cut off — which is enough to watch the escalation rate on its own. It does not show what the PM actually answered, or whether a later turn used it, so a consult that got a bad answer looks exactly like one that got a good one.

**The transcript is framed as untrusted to the model; the consult exchange is not framed at all.** The two are kept in separate blocks — the structural half of the defence, and that half is built. What is missing is a sentence telling the model the two blocks differ in provenance — that the transcript is reported room speech and the consult exchange is a trusted colleague's answer — so today the separation relies on the model inferring that from two different tag names rather than being told outright. Closing it means another edit to the speaking prompt, and prompt edits here have measured non-local effects, so it wants its own measured before-and-after run rather than riding along on something else. Not done yet for that reason.

**A failed chat post can leave the record claiming a delivery that did not happen.** On the chat-only fallback path, the transcript records the answer as spoken before the chat post is even attempted, and that post swallows its own failure — logged, not surfaced. A post that then fails leaves the transcript saying the room got an answer it never received. Narrow and pre-existing, and the same recurring defect named above wearing one more mask; noted here rather than fixed in passing.

**Settled: FIFO pairing an answer with the wrong question.** This stood here as a known, accepted cost — with two consults outstanding and the PM answering out of order, the answer landed on the older question, silently — on the reasoning that any mitigation strong enough to fix it would mean putting an id back on a tool surface. That reasoning was wrong: capping outstanding questions at one fixes it without an id anywhere, by removing the pairing decision instead of trying to make it correctly. `routeConsult` now refuses a second question while one is unanswered, and records the refusal where the log, the corpus and the model can each see it. See "Voice is an agent, with tools" above for the cap and what refusing costs.

**Settled: a delayed answer arriving in a room that has moved on.** The consult mechanism above already covers it: an answer never forces its way in, it only raises the debt, and the debt is discharged only once the room is genuinely quiet — at which point the model reconsiders the whole conversation fresh, consult answer included, and may decide the moment for it has passed.

**Settled: disclosure.** Archie announces itself in the meeting chat on joining and appears in the participant list under its own name, so its presence and its listening are disclosed to the room. The transcript stays in the task folder rather than being posted to a channel.

## Parked, with reasons

**Calendar-driven joining.** Deliberately later. See above — it is the same question as where a summary belongs.

**Emotion tags.** Soniox supports inline emotion markup. It would add a new output channel to the model's contract, and prompt edits in this repo have measured non-local effects, so it wants its own pass behind the case suite.

**Bracketed text is silently deleted by the speech engine**, so a spoken `[503]` vanishes without an error. Two prompt wordings were tried and measured; both left the headline metrics intact and broke something unrelated — one made the bot read *more* identifiers aloud, the other made it drop an owner's name the transcript had supplied. The next attempt should teach the mechanism (brackets are consumed as emotion markup) rather than assert a rule, which is likely why both attempts leaked into neighbouring behaviour. Exposure is small: the `CHAT:` line is never spoken, so brackets only matter in prose.

**The connection route lottery.** Roughly forty per cent of speech connections draw a path about a hundred milliseconds slower for the life of the socket, and the handshake time predicts it with no overlap. One reconnect above a threshold fixes it. Measured twice live; not worth the code yet.
