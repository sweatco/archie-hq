# Trigger task owns conversation

**Date:** 2026-08-19 · **Status: Implemented (this PR).**

## Brief

A trigger fire should produce a task that owns its conversation. On a channel-message fire the triggering message lands in the task knowledge log, where every agent on the task reads it, and the triggering thread is the task default channel. On a schedule fire the task opens its OWN thread in the channel the trigger was bound to, on its first post to the user, so a human reply routes back into that same task instead of starting a stranger task. That channel is the task home: its standing context applies from turn one, posting there is post_to_user, and posting anywhere else stays detached as today. Base: the branch of PR #291, whose single Slack render path this change consumes.

## Design

PROBLEM. A trigger fire spawns a fresh task, and today that task does not own its conversation in either firing mode. On a channel_message fire the triggering message is never written anywhere the task can read: `dispatchChannelMessageTriggers` renders the message body and passes it as `FireContext.text` (src/connectors/slack/events.ts:879), and `fireTrigger` never reads that field — grep for `context.text` across src returns nothing — so the only thing the PM is told is that 'a new message in #x matched your filter'. Nothing reaches knowledge.log, so a delegated repo or plugin agent, which sees only the log, cannot know what was said. On a schedule fire the task gets no thread at all: `fireTrigger` links a thread only in the message branch (src/system/trigger-scheduler.ts:370) and the schedule branch instead seeds a prose sentence telling the PM to post to '#<channel_name> (Slack channel ID …)'. The only tool that can post into a channel the task is not in is `post_to_channel`, which is deliberately detached and demands a `mandate` — a verbatim quote of a human in this task asking for the post (src/agents/tools.ts:1058) — which a scheduled fire has no way to produce honestly. When such a post does land, a human reply to it starts a brand-new task (the reply's root author is our bot, so `mayWakeTask`/`shouldCreateNewTask` seeds a stranger task) with no trigger directory, no history and no idea an automation exists.

APPROACH. Give the fired task a home. A new optional `TaskMetadata.home_channel` names the Slack channel the trigger was bound to, written by `fireTrigger` on a schedule fire. It answers exactly two questions that a task with no thread yet cannot otherwise answer: where do I open my thread, and which channel's standing context applies before one exists. `Task.postToUser` grows one new branch: when there is no default channel and `home_channel` is set, it posts the message as a NEW top-level message in that channel (no `threadTs`), takes the `ts` that `postSlackMessage` returns (src/connectors/slack/client.ts:191 — it already returns `Promise<string | undefined>`), links it via the existing `linkSlackThread` (src/tasks/task.ts:926) and flushes metadata. The consequence is that the task's first user-facing message IS the thread root, which preserves the documented no-preamble rule: firing itself still posts nothing. Every later message goes to `default_channel`, i.e. into that same thread, and a human reply there resolves to this task through `findTaskByThread`, so the run continues instead of restarting.

WHY THE FIRST POST AND NOT AN EAGER OPEN. The rejected alternative is for `fireTrigger` to post an opening message itself and link the returned ts. That is simpler but it reintroduces the preamble the feature deliberately removed — the channel would see an 'I was triggered' line before any result — and it spends a Slack write on a fire whose task may conclude it has nothing to say. Deferring to the first post costs one new branch in `postToUser` and nothing else.

WHY A METADATA FIELD AND NOT A TOOL ARGUMENT. Opening a top-level post that becomes a task thread is a capability that was deliberately deleted in 89f81b7 ('Remove the PM's ability to open DMs, open new task-linked threads'). It is reintroduced here in the narrowest possible form: no tool takes a destination, no model input names the channel, and the only writer of `home_channel` is `fireTrigger` reading the binding of a human-approved trigger. An agent can therefore open exactly one thread, in exactly the channel a human approved, and nowhere else.

MESSAGE FIRES. `FireContext` stops carrying `text`/`threadId`/`channelId` and carries the fetched `SlackThread` instead, which the dispatch call site already holds (src/connectors/slack/events.ts:823 passes `thread.channel.name` from it). `fireTrigger` then calls `task.append(thread)` — the same ingestion path every other Slack task uses. That one call does all of: writes the message to knowledge.log through the single renderer with the author line and the `msg:<ts>` id, applies the redaction policy via `shouldRedact` and skips file downloads for a redacted message, downloads files otherwise so the `[Attachments: …]` suffix carries local paths, links `slack:<channel>:<threadId>` as a channel and promotes it to `default_channel`. `linkSlackThread` in the message branch is therefore replaced by `append`, not supplemented by it — `append` links the same key with the same shape, and doing both would write the entry twice. A message fire consequently needs no `home_channel`: its thread exists before the PM wakes, so both questions the field answers are already answered, and leaving it unset keeps the field's meaning precise rather than decorative.

MATCHING IS ALREADY CORRECT ON THIS BASE. AC5 is satisfied by the base branch, not by this change: `dispatchChannelMessageTriggers` renders once via `rawMessageBody` (src/connectors/slack/events.ts:863) and tests `contains` against that rendered body (:868), so a report whose content lives only in Slack attachment cards — the #sweatcoin-mobile expired-flags report is the worked example — now matches. This change adds no matching logic; it verifies the behaviour and inherits the base's coverage at src/connectors/slack/__tests__/trigger-dispatch.test.ts:171.

STANDING CONTEXT FROM TURN ONE. `buildChannelCanvasPromptSection` (src/connectors/slack/channel-canvas.ts:253) and `buildChannelPinsPromptSection` (src/connectors/slack/channel-pins.ts:307) both derive the channels they cover by walking `metadata.channels` for slack entries. A schedule-fired task has none until its first post, so without a change its first agent — the one that does the work — would spawn with no canvas brief and no pin index, and would get them only on a later wake. Both builders therefore also read `metadata.home_channel`. The duplicated label-map derivation moves into one exported helper in src/connectors/slack/channel-ids.ts so the two builders cannot drift on which channels they consider. Separately, the stores those builders read are only refreshed by inbound Slack events (src/connectors/slack/events.ts:702), and a schedule fire is not one — so `fireTrigger` refreshes them for the bound channel before it wakes the task, with the same pair of calls the event path uses. Both are TTL-bounded and documented as never throwing; the call is still wrapped so that a scan failure cannot lose a fire.

THE POSTING BOUNDARY. One new refusal in `post_to_channel` (src/agents/tools.ts:1046): while the task has a `home_channel` and no `default_channel`, the tool refuses and says to post the result to the user first. That is the sequencing rule — a fired task cannot speak anywhere before it has a home — and it is scoped to exactly the tasks that have a home_channel and no thread, so no non-trigger task changes behaviour. Once the thread is open the tool is untouched in every respect, including posting into the task's own channel: the mandate gate, the mute checks, the standing-brief preflight and the detached semantics all stay as they are. The rejected alternative was to refuse `post_to_channel` whenever the target is the task's own channel; it was dropped because it changes behaviour for ordinary Slack tasks, which is outside this change.

SEED TEXT. `AGENT_PROMPTS.triggered` (src/agents/prompts.ts:47) currently ends 'Nobody is waiting in a thread here — post the result to the bound channel when you are done', which contradicts both new paths: a message fire does have a thread, and a schedule fire must not post to a channel out-of-band. The tail keeps only what it was really carrying — that nobody is waiting on the other end, so nothing arrives unless the task posts it — and the per-mode delivery sentence built in `fireTrigger` says the rest: for a message fire, that the reply goes in the default channel and the triggering message is in knowledge.log; for a schedule fire, that the first `post_to_user` opens this task's own thread in the named channel and every later message lands in it.

ERROR AND RECOVERY PATHS. A failing home-channel post (bot not in channel, channel archived) propagates out of `postToUser` exactly as a normal post failure does; the `post_to_user` tool already catches it and returns `formatSlackSendError` (src/agents/tools.ts:433-444), nothing is linked, and a retry can still open the thread. Slack dry-run mode returns no `ts` (src/connectors/slack/client.ts:194-197), so the open path logs a warning, records the outgoing message and links nothing rather than fabricating a key. Because the linked thread is the record that routes every future reply, the open path flushes with `save(true)` rather than `debouncedSave()`, so a crash immediately after the post cannot orphan the thread it just created. On restart the reloaded metadata already carries both the linked channel and `default_channel`, so a recovered task posts into the same thread; `home_channel` stays on the task and is harmless once a default exists, since the open branch is reached only when there is none. If the task somehow holds a linked thread in the home channel while `default_channel` is unset, the open path reuses that thread instead of opening a second root — one connected thread per channel, which today is only prompt guidance (skills/thread-conduct/SKILL.md) and nothing enforced.

WHAT IS DELIBERATELY NOT DONE. DM (`user`) bindings stay untouched: `propose_trigger` accepts channel bindings only (src/agents/tools.ts:2381), so no DM-bound trigger can exist to deliver to, and the schedule branch's existing user-binding sentence is left exactly as it is. Bursts are not coalesced and fires are not deduplicated: N matching top-level messages produce N tasks, each holding its own message, which is the existing 'each fire is an independent new task; no reuse' decision (docs/plans/v31-triggers.md:160) and needs no timer or dedup state. No manual-fire or debug hook is added. `postFilesToUser` still cannot open a thread — it needs a linked channel, and its existing warning stands.

CORRECTIONS FROM THE BLIND AUDIT AND THE DEPENDENTS SEARCH. Four facts refuted or widened the first draft, and each is handled in a task rather than argued away.

(1) THE AGENT COULD NOT HAVE REACHED THE NEW BRANCH. `post_to_user` refuses before it ever calls `Task.postToUser` whenever the task has no linked channel and no explicit target (src/agents/tools.ts:424: `Object.keys(task.metadata.channels).length === 0`), `report_completion` carries the same refusal for a message (src/agents/tools.ts:803), and spawn tells the PM outright 'Channel(s): none — there is nowhere to reply in this task; finish with report_completion() (no message).' (src/agents/spawn.ts:349). A schedule-fired task has exactly that shape, so the first draft would have shipped an open-and-link branch no agent could ever trigger, with the prompt actively telling it not to try. All three surfaces are corrected in T05: the two tool guards treat a `home_channel` as somewhere to post, and the spawn line says the task has its own thread to open in that channel.

(2) SYSTEM NOTICES MUST NOT OPEN THE THREAD. Two internal callers post with no target and no agent name — the inter-agent budget warning (src/tasks/task.ts:1139) and the wall-clock pause message (src/tasks/task.ts:1685) — and under the first draft either would have opened the task's thread with an operational notice as its root, which is the preamble the no-preamble rule exists to prevent. Both reach `postToUser` without an `agentName`, so `sender` is the literal 'system'. The open path is therefore gated on `sender !== 'system'`: only an agent's own message may open a task's thread, and a system notice with nowhere to go keeps today's warn-and-drop behaviour. That is a one-line, greppable rule rather than a new option threaded through the signature.

(3) THE FETCHED THREAD IS NOT GUARANTEED TO CARRY THE TRIGGERING MESSAGE. `Task.append` writes no knowledge-log entry when `thread.messages` is empty — a fact-check corrected the first draft here, which had claimed it writes nothing at all: the per-message loop simply does not execute, while the channel link, the `default_channel` promotion and the `last_processed_ts` watermark are all still written (src/tasks/task.ts:366-380). So the thread is always owned; only the message body can go missing, and the floor below therefore writes the entry and nothing else, `fetchSlackThread` drops any raw message with neither a `user` nor a `botId` (src/connectors/slack/client.ts:2217), and the dispatch path renders from the raw event precisely because that class exists (src/connectors/slack/events.ts:805). An app post carrying `bot_id` — the #sweatcoin-mobile expired-flags report — is kept and ingests with a synthesized author (src/connectors/slack/client.ts:1440), so the primary path covers the real case. But a payload with neither identity still reaches dispatch under the inverted subtype denylist, and for it `append` alone would write nothing at all, silently reproducing the bug this change exists to fix. So the message fire carries the rendered body and the triggering ts alongside the thread, and after `append` it checks whether a message with that ts was actually written; when none was, it writes the rendered body itself through `appendSlackMessage` attributed to `unknown`. `append` stays the primary path and keeps its redaction, its file downloads and its author resolution; the fallback is a floor, not a second renderer — it reuses the body dispatch already rendered and adds no rendering logic.

(4) TWO EXISTING SUITES PIN THE OLD FIRECONTEXT SHAPE. src/connectors/slack/__tests__/trigger-dispatch.test.ts:186 asserts `toMatchObject({ kind, text, threadId, channelId })` and src/connectors/slack/__tests__/single-render-path.test.ts:245 and :262 assert `.text` and the same three fields. Both are updated in T03, and single-render-path.test.ts — which the first draft left out of the test command entirely — is now in it.

DEPENDENTS THAT ARE GENUINELY UNAFFECTED, AND WHY. Metadata gains an optional field, and nothing enumerates, validates or filters metadata keys: `save`/`debouncedSave` stringify the whole object (src/tasks/task.ts:1101, :1702) and `loadMetadata` is a bare `JSON.parse` (src/tasks/persistence.ts:214), so `home_channel` round-trips a restart untouched and every existing fixture stays valid. The API projections pick fields explicitly (src/connectors/api/routes.ts:102) or return metadata verbatim (:153), so neither breaks. `findTaskByBranch`'s substring needle is the only scanner whose value space a new string could collide with, and it verifies structurally before returning (src/tasks/persistence.ts:657). No suite mocks channel-ids.ts, so its new export widens no factory. tool-contract.test.ts asserts the comms server's exact 13 tool names (src/agents/__tests__/tool-contract.test.ts:118) and this change adds no tool. `postToUser` returning a key for the first time is safe at every call site: `post_to_user` already renders it (src/agents/tools.ts:440), and `report_completion` (:810), `mute_channel` (:894) and the two internal callers discard it — and the internal pair can no longer reach the open path at all under correction (2). explore-tools.test.ts:94 pins `postToUser` to a mocked null and is unaffected because it never sets a `home_channel`. Two `metadata.channels` walkers gate `fetch_slack_reference`'s allowlists (src/connectors/slack/channel-canvas.ts:358, src/connectors/slack/channel-pins.ts:398), and a third gates explore reads (src/agents/tools.ts:78). The first draft left all three alone, reasoning that a home-channel canvas's file references stay unfetchable for the one turn until the thread opens. Review refuted that as incoherent rather than merely incomplete: the injected pin block NAMES a file id and tells the PM to open it with `fetch_slack_reference`, and the canvas block's content is already in the prompt — so the task's own first-turn instructions pointed at tools that refused, and a task homed in a private channel was handed that channel's pin index while being refused permission to read the channel the index describes. All three now derive from one `taskSlackChannelIds` helper alongside the label map, so prompt and capability cover the same channels. This grants no information class the prompt did not already carry: the file ids come from the very canvas and pins already injected, and the home channel is named by a human-approved trigger binding rather than by any model input. render-path-structure.test.ts sweeps every non-test file for `.ownText` reads outside the two sanctioned modules, inline `redacted: false` literals and the string '?? { text:' (src/connectors/slack/__tests__/render-path-structure.test.ts:108), so no task may read `.ownText` or hardcode redaction — the floor in T03 passes an already-rendered string and does neither.

DOCS THE SHIP STAGE MUST RECONCILE (no code task touches them): docs/architecture/persistence.md:94 reproduces the `TaskMetadata` interface as a code block and is already stale on this base — it still shows the old `repositories` shape and omits `briefed_channels`, `triggered_by`, `pending_trigger_id`, `max_mode` and more — so the docs stage adds `home_channel` there rather than pretending the block is current; docs/architecture/triggers.md:75 says a schedule fire leaves the PM to open the destination itself, :78 states the no-preamble rule that still holds, and the key-files table at :176 credits `linkSlackThread` for a call this change removes; docs/architecture/slack-integration.md:194 enumerates `postToUser` as exactly two routing modes; docs/architecture/agents.md:57 says the PM cannot open new task-linked threads; skills/triggers/SKILL.md:53 restates the no-preamble rule and stays true. `Task.postToUser`'s own doc comment (src/tasks/task.ts:445) asserts both 'Opening new DMs/threads is intentionally not supported' and 'Always returns null', and `linkSlackThread`'s (:920) names `fireTrigger` as its consumer — those two are code comments inside files T01 and T03 already own, so they are corrected there rather than at ship.

WHAT REVIEW CHANGED, AFTER THE CODE LANDED. Four defects were found by the blind reviewers and fixed by the driver; each is worth recording because three of them were invisible from the plan alone. (i) A reviewer found that the standing-context refresh calls `ensureChannelCanvas`, which announces canvas adoption as a NEW TOP-LEVEL message, and ruled that a notice landing ahead of the fire's own result contradicts `firing posts no preamble`. That was built as suppression — an `announce` option, a `pendingAnnouncements` queue on the channel store, and a flush ahead of the TTL — and then **reverted in full during live QA**, on the operator's judgement, which was right. A canvas adoption notice is not the fire announcing itself: it reports a real change to what Archie reads in that channel, it explains why the fire's output reads the way it does, and it carries no task footer so it cannot be mistaken for the result. The second claimed harm — a human replying to a bot-rooted notice spawns a stranger task — is true of every canvas announcement on every path and is not made worse by the fire. Promoting the finding without first asking whether a canvas notice *is* a preamble was the error; the suppression cost a new option, a persisted store field, and two defects of its own (a notice that could sit queued indefinitely in a quiet channel, and a re-adoption going silent across a suppressed scan). Reverting removed 159 lines and both defects. The refresh itself stays, and is what puts the channel's brief in a fired task's first turn. (ii) The capability unification above. (iii) The ingestion floor was wider than the hole it documents: `fetchSlackThread` also drops a bot post from another workspace, and the dispatch-side gate that should catch those first reads different fields, so a payload with no team at all could pass dispatch, be dropped by the fetch, and have its body written to `knowledge.log` past the one policy every other write goes through. The floor now fires only when the payload carried NO identity — no user id and no bot id, the single reason a drop happens that redaction has nothing to say about — and refuses an empty body or a missing `ts`. The entry is attributed to `unknown`, which is the condition rather than a fallback: the branch runs precisely because no author id was derived. (iv) Opening the home thread had no mutual exclusion, so two `post_to_user` calls in one agent turn would each root a top-level message and the channel would show two competing roots for one task. The open is now serialized by a keyed lock at module scope, keyed by task id — so it holds across separate `Task` instances built from disk for the same task, and the open body's own "is there already a thread here" check is what makes the second caller post inside the first survivor's thread. An instance-scoped promise guard was tried first and leaked with three or more concurrent callers when the opener failed: every waiter had already passed the in-flight check, so each fell through and rooted its own message. Reproduced with three callers before replacing it.

### T01 — home_channel on TaskMetadata, and the postToUser open-and-link branch

In src/types/task.ts, add to `TaskMetadata` (near `default_channel` at :284) an optional field `home_channel?: { channel_id: string; channel_name: string }` with a doc comment stating: the Slack channel a trigger-fired task is homed in, written only by `fireTrigger` from an approved trigger's binding; it answers where the task opens its own thread and whose standing context applies before one exists; it is never set from a model input.

THE SENDER GATE. The replaced block reads: `if (!defaultCh) { if (this.metadata.home_channel && sender !== 'system') return this.openHomeThread(message, sender, footer); <the existing warn + return null, unchanged> }`. The `sender !== 'system'` conjunct is load-bearing: two internal callers post with no `agentName` and therefore with `sender === 'system'` — the inter-agent budget warning (src/tasks/task.ts:1139) and the wall-clock pause message (src/tasks/task.ts:1685) — and an operational notice as the thread root is exactly the preamble this feature forbids. Only an agent's own message may open a task's thread. Do not change either call site.

Add the private method `openHomeThread(message: string, sender: string, footer: string): Promise<string | null>` immediately after `postToUser`, doing exactly this in order:
1. `const home = this.metadata.home_channel!;`
2. Reuse check: scan `Object.entries(this.metadata.channels)` for the first entry whose value has `type === 'slack'` and `channel_id === home.channel_id`. If found, set `this.metadata.default_channel = key`, `await postSlackMessage({ channel: ch.channel_id, threadTs: ch.thread_id, text: message, footer })`, `this.logOutgoingMessage(sender, message, Task.formatSlackDest(ch).display, ch, footer)`, `await this.save(true)`, and return that key. (This is the one-thread-per-channel rule: never open a second root in a channel this task already has a thread in.)
3. Otherwise `const ts = await postSlackMessage({ channel: home.channel_id, text: message, footer })` — NO `threadTs`, so it is a top-level post. Let a thrown error propagate untouched; do not catch it.
4. If `ts` is falsy (dry-run): `logger.warn('task', ...)` naming the task id and the channel and saying nothing was linked, then `this.logOutgoingMessage(sender, message, formatSlackChannelDisplay(home.channel_name), undefined, footer)` and return null. Do not link, do not save.
5. Otherwise `const key = this.linkSlackThread(home.channel_id, ts, home.channel_name);` then read the linked channel back out of `this.metadata.channels[key]` and call `this.logOutgoingMessage(sender, message, Task.formatSlackDest(ch).display, ch, footer)`, then `await this.save(true)` (flushed, not debounced — this record is what routes every future reply), then return `key`.

`linkSlackThread` already promotes `default_channel` with `??=` and calls `debouncedSave`; the `save(true)` above is what makes it durable. Do not change `linkSlackThread`, `append`, `postFilesToUser`, or any other method. Do not add a `PostTarget` field. Do not touch `src/system/trigger-scheduler.ts` in this task — nothing writes `home_channel` yet, so the branch is dormant and the tree stays green.

## Open at plan time

What the checks could not close. These travelled to implementation as watch-outs and to the pull request as unresolved items.

- A trigger-fired task that has not opened its thread yet cannot show an approval card: `postInteractiveToUser` resolves its destination from linked channels only and has no `home_channel` branch, so a fired task that requests edit mode before its first post gets an SSE event and a log line and no Slack buttons. Documented in triggers.md as a known edge; the seed still tells the agent to request edit mode first.
- A failed first home-channel post leaves the task mute rather than merely un-threaded: `default_channel` stays null, so `post_to_channel` keeps refusing and `post_to_user` keeps throwing until a retry succeeds. `isChannelReachable` passes a public channel the bot is not a member of, so the pre-flight does not catch that case.
- post_files_to_user still cannot open a task's thread: it needs a linked channel, and Slack's file upload carries no text to serve as a thread root. The PM's channel-context line and the delivery seed both say to post to the user first.
- `post_to_user` reports 'New channel linked: <key>' on the reuse path too, where the channel was already linked and nothing new was saved. Cosmetic; the key it names is correct.
- A user-bound (DM) trigger fire remains undeliverable end to end: propose_trigger cannot create one, so nothing can reach that arm. Out of scope by operator decision.
- sendSharedChannelWarnings is not called on the trigger path, so a message-fire task in a Slack Connect channel never gets the shared-channel note in its system prompt even though it now ingests that thread. Pre-existing; ingestion itself still redacts via shouldRedact.
- A Slack post that succeeds while the flushed metadata write fails is reported to the agent as a send failure even though the message is live, which invites a duplicate repost.
- prompts/pm-agent.md was deliberately left unchanged: it is always-present prompt text, and the threadless shape reaches the agent at runtime through the delivery seed, the spawn channel line and the post_to_channel refusal. The thread-conduct skill, which the PM loads before posting outside its thread, does cover it.
- Verified live against a real Slack workspace on 2026-08-19: a scheduled fire opened its own thread with the result as the root (no preamble), a human reply routed back into that same task rather than spawning a new one, a message fire's task echoed the full triggering sentence out of its knowledge log, and a fired task obeyed its home channel's canvas brief on its first turn while holding no linked channel. The sequencing gate (post_to_channel refused before a channel is open) was not exercised live and rests on its unit tests.
