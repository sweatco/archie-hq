# Personal connections

**Date:** 2026-10-23 · **Status: Planned (in progress).**

## Brief

A person connects their own account to one of Archie's OAuth MCP servers from their 1:1 Slack DM: `connect <server>` replies with an authorize link, the OAuth callback stores an encrypted record bound to their Slack id and confirms in the DM, `connections` lists their records and `disconnect <server>` removes one. Records refresh with the standard refresh-token grant under a per-(user, server) lock, and Task.getDmOwner() names the internal person a DM task belongs to. Nothing in a task uses a personal record yet; personal MCP sibling instances and Slack-as-user build on this. Groundwork reviewed out of #173 (Igor Sova).

## Acceptance criteria

| id | criterion | method |
|---|---|---|
| AC1 | Store: put/get/list/delete of a person's OAuth record, file mode 0600, secrets only inside the AES-256-GCM envelope, unsafe ids rejected before disk; the startup key check also fires when any personal record exists, so a missing key fails at boot. | unit |
| AC2 | Refresh: the personal fresh-token call returns the stored token untouched while more than 60 s remain; otherwise it runs one standard refresh-token grant with the record's own client under a per-(user, server) lock, so concurrent callers refresh once; the result is persisted and a non-rotated refresh token is kept; on failure the stored record is untouched and it throws. | unit |

## Design

A person connects their own account to one of Archie's OAuth MCP servers from their 1:1 Slack DM. The engine, never the PM, handles three DM commands: `connect <server>`, `disconnect <server>` and `connections`. `connect` runs main's existing MCP OAuth connect (discovery, DCR, PKCE) with the person attached and replies with the authorize link; the existing public `GET /oauth/callback` exchanges the code and, because the pending carries the person, stores the record under their Slack user id instead of as the shared record, then confirms in the DM. A per-person fresh-token call refreshes these records with main's existing refresh code. `Task.getDmOwner()` names the person a DM task belongs to. No task uses a personal record yet: personal MCP sibling instances and Slack-as-user (Slack's hosted MCP, which uses the same standard OAuth) are the later consumers. Credit: the per-person record layout and refresh under a per-key lock come from Igor Sova's #173; the rich-text command parsing comes from the Claude extension branch's dm-commands.ts.

**Records reuse main's shared OAuth shape.** A personal record is exactly a shared record (`OAuthRecordMeta` + sealed `OAuthSealed`: access token, refresh token, client id and secret, token type; plaintext issuer, token endpoint, scopes, resource, expiry) plus `slack_user_id`. The DCR client is sealed inside each person's record, as the shared record bundles its own, so there is no shared client file and nothing to keep consistent between a client and a grant. New types in src/system/oauth/types.ts: `OAuthPersonalRecordMeta extends OAuthRecordMeta { slack_user_id: string }` and `OAuthPersonalRecord extends OAuthPersonalRecordMeta { envelope: EncryptedEnvelope }`. Location: `${SECRETS_DIR}/oauth/personal/<slackUserId>/<server>.json` — a new `OAUTH_PERSONAL_DIR = join(OAUTH_DIR, 'personal')` in src/system/workdir.ts, created 0700 by `bootstrapWorkdir` next to `OAUTH_PENDING_DIR`; it is already covered by the `secrets/oauth/` .gitignore line, and `listOAuthServers` and the startup scan only look at `*.json` entries of OAUTH_DIR, so a subdirectory changes neither. New functions in src/system/oauth/storage.ts, next to the shared ones and built from the same vault primitives (`encryptJson`, `decryptJson`, `writeJsonAtomic(…, 0o600)`, `readJson`, `deleteFileIfExists`): `personalPathFor(slackUserId, serverName)` (the existing `assertSafeServerName` for the server plus a new Slack-id check `/^[UW][A-Z0-9]{2,30}$/` for the directory segment, both before any path is built), `writePersonalRecord(meta, sealed)`, `readPersonalRecord(slackUserId, serverName)`, `listPersonalRecords(slackUserId)` (plaintext meta only, envelope stripped, sorted by server_name; ENOENT gives []), `deletePersonalRecord(slackUserId, serverName)`. The startup check in src/index.ts becomes `const hasVaultRecords = readdirSync(OAUTH_DIR).some(…) || readdirSync(OAUTH_PERSONAL_DIR, { recursive: true }).some((name) => String(name).endsWith('.json'));` — recursive and by file name, because `disconnect` only unlinks the file and leaves the person's emptied directory behind; a missing or wrong key then fails at boot rather than at the first callback or spawn. bootstrapWorkdir runs before it and creates the directory, so readdirSync never sees ENOENT.

**Refresh reuses main's code.** The body of `ensureFreshToken` in src/system/oauth/refresh.ts (leeway check, decrypt, refresh-token grant with the record's own client and RFC 8707 resource, write back, keep a non-rotated refresh token) moves unchanged into a private `freshTokenFor(record, write, options)` that takes the record and a write function. `ensureFreshToken(serverName, options)` keeps its exact signature and behaviour (lock `oauth:<server>`, `OAuthRecordMissingError` when absent) and calls it with `writeOAuthRecord`. A new `ensureFreshPersonalToken(slackUserId, serverName, options)` takes the lock `oauth:personal:<user>:<server>`, returns null when no record exists, and otherwise calls `freshTokenFor` with `writePersonalRecord`. Because the read, the refresh and the write all happen inside the lock, a second concurrent caller sees the already-refreshed expiry and does not spend a rotating refresh token again; a refresh error throws `OAuthRefreshError` before anything is written. As on the shared path, when a provider omits `expires_in` the old expiry is kept, so a later caller would refresh again; that is main's existing behaviour and is not changed here. `writePersonalRecord` and `deletePersonalRecord` are plain atomic file operations, not locked, as the shared ones are.

**Connect: beginConnect with a person.** src/system/oauth/connect.ts: `ConnectInput` gains `person?: { slackUserId: string; channelId: string; threadTs?: string }`; when present, `beginConnect` adds `slack_user_id`, `dm_channel_id` and (when defined) `thread_ts` to the pending record's plaintext meta; nothing else changes, and the CLI never passes it. `OAuthPendingMeta` gains those three optional fields. A new `publicRedirectUri()` export returns `<ARCHIE_PUBLIC_URL without trailing slashes>/oauth/callback` exactly as src/cli/oauth.ts computes it inline, and throws a plain Error naming ARCHIE_PUBLIC_URL when it is unset; the CLI keeps its own inline version and is not touched. The pending's sealed half still holds only the PKCE verifier and client credentials; no token is ever written into a pending record, and the existing 1 h reaper removes abandoned ones.

**Callback.** src/connectors/oauth/routes.ts `completeFlow`, after the successful token exchange: when `pending.slack_user_id && pending.dm_channel_id`, it writes the same meta and sealed values the shared branch writes, plus `slack_user_id`, with `writePersonalRecord` instead of `writeOAuthRecord`; deletes the pending; logs with the unified logger; posts ``Connected `<server>` with your account. Say `disconnect <server>` to remove it.`` to `dm_channel_id` (thread `thread_ts`) with `postSlackMessage`, where a Slack failure is logged at warn and does not fail the callback because the record is already stored; and renders the success page saying the server is connected to their account. Without those fields the shared branch runs unchanged. Every failure path before the exchange and the exchange failure itself (markPendingError, failure page, nothing stored) is today's code, shared by both.

**Slash command (replaces the first cut's DM-text commands, per the operator).** New src/connectors/slack/connect-command.ts registers one Bolt command handler, `registerConnectCommand(boltApp)`, called from `mountSlackApp` in src/connectors/slack/events.ts next to `registerMergeActionHandlers`/`registerToolApprovalHandlers`/`registerMemoryPreferenceHandlers`. The command name is `ARCHIE_SLASH_COMMAND` (trimmed) or `/archie`, read at registration, because slash command names are unique per workspace and the test app needs its own (`/archie-test`). Bolt's ExpressReceiver serves events, interactivity and slash commands on the same `/webhooks/slack` endpoint, and Socket Mode delivers commands over the socket, so nothing else is wired. The handler calls `ack()` first (Slack's 3 s limit; discovery and DCR take longer) and then answers with `respond({ response_type: 'ephemeral', text })` through the command's response_url, so every reply, the authorize link included, is visible only to the caller and never lands in history; a failed respond is logged at warn. The reply text comes from `connectCommandReply({ user_id, channel_id, text })`, in this order: (1) DM only — unless `channel_id` starts with 'D' and `getChannelInfo(channel_id)` reports `isIm` with `imUserId === user_id` (the app's own IM with the caller; a DM between two people is not visible to the bot, so getChannelInfo reports isIm false there), the reply is `Use this in your DM with Archie.` and nothing else happens; (2) identity — `isInternalMemoryUser(await getUserInfo(user_id))`, failing closed: a lookup error replies that the account could not be confirmed, and a non-internal person is told only members of this workspace can connect their own accounts; (3) parse the trimmed, lower-cased text as `connections` or `/^(connect|disconnect)\s+(\S+)$/`, otherwise reply with the usage line; (4) `connect` calls `beginConnect({ serverName, redirectUri: publicRedirectUri(), person: { slackUserId: user_id, channelId: channel_id } })` and replies with the authorize URL as a CommonMark link, `disconnect` calls `deletePersonalRecord`, `connections` lists `listPersonalRecords`; any error replies `That didn't work: <message>`. The OAuth callback still confirms in the DM (`dm_channel_id` = the command's channel). The first cut's `handleSlackEvent` hook and src/connectors/slack/dm-commands.ts are removed, with their tests (src/connectors/slack/__tests__/dm-commands.test.ts and the 'engine DM commands' block in src/connectors/slack/__tests__/trigger-dispatch.test.ts). src/connectors/slack/__tests__/render-path-structure.test.ts scans every source file, so connect-command.ts must not read `.ownText`, write `redacted: false`, or contain the sequence `?? { text:`. slack-manifest.yaml declares the command under `features.slash_commands` with the same request URL as events and interactivity, and adds the `commands` bot scope that slash commands require; .env.example documents ARCHIE_SLASH_COMMAND.

**DM owner.** src/tasks/task.ts `async getDmOwner(): Promise<string | null>`: the Slack user id when `metadata.memory_destination.channel_id` starts with 'D', `getChannelInfo` reports `isIm` with an `imUserId`, and `isInternalMemoryUser(await getUserInfo(imUserId))`; otherwise null, including when getUserInfo throws (getChannelInfo already swallows its own errors and reports isIm false). memory_destination is set once — from the first Slack thread a task appends, or from a trigger's binding or thread — and setMemoryDestination refuses a different channel afterwards, so it names the single owner. Open PR #355's `dmPartnerOf` computes the same fact; whichever lands second reuses the other.

**Rejected.** #173's shape (a separate users/ tree with its own record types, a shared client file bound by issuer/resource/redirect, a durable wake outbox that kept live tokens in pending records past the reaper, a PM tool escalating after a 401): the operator wants connect-up-front with no fail-first. A per-kind finisher registry: one standard OAuth finisher serves every known consumer, Slack's hosted MCP included. A parallel personal-grants module with its own types and refresh: it would duplicate storage.ts and refresh.ts. Case and punctuation variants of the commands: lower-case and trim only. Provider-side revocation on disconnect: local deletion, as `oauth:revoke` does.

**Dependents checked.** `ensureFreshToken` keeps its signature and behaviour for its callers src/system/oauth/inject.ts (spawn-time binding, reached from src/agents/spawn.ts) and src/cli/oauth.ts (`oauth:refresh --force`), and src/system/oauth/__tests__/refresh.test.ts and src/system/oauth/__tests__/inject.test.ts must pass unchanged. src/cli/oauth.ts also calls `beginConnect` without a person and polls pending records (`error`, `completed_at`), both unaffected by optional fields. tools/e2e/prepare-worktree.ts copies the whole `secrets/oauth` tree into a worktree, so a worktree boot starts with main's personal records too (none exist in dev today). Tests that import events.ts — src/connectors/slack/__tests__/subtype-sweep.test.ts, src/connectors/slack/__tests__/mpim-external-author.test.ts, src/connectors/slack/__tests__/trigger-dispatch.test.ts, src/connectors/slack/__tests__/trigger-card-resolution.test.ts, src/connectors/slack/__tests__/single-render-path.test.ts and src/connectors/__tests__/merge-approval-surfaces.test.ts — mock `../client.js` and `workdir.js` partially and some drive `mountSlackApp` with a fake Bolt app; they stay green because storage.ts, connect.ts and connect-command.ts read workdir paths only inside functions, and the fake Bolt apps must accept a `command` registration (the fake in trigger-dispatch.test.ts and any other `mountSlackApp` fake gets a no-op `command` method if it lacks one). Tests whose client.js factory lacks `getUserInfo` while loading task.ts — src/agents/__tests__/tool-contract.test.ts, src/memory/__tests__/tools.test.ts, src/tasks/__tests__/persistence.test.ts and src/tasks/__tests__/usage-persistence.test.ts — never call getDmOwner, so the new import is never read. The docs describing these flows (docs/architecture/secrets.md, docs/architecture/slack-integration.md, docs/architecture/orchestration.md, docs/architecture/triggers.md) are updated in the ship stage, not by a task.

**Risks.** Whoever opens the authorize link completes the grant under the DM owner's Slack id, because the callback binds only through `state`; a forwarded link would bind someone else's provider account to the DM owner. The link is single-use, expires in an hour and is posted only in their own DM; this is inherent to link-based OAuth and accepted.

**Trade-offs.** One DCR client per person per connect at the provider (harmless at ~100 people). A server without DCR replies with the existing CLI-worded error (static clients come with Slack-as-user). Tests mock Slack entirely; the live check is the operator's DM through Hookdeck with ARCHIE_PUBLIC_URL set to the local instance in the worktree .env only.
