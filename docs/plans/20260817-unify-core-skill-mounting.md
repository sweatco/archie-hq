## Design

PROBLEM. Which agents receive one of archie-hq's own core skills is decided today by which directory a file sits in. The interface is `AgentDef` (src/types/agent.ts:149 - note it is NOT called `AgentDefinition` anywhere in the repo) and it carries two skill-path fields: `skillsPath` (src/types/agent.ts:215), a plugin's own skills/ directory, set on repo agents (src/agents/registry.ts:91) and plugin agents (:113); and `coreSkillsPath` (src/types/agent.ts:218), archie-hq's built-in skills/ directory via `CORE_SKILLS_DIR` (src/agents/registry.ts:24), set on exactly one def, the PM (:416). So a core skill's audience is implicit in its location, and a second audience would mean a second directory.

APPROACH. Replace the two fields with ONE ordered list of already-resolved absolute skill directories, `skillPaths?: string[]`, built by one central manifest module, src/agents/core-skills.ts, that declares which core skills each agent track mounts. Plugin skills keep expanding from the plugin's own directory and their entries stay FIRST, so plugin-shadows-core is unchanged. `setupAgentWorkspace` (src/agents/spawn.ts:113) becomes a plain symlinker over that list. The manifest encodes today's mapping exactly - all four core skills on the `pm` track, nothing on the others - so nothing changes behaviorally. A boot warning in src/index.ts names any core skill no track mounts.

THE MANIFEST MODULE (src/agents/core-skills.ts). It owns `CORE_SKILLS_DIR`, moved from src/agents/registry.ts:24. The `join(__dirname, '..', '..', 'skills')` expression is reused verbatim and is correct because the new module sits at the same directory depth (src/agents/, compiling to dist/agents/), so it resolves to <root>/skills from both source and build layouts. It exports: `AgentTrack = 'pm' | 'repo' | 'plain'`; `CORE_SKILL_MOUNTS: Record<AgentTrack, string[]>`; `resolveSkillPaths(track, pluginSkillsPath?)`; and `findUnmountedCoreSkills()`. `CORE_SKILLS_DIR` itself is NOT exported, which is what AC6's grep decides.

WHY 'track' IS DERIVED, NOT STORED. There is no `track` field in src/ today; the only classification is `isRepoAgent(def)` = `def.repo != null` (src/types/agent.ts:257) and `isPmAgent(def)` = `def.isPm === true` (:262), with a plain plugin agent as the negation of both. Rather than add a stored field a construction site could set wrongly, each site passes the track literal it already branches on: `scanAgentDefs` already forks on `if (agent.repo)` (src/agents/registry.ts:66), so the repo arm passes 'repo' and the plugin arm 'plain'; `buildPmDef` passes 'pm'; `synthesizeDynamicAgentDef` passes 'repo' because a dynamic agent always sets `repo` (src/agents/registry.ts:245) and its own comment (:235) calls it a repo agent. Dynamic agents therefore mount the repo track, empty today - identical to their current behavior of mounting nothing, which is what docs/architecture/agents.md:143 asserts and which stays true only while that track is empty.

RESOLUTION ORDER AND SHADOWING. `resolveSkillPaths` returns plugin entries first, then the track's core skills, deduplicated by directory basename with the first occurrence winning. Plugin expansion replays today's spawn-time classification exactly: `readdirSync(pluginSkillsPath, { withFileTypes: true })`, and an entry counts as a skill if `isDirectory()` OR it is a symlink whose `statSync` target is a directory (a skill can be vendored as a git submodule exposed through a symlink; `Dirent.isDirectory()` is false for those, and a dangling link is skipped because `statSync` throws). This filter is load-bearing rather than defensive: workdir/plugins/pm/skills contains a `.DS_Store` file alongside its 22 real directories, and dropping the filter would change the mount count. The plugin directory is skipped entirely when falsy or absent, matching today's `existsSync` filter at src/agents/spawn.ts:122-124. Core entries are `join(CORE_SKILLS_DIR, name)` included only when the path exists, preserving the `existsSync(CORE_SKILLS_DIR)` guard at src/agents/registry.ts:416 that exists because the prod image only has /app/skills if Dockerfile.prod copied it.

WHY DEDUPLICATE IN THE RESOLVER. Today shadowing is resolved twice, differently: `setupAgentWorkspace` resolves it by `if (!existsSync(target))` on the symlink it is about to create (src/agents/spawn.ts:141), and the boot banner resolves it independently with a `Set<string>` (src/index.ts:142-152). Deduplicating once in the resolver makes the list the authoritative answer to 'what does this agent mount', which is what all three consumers want. The spawn-side `existsSync(target)` guard is KEPT unchanged, because it also protects against a target left by a previous run.

WHY EXPANSION MOVES TO REGISTRY-SCAN TIME, AND WHAT IT COSTS. The list must be uniform for the symlinker to be plain; a list mixing 'a directory to expand' with 'a single skill directory' would not be. So plugin expansion happens in `resolveSkillPaths`, called from `scanAgentDefs`. TRADE-OFF, stated because it is real: `scanAgentDefs` runs not only at boot (src/index.ts:109) but on every `Task.create` and `Task.get` (src/tasks/task.ts:206, :274) and on plugin sync (src/system/plugin-sync.ts:40), and `getPlugins()` returns a cached list, so today that path performs only one `existsSync`. After this change it performs roughly a dozen small `readdirSync` calls plus a few `statSync` calls per scan - one per agent def, over directories of tens of entries. This is accepted as sub-millisecond on a warm local or container filesystem and is not made async, because `scanAgentDefs` is synchronous and making it async would ripple into `Task.get`. It is called out here so a reviewer judges it deliberately rather than discovering it.

SPAWN. The block at src/agents/spawn.ts:120-147 collapses to: read `agent.def.skillPaths ?? []`; if non-empty, for each path compute `target = join(agentSkillsDir, basename(skillPath))` and, when `!existsSync(target)`, `mkdir` the skills dir and `symlink(skillPath, target)`. The lazy `mkdir` inside the loop is preserved so an agent with no skills still gets no .claude/skills directory - which is safe either way, because src/agents/spawn.ts:289 lists that path in `protectedWorkspaceFiles` unconditionally and `denyWrite` membership is tested by path prefix, never by existence (src/agents/sandbox.ts:187-192).

BOOT. The banner's `skills:` line becomes `(pmDef?.skillPaths ?? []).map(basename).sort()`, replacing the re-enumeration at src/index.ts:142-152. CORRECTION TO AN EARLIER CLAIM: this was expected to also fix a skew, because the old banner used a plain `isDirectory()` test and so omitted symlink-vendored skills the mount installed. There is in fact NO symlinked skill anywhere under workdir/plugins today, so the banner output is byte-identical before and after; the improvement is real but latent, and AC8 therefore pins byte-identical output plus a fixture proving a symlink-vendored entry would be included. Then, immediately after the existing 'no externally reachable agents' invariant loop ending at src/index.ts:205, `findUnmountedCoreSkills()` is called and each name produces one `logger.warn('system', ...)` (src/system/logger.ts:288).

TWO LIMITS THE MANIFEST COMMENT MUST STATE RATHER THAN HIDE, so a future audience is not added on a false promise. (1) SANDBOX: mounting a core skill for a new track makes it loadable through `Skill` and `Read`, because the PreToolUse guard resolves the raw tool-input path with `resolve(cwd, rawPath)` and never calls `realpath` (src/agents/sandbox.ts:231), `READ_TOOLS` is only {Read, Glob, Grep} so `Skill` is never seen (src/agents/sandbox.ts:181), and the workspace is in `allowReadPaths` on every track (src/agents/spawn.ts:326, :555). It does NOT make the files readable from `Bash`: bwrap resolves symlinks and /app is hardcoded in `denyRead` (src/agents/sandbox.ts:83). (2) CONTENT: all four core skills are written in the PM's voice and instruct PM-only MCP tools - `post_to_channel`, `mute_channel`, `read_thread`, `fetch_slack_reference`, `propose_trigger` - which are attached only inside the `isPmAgent(def)` branch at src/agents/spawn.ts:412-414; skills/self-awareness/SKILL.md:53 even says of itself that it is a built-in PM skill. So giving one of them a new audience needs prompt and tool work too, not just a manifest line. Neither limit is changed here.

ALTERNATIVES REJECTED. (a) `string[]` of SOURCE directories rather than resolved skill directories: cannot express per-skill core selection, because reading skills/triggers yields SKILL.md, not a skill named triggers. (b) A `{ name, path }[]` list: redundant, since `basename` already gives the name. (c) A stored `track` field on `AgentDef`: more surface area and a second thing to set wrongly, for no gain over the literal each construction site already knows. (d) A JSON manifest file: the repo has no JSON config under src/ and reserves JSON for values that live in the plugins repo and hot-reload (src/system/branding.ts:1-18); core-skill mounting is engine behavior, so the idiom to follow is a hardcoded const in the owning module, as `TRUSTED_PACKAGE_REGISTRY_DOMAINS` does at src/agents/sandbox.ts:48. (e) Adopting the `linkAgentSkills` extraction that exists on an unmerged personal-fork branch: it carries an unrelated rm-then-rebuild bugfix which would make this change no longer behavior-preserving; that bug is filed as a separate issue instead.

OUT OF SCOPE. `LoadedPlugin.skillsPath` (src/system/plugin-loader.ts:179, set at :395) is a different field on a different type and is untouched, including its documentation at docs/architecture/plugin-system.md:137. No new audience is added. The sandbox /app denyRead boundary is unchanged. CHANGELOG.md is not edited.

AMENDMENTS AFTER REVIEW AND QA - what shipped differs from the plan above in six ways, all of them corrections the reviewers found rather than changes of intent.

(1) THE MOUNT LOOP RE-CHECKS ITS SOURCE. The plan's spawn loop trusted the scan-time snapshot and called symlink() directly. That was a regression against the original implementation, which enumerated the plugin directory at spawn time and so could never name a skill that had since been removed. Because symlink(2) does not validate its target and refreshPlugins does a git reset --hard, trusting the snapshot introduced the one code path able to create a DANGLING link - and a dangling link at the mount target wedges that agent permanently, since the target guard is existsSync, which follows the link, reports false, and lets symlink() throw EEXIST out of a path that does not catch it. Shipped code adds an existsSync check on the source inside the loop, restoring what the old enumeration gave implicitly. A reviewer reproduced the pre-fix wedge and confirmed the post-fix loop is a clean no-op.

(2) FIVE EXPORTS, NOT FOUR. mountedSkillNames was added and is the single derivation of the boot banner's name list, called by src/index.ts and by the tests so that the shipped line and the test asserting it cannot drift. The plan had index.ts computing the basename-and-sort inline and adding basename to its path import; shipped index.ts calls the helper and imports only join.

(3) findUnmountedCoreSkills TAKES AN INJECTABLE DIRECTORY. With CORE_SKILLS_DIR module-private and the real tree having nothing unmounted, the only assertable case was the empty one - so the whole function could be replaced by a bare empty return with every test still green, which is precisely the direction that matters for a guard against forgetting the manifest. It now takes a coreSkillsDir parameter defaulting to CORE_SKILLS_DIR; production callers pass nothing, and that mutation now fails two tests.

(4) CORE ENTRIES ARE CLASSIFIED, NOT MERELY EXISTENCE-CHECKED. The plan had core paths admitted by existsSync. A documentation verifier pointed out that this diverged from the original behaviour, which read the core directory and applied the directory-or-symlink-to-directory rule - so a manifest name resolving to a regular file would have been symlinked as a bogus skill. Shipped code routes both plugin and core entries through one rule, isSkillPath.

(5) THE EQUIVALENCE TEST DERIVES ITS COUNTS. The plan pinned the literal 26 / 22 / 4 and asserted 13 defs. Those totals are owned by the separately versioned archie-plugins repo, so pinning them would break the suite whenever that repo gained or lost a PM skill - a failure with no local cause, and with no CI signal either, because that file skips in CI where workdir/ is gitignored. The shipped test derives the core count from the manifest, asserts that the PM's total is exactly its two sources, and pins the invariants that must hold whatever the plugins clone contains. The 22 + 4 = 26 numbers were still measured, three independent ways, and recorded in the QA manifest rather than frozen into an assertion.

(6) AC6 IS TRUE OF PRODUCTION CODE, NOT OF EVERY BYTE IN src/. Both removed field names survive as prose inside comments in the two new test files, and those files recompute the repo's skills/ path for their own assertions. No code outside the manifest module builds a core-skill path or enumerates the core directory, which is the criterion's substance; the literal grep in its original form does not come back empty, and the QA row records that rather than rounding it to a pass.

Two stale citations that had reached shipped comments were also corrected: the workspace's presence in allowReadPaths is at src/agents/spawn.ts:312 and :541, not :326; and the PM-only MCP servers are registered at src/agents/spawn.ts:398-400, inside the isPmAgent branch beginning at :325, not at :412-414, which is inside the isRepoAgent branch. The same comment's tool list named propose_trigger, which appears in no core skill, where report_completion does.

## Superseded after the fact

- The SANDBOX limit stated in the Design section — that mounting a core skill for a new track does **not** make its files readable from `Bash`, because bwrap resolves the symlink and `/app` is in `denyRead` — was true when this plan was written and is no longer. Spawn now grants each agent's mounted core skill directories in `allowReadPaths`, so a skill file is readable on both enforcement layers. Measured before the change, against `/app/skills/triggers/SKILL.md`: unreachable from `Bash` by either route, and reachable to `Read` only through the workspace symlink, which worked because the guard does not resolve it. Loading a skill was never affected and never needed a grant. See `coreSkillPaths` in `src/agents/core-skills.ts` and the Filesystem Isolation section of `docs/architecture/security.md`.
