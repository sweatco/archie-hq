# DM delivered triggers

**Date:** 2026-08-27 · **Status: Implemented; AC12 (live DM run) not yet verified.**

**Rebased 2026-10-12.** Main had since moved the triggers skill to `core-plugin/skills/triggers/SKILL.md` and added `Task.prepareTriggerDelivery`, which only lets a trigger deliver to the task's own conversation. So a DM user can no longer name a different channel, and the review fixes added after this plan was written (the `home_channel` visibility fallback, and refusing `propose_trigger` before a fired task's first post) apply on top of that. Line numbers below are from August.

## Brief

Let a user set up a trigger that delivers to their own Slack DM. Such a trigger can only be created from inside that DM, always targets the person asking, runs on a schedule only, and when it fires the spawned task opens its own thread in that DM.

## Design

PROBLEM. Triggers can already be bound to a user (`TriggerBinding` has a `user` variant, `triggerVisibleFrom` handles it, and `trigger-visibility.test.ts` covers it), but no such trigger can ever be created: `propose_trigger`'s zod schema accepts only `type: 'channel'` (src/agents/tools.ts:2421) and its handler refuses any `D…`/`U…` binding id (src/agents/tools.ts:2439). Two reasons, both recorded. The first was a capability gap — when triggers shipped, the fired PM had no way to deliver to a DM (docs/architecture/triggers.md:10). The second, added in commit ee99eb2c, is the load-bearing one: the binding id is written into `metadata.home_channel` by `fireTrigger`, and `taskSlackChannelIds` includes the home channel in the set of conversations the fired task may READ (src/connectors/slack/channel-ids.ts:61), with the explore tools' DM-prefix guard bypassed for ids in that set (src/agents/tools.ts:1008-1012). So a model-supplied `D…` id would hand a fired task read access to a DM, while the human approving it sees only a channel NAME on the card.

APPROACH. Both objections are answered by never letting the DM binding come from the model. The first is answered by the `home_channel` mechanism that landed in commit 040261cb: a schedule fire is homed in a conversation and its first `post_to_user` opens the task's own thread there. That mechanism is conversation-agnostic — `openHomeThread` posts to `home.channel_id` via `postSlackMessage` with no `threadTs` and then links the resulting ts (src/tasks/task.ts:536-545) — and Slack accepts a `D…` id there exactly as it accepts a `C…` id, which is exactly the ordinary DM reply path: a DM task links its thread with the `D…` conversation id (src/tasks/task.ts:379, classified as a DM at src/connectors/slack/events.ts:637) and `postToUser` hands that id straight to `postSlackMessage` (src/tasks/task.ts:496), which passes it to `chat.postMessage` unmodified (src/connectors/slack/client.ts:206). `notifyCreator` is NOT evidence for this — it posts to a `U…` USER id, which is a different Slack affordance. The second is answered by deriving the whole binding from the request's ORIGIN: `resolveTriggerOrigin` already classifies a Slack IM as `{ kind: 'dm', userId }` (src/agents/tools.ts:2321-2336), and that classification fails closed — but not where it looks: `getChannelInfo` catches every `conversations.info` error and returns `isIm: false` (src/connectors/slack/client.ts:1735-1738), so a Slack failure makes the conversation look like a channel and a `user` binding is REFUSED rather than mis-targeted. `resolveTriggerOrigin`'s own catch is effectively unreachable; the guarantee comes from `getChannelInfo`'s. The same catch covers the one odd shape Slack can return, an `is_im` conversation with no `channel.user`: it yields no `imUserId`, so `origin.userId` is undefined and the guard refuses. For a `user` binding the tool reads NO id from its arguments at all.

DESIGN. Make the `user` binding symmetric with the `channel` one: `{ type: 'user'; user_id; channel_id; channel_name }`, where `channel_id` is the 1:1 DM conversation (`D…`) the request arrived in and `channel_name` is Slack's own `DM with <real name>` label. Three consequences follow, and each is a simplification rather than a special case. (a) `fireTrigger`'s separate `binding.type === 'user'` branch — which today only produces an English instruction naming a user id, and which no test can distinguish from delivering nothing — is DELETED, and its schedule branch homes the task from `binding.channel_id`/`binding.channel_name` for either binding type, because both variants now carry those fields. (b) `postToBinding`'s `binding.type === 'user' ? binding.user_id : binding.channel_id` collapses to `binding.channel_id`. (c) The canvas/pins refresh stays gated on a channel binding via a local that is set only in that case, so a DM never gets a canvas scan.

The enforcement is two guards in `propose_trigger`, both in the handler and both decided before anything is written. A `user` binding requires `origin.kind === 'dm'` with a `userId` and a `channelId`; otherwise the call is refused and no record is saved. And a `user` binding may carry only `schedule` conditions: `channel_message` is refused, because `fireTrigger`'s message branch ingests the watched thread and replies THERE, which would silently deliver a 'DM me' trigger into the watched channel instead. That check goes inside `buildConditions`, which takes the binding type as a third parameter, so `propose_trigger` and `update_trigger` are covered by one implementation — `update_trigger` cannot change a binding (it has no `binding` parameter, src/agents/tools.ts:2541-2546) but it CAN replace conditions, which is the same hole.

Why not resolve the DM channel at fire time from `user_id` via `conversations.open`? Because storing it at creation is what makes the record self-evidently the DM it was configured from — the requirement is not merely 'delivers to a user', it is 'was configured in that user's DM and delivers only there' — and because it keeps a network call off the fire path.

ANNOUNCEMENTS. `announceTriggerChange` returns early for a `user` binding. The announcement exists so a CHANNEL knows what automation runs in it even when the change was made from a DM (docs/architecture/triggers.md:186); in a DM the only member is the person who just pressed Approve, so the notice would report their own action back to them. One early return covers all five call sites (src/connectors/api/routes.ts:442,463; src/connectors/slack/events.ts:462; src/tasks/task.ts:1917; src/agents/tools.ts:2602,2639).

MIGRATION AND CAPS. No migration: `propose_trigger` has only ever accepted `type: 'channel'`, and the HTTP API has no creation route and cannot change a binding (src/connectors/api/routes.ts:393-395), so no `user`-bound record exists on disk and the two new fields can be required. No new cap: `MAX_TRIGGERS_PER_USER` counts by `created_by`, which in a DM is always known, and `handleTriggerApproval` re-checks it at approval for any binding type (src/tasks/task.ts:1897-1900). The per-channel cap correctly skips user bindings, since it filters on `binding.type === 'channel'`.

DISPLAY. A DM conversation's name is already human-readable (`DM with Dana`), so the `#` prefix that several render sites hardcode produces `#DM with Dana`. `spawn.ts`'s `renderChannel` already special-cases this inline; the same rule is extracted as `formatConversationLabel` in `channel-ids.ts` (which is deliberately dependency-free and is where `taskSlackChannelLabels` needs it — `src/types/task.ts` has no imports, so `client.ts` importing this module creates no cycle), and `formatSlackChannelDisplay` delegates to it so `Task.formatSlackDest` and the persistence log destinations are fixed at the same time.

ACCEPTED RISK, stated so review can weigh it. Because `home_channel` is included in `taskSlackChannelIds` and the explore tools bypass their DM-prefix guard for that set, a fired DM task CAN read that DM's history. That is the creator's own DM, the binding cannot be pointed at anyone else, and the same widening already applies to a private channel a trigger is bound to — but it is new read surface and belongs in the PR description.

OUT OF SCOPE, deliberately: channel-message conditions on DM triggers; DM triggers targeting another user; group DMs (`mpim`, which are `C…`/`G…` ids and are not classified as DM origins by `resolveTriggerOrigin`); a trigger-creation API route; binding edits; any change to channel-bound behaviour; a per-DM cap; and `CHANGELOG.md`, which this repository generates automatically.

CHANNEL_NAME ON A DM BINDING. `getChannelInfo` sets `imUserId` only on the branch that also formats the name as `DM with <real name>` (src/connectors/slack/client.ts:1723-1726), and `getUserInfo` does not catch its own errors, so a failure there unwinds into the outer catch and produces `isIm: false`. Therefore whenever the origin is a DM with a known `userId` — the only case in which a `user` binding is built at all — `origin.channelName` is always of that form. The binding still carries a defensive fallback, and that fallback is deliberately a string that reads as a DM rather than a raw id, because this value is rendered to the agent and in listings and must never surface as `#D0ABC…`.
