# Slack single message path

**Date:** 2026-08-18 · **Status: Implemented (this PR).**

## Brief

Slack messages reach agents through one extraction path but seven different render paths, three of which read `SlackThreadMessage.text` -- a field holding only part of the message. Those paths silently hand agents less than what was posted. That is the defect behind PR #280, and it has been hand-patched twice before. This change makes the Slack-payload-to-agent-text transform a single path, renames the partial field to `ownText` so every mis-read becomes a compile error, and inverts the inbound subtype gate from a 3-entry allowlist to a 17-entry denylist so an unrecognised or future Slack subtype is forwarded rather than silently dropped. Fully supersedes PR #280. Explore-read behaviour is deliberately unchanged.

## Design

Slack ingestion has one extraction path and seven render paths. `resolveRawMessages` (src/connectors/slack/client.ts:826) already funnels every raw payload through one blocks/attachments/files/URL-recovery extractor. What is NOT funnelled is the second half: turning those structured parts into the string an agent reads. Today that happens in three different renderers with four different answers on redaction, and three call sites read `SlackThreadMessage.text` -- a field whose own doc comment says it holds only "the author's own typed text", not the message body. Reading it silently yields less than what was posted. That is the defect behind PR #280 and it has been hand-patched twice before (formatExploreMessages, and handleSlackEdit in b6e0172).

The name already exists internally. The extractor calls this value `ownText` at src/connectors/slack/client.ts:843, 1013, 1245 and 1355, and only degrades it to `text` at one boundary, src/connectors/slack/client.ts:1398, plus the raw-to-public copy at src/connectors/slack/client.ts:1443. So this change propagates a name the code already uses rather than inventing one.

MECHANISM 1 -- one render module. A new file src/connectors/slack/message-body.ts becomes the only place a Slack message becomes agent-facing text. It exports: `SlackMessageParts`; `renderMessageBody(parts, {redacted, includeReactions})`, moved verbatim from `renderMessageForContext` at src/tasks/persistence.ts:267 with one added option; `shouldRedact(msg, ctx)` returning `ctx.shared && isExternalUser(msg.user)`; `messageBody(msg, ctx)` for fetched messages; `exploreBody(msg)`, the single named never-redacted path; and `rawMessageBody(raw, channelId)` which composes `extractMessageContent` (src/connectors/slack/client.ts:2102) with the renderer for callers holding a raw Bolt payload.

`shouldRedact` is the deliberate isolation point for PR #276, which proposes replacing `isExternalUser` with a three-state `classifySlackIngestAuthor` and a broader rule independent of `thread.shared`. Because every path routes its redaction question through this one function, #276 replaces one function body and no call site changes. That converts a competing-designs collision into a one-function merge.

`renderMessageForContext` is deleted from src/tasks/persistence.ts, and `appendSlackMessage` is reshaped to accept an already-rendered body string instead of rendering internally. This also deletes the tasks-to-slack import of `isExternalUser` at src/tasks/persistence.ts:15. `renderAttachmentsSuffix` deliberately STAYS in src/tasks/persistence.ts: it serves outbound logging and has no Slack input, so moving it would hand the tasks layer a fresh connectors/slack import for an outbound-only concern. Its doc comment claims it mirrors the inbound suffix and nothing enforces that, so a test now asserts the two agree.

MECHANISM 2 -- the field rename. `text` becomes `ownText` on `SlackThreadMessage` (src/types/task.ts:56) and on the internal `RawSlackMessage` (src/connectors/slack/client.ts:21). This is the enforcement: every present and future mis-read becomes a compile error rather than a silent blank. Measured blast radius is 43 sites in 8 files, 10 of them production. Nothing serialises this shape -- it exists only as transient `SlackThread.messages` (src/types/task.ts:77) -- so there is no migration. The guarantee is scoped to src/: tools/ is outside the tsconfig program, so a mis-read there would still compile.

MECHANISM 3 -- the subtype gate. `shouldForwardMessageEvent` (src/connectors/slack/task-routing.ts:57) currently answers two different questions with one boolean over an allowlist of three subtypes, which is why PR #280 had to carve a bot_message exception inside the return expression. It splits into `mayWakeTask(event)` and `mayReachTriggers(event, hasWatchingTrigger)`, both consulting one `isContentBearingSubtype` predicate backed by a 17-entry DENYLIST. An unrecognised or future subtype is therefore forwarded, not dropped. `shouldForwardMessageEvent` is retained as the disjunction of the two so the single call site at src/connectors/slack/events.ts:175 keeps its shape and the trigger-index lookup stays lazy. When the gate refuses an event in a channel that has a watching trigger, it logs at debug -- the original incident produced no log line at all.

Trigger dispatch is rewritten. `handleSlackEvent`'s event parameter loses `text` and gains `raw`, and `dispatchChannelMessageTriggers` (src/connectors/slack/events.ts:802) takes the rendered body from `rawMessageBody(event.raw, event.channel)`, computed only after the trigger-count short-circuit so unwatched channels still cost nothing. There is no thread re-fetch, no root-by-ts lookup, and no `?? { text: event.text }` fallback -- that fallback reopens the original empty-string bug whenever fetchSlackThread's filter drops the root (src/connectors/slack/client.ts:2208 drops a message with neither user nor botId).

PIN PATH, AND WHY THE RENDER DOES NOT LIVE IN client.ts. The obvious shape -- have listChannelPins call the renderer at src/connectors/slack/client.ts:1932 -- creates a real module cycle: message-body.ts must import isExternalUser from client.ts for the forwarded-attachment provenance label, and src/connectors/slack/channel-pins.ts:9 already imports listChannelPins from client.ts. So the render moves one level out instead. listChannelPins stops pre-joining a string: PinnedItem drops `text` and instead carries the structured parts it already has -- ownText, attachments and files -- and src/connectors/slack/channel-pins.ts:141, which is the ONLY production reader of that value and already computes sourceText there, calls renderMessageBody with includeReactions:false. The dependency graph becomes channel-pins -> message-body -> client with no edge back, and client.ts is left as what it should be: the extractor, which renders nothing. includeReactions:false is load-bearing rather than cosmetic: RawSlackMessage carries reactions (src/connectors/slack/client.ts:32), the pin summary cache is keyed on digestOf(normalisePinText(sourceText)) at src/connectors/slack/channel-pins.ts:142, and reactions change without the pin being edited, so including them would convert re-summarise-on-edit into re-summarise-on-every-emoji. Widening the text does force exactly one re-summarise per affected pin -- normalisePinText collapses whitespace so even the separator change alters the digest -- on demand via the existing TTL scan and bounded by MAX_MODEL_CALLS_PER_SCAN and MAX_INDEXED_PINS (src/connectors/slack/channel-pins.ts:26,33); that cost is accepted. The pin trust gate at src/connectors/slack/channel-pins.ts:112 reads botId and teamId and is untouched.

NOT CHANGED. Explore reads keep rendering unredacted, via the explicitly named `exploreBody`, because the operator required no behaviour change where nothing is broken; `SlackChannelMessages` therefore does not gain a `shared` field. The admission gates in src/connectors/slack/channel-pins.ts and src/connectors/slack/channel-canvas.ts are untouched: they DROP un-vetted content and fail closed, which is categorically different from redaction, and folding them into a renderer would weaken them. DEVIATIONS FORCED BY REVIEW, AND WHY. A blind review confirmed six defects; all are fixed in commit 14b7898 and two of them narrow decisions recorded earlier in this plan.

First, the denylist inversion was applied to BOTH arms of the gate as the operator chose, but the task-creating arm needed a floor the plan did not anticipate. A payload with no author and no body — an assistant-container notice, a `tombstone`, a `bot_add` — reached `Task.create()` and woke the PM on an empty knowledge log. The floor is `thread.messages.length > 0`, applied to the task-creating branch ONLY. It is subtype-agnostic on purpose, so a future empty subtype is refused with no list to maintain, and it is deliberately absent from the trigger branch: that path renders from the raw event precisely because `fetchSlackThread` drops a message with neither a `user` nor a `botId`, so gating it on the fetched thread would reintroduce the blindness this change removes. An earlier attempt placed the guard before the trigger branch and did exactly that; the dispatch tests caught it.

Second, `bot_message` now reaches triggers but never wakes a task. Forwarding it on the task arm meant every CI, Jira, Datadog and GitHub-app post into a followed thread cost a PM model turn, at volumes no human sends. The operator's `me_message` case — a human thread reply — is unaffected. This is a real narrowing of the 'invert both arms' decision and is surfaced to the operator rather than buried. Relatedly, `routeSlackEvent` now also discards events authored by our own bot USER id, not just our `bot_id`: Slack attributes some app-authored events to the acting user, and `handleSlackEvent` itself refreshes the canvas and pin index, so a filterless trigger in a watched channel could otherwise fire on Archie's own housekeeping.

Third, two invariants existed only as comments and the review proved both deletable with the suite green: the `PinnedItem` reactions/files carry, and `Task.append`'s render-after-download ordering. Both now have tests that fail under the corresponding mutation. The pin-reactions commit's own justification had been unverified, which is the sharpest possible argument for the check.

Fourth, `pinBody()` in the render module replaces an inline `renderMessageBody(..., { redacted: false, includeReactions: false })` at the pin call site. Without it, AC2 and AC6 were literally false — `channel-pins.ts` read the partial field and answered the redaction question for itself, and the structural guard had been widened to permit both. The guard's allowlists are now back to the render module and the extractor.

Fifth, the gate drop-log is `debug`, not `warn`. With a denylist, the only events droppable in a trigger-watched channel are the denylisted noise ones, because a content-bearing top-level post always satisfies `mayReachTriggers` there. The silent-drop class the log was written to catch is now structurally impossible rather than merely reported, so warning on it would flag routine `channel_join` traffic as an anomaly.

Sixth, a security gap this change opened and closed. The author bail-out in `handleSlackEvent` is `event.user`-gated, and an app post carries no `user`, so it is never classified there; trigger dispatch renders from the raw event rather than the fetched thread, so `fetchSlackThread`'s external-bot filter never applies either. While app posts were dropped by the subtype allowlist that closed the hole by accident, but forwarding them deliberately meant an app post from a FOREIGN workspace in a Slack Connect channel could fire a trigger unclassified. `dispatchChannelMessageTriggers` now gates on the bot's own team before rendering, mirroring the rule thread ingestion and the pin index already draw — drop a bot from a foreign team, keep internal bots — rather than inventing a stricter one. Found by the documentation verifier, not by either review round.

## Open at plan time

What the checks could not close. These travelled to implementation as watch-outs and to the pull request as unresolved items.

- The triggered task never sees the message body. `FireContext.text` is declared at src/system/trigger-scheduler.ts:193 and never read inside `fireTrigger`, and `linkSlackThread` sets `last_processed_ts` to the triggering ts so a later append skips that message. So this change alters which posts FIRE, not what the spawned agent then reads. A trigger with no `contains` filter sees no behavioural change at all. Worth a follow-up if the intent is for the PM to receive the report it fired on.
- `rawMessageBody` re-extracts a message the upstream `fetchSlackThread` already pulled, because `handleSlackEvent` needs the channel name before dispatch. Taken deliberately over a thread-root lookup, which is exactly what can miss and fall back to an empty string. Cost is confined to watched channels with a matching trigger.
- PLAUSIBLE, not fixed: the @mention de-dup at src/connectors/slack/events.ts reads `event.text?.includes('<@BOT>')` on the raw payload, so a post mentioning Archie only inside a block or attachment is not skipped — `app_mention` creates a task and the message handler can also fire a trigger. Pre-existing in kind for blocks-only human posts; newly reachable for bot posts now that they are forwarded.
- `rawMessageBody` cannot emit the `[forwarded from … — external]` provenance label, because `extractMessageContent` strips attachment authors (src/connectors/slack/client.ts:2108). Pre-existing on the edit path; it means the trigger-dispatch body and the edit body carry attachment text without provenance.
- Two test files mock `client.js` without supplying `extractMessageContent`, which `message-body.ts` imports transitively: src/tasks/__tests__/persistence.test.ts and src/connectors/slack/__tests__/channel-pins.test.ts. Both pass because the binding is never dereferenced on their paths — a latent trip-wire if the render module ever calls it on a shared path.
- docs/architecture/slack-integration.md:62 still documents the old three-entry allowlist, and :139 the pin index shape. CLAUDE.md requires docs/architecture to describe the current system accurately, so these are updated at ship, not deferred.
- Live-e2e was proven for boot, attestation and health (Attested: instance composed from b7f9b56, /health git_sha matched, clean teardown, no Slack side effect). The scenario DRIVE loop could not be exercised: this session's permission classifier blocked both a subagent and a direct POST to the local instance.
