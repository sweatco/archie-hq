# voice-cases

A prompt-regression harness for `prompts/voice-speaking.md` — the system prompt that decides what Archie says out loud in a voice meeting and what it posts to chat instead.

## What it measures

`defect.mjs` runs a 41-case suite (`dcases.mjs`) targeting nine specific defects the prompt has previously shipped with, or could plausibly ship with next: D1 contamination (the transcript brushes against a worked example's topic and the reply leaks that example's identifiers as if they were fact), D2 fabrication (the transcript has no dates/times/ids/figures at all, and the reply invents some anyway), D3 spoken-detail leakage (a hash, path, URL, ticket id or version number reaches the room's ears instead of the chat line), D4 owner's-name-from-transcript (the answer is sitting a line or two up in the conversation, asked in Russian, with an English control for each case), D5 machinery-leak (the transcript holds a genuine unknown that tempts a PM consult, and the spoken half names who or what Archie asks rather than just promising to find out), D6 pending-nag (a PM consult was already acknowledged once, and a later, unrelated turn gets the pending lookup re-announced anyway instead of a plain answer to what was actually asked), D7 insistence-fabrication (pressed directly for that same unanswered consult's value, the reply asserts a specific open-ended answer — a title, a name, a sentence — that nothing sourced, the same defect D2 measures but shaped as prose rather than a number or hash D2's harvester would catch), D8 provenance-denial (asked point-blank whether an earlier answer was real or invented, the reply claims a source that never existed instead of admitting the answer was not sourced), and D10 untold-consult (the same outstanding consult with the acknowledgement **deleted** from the transcript, which is the state production reaches whenever a turn is abandoned before a byte of audio plays: `routeConsult` runs in `answerRoom`'s `finally` however the turn ended, while the transcript receives only what the sink confirms, so the question is out and the room was never told — and the graded behaviour is therefore the exact inverse of D6's, since the reply *must* volunteer the pending lookup rather than suppress it). D6/D7/D8 reconstruct one real live-meeting incident as three prefixes of the same expanding transcript; see the family comment above `DCASES` in `dcases.mjs` for the full incident. D10 is that same incident's first prefix with Archie's own acknowledgement taken out, so that the suite can reach the state the code reaches routinely and D6's fixtures never present, and it has its own family comment further down that file. Each family has Russian and/or English cases so a failure can be told apart from a language-specific gap.

One further defect is measured across families rather than as a family of its own: **a promise of future work with nothing behind it.** The prompt tells this voice to say it will find something out, and gives it exactly one way to make that true — a trailing `PM:` line — so "let me check the logs and I'll get back to you in a second", with no `PM:` line and no consult already in flight, promises an action nobody is taking. `unbackedPromiseCheck` recognises the grammatical act of that commitment (a first-person forward commitment to obtain information) in English and Russian, anchored on grammar rather than vocabulary for the same reason `assertedAnswerCheck` is; `gradeDefect` grades it as a hard failure on D2 only — the fabrication family, where a fabricated future *action* belongs, and where `D2f-invited-promise` exists to measure the distinction rather than to ban the promise — and records it as advisory information on every other family, so the fail definitions the stored result rows were collected under stay intact. `compare.mjs` prints the advisory half.

Six of those 41 cases (`D4g`-`D4l`, built by `long-transcripts.mjs`) are the only ones in this harness that measure **production's real transcript length**. Every other fixture here holds 10 to 30 lines, because the speaking window was three minutes wide when they were written; it is now the whole meeting, bounded by a three-hour backstop, and `TRANSCRIPT_WINDOW_MS` in `meeting.ts` measures real transcript logs at 8,000-10,400 tokens per hour. So the rest of the suite measures the short-transcript case while production runs the long one — and the risk that opens is specific: more context can make a model *worse at finding an answer that is present*, and worse in a way that depends on where the answer sits (Liu et al., "Lost in the Middle": up to a 22-point drop between a fact at the start of a 20k+ token input and the same fact in the middle). The six are therefore two triples rather than two cases — the same question, the same answer and the same ~490-line meeting, with the supplying line near the start, at 49% depth, and four lines above the question — because "does it cope with length" and "does position matter" are different measurements and one case cannot tell them apart. English and Russian are mirrors here, as `D4a`↔`D4d` already are, and are matched on tokens rather than on lines (~9.5k and ~10.2k respectively; Russian costs about 2.43 chars per token against English's 3.17). The filler is hand-written meeting talk rather than generated boilerplate, and its inertness is asserted mechanically by `long-transcript.test.ts` rather than by reading: every `must` regex matches the one supplying line and finds zero matches in the other 489, no near-miss term appears in the filler at all, the three variants are byte-identical apart from the index of one line, and no worked-example identifier is anywhere in the transcript (one would silently disarm the contamination check, since `leakCheck` excuses anything the transcript already contains).

`turns.mjs` runs a second, **multi-turn** suite: `tcases.mjs`'s three `kind: 'D9'` cases, each a chain of turns rather than a single snapshot. Every case in `dcases.mjs` hands the model one transcript and grades one reply, which means none of them can reproduce a failure that only emerges once the agent's *own* prior turns are part of its input — and that is exactly the shape a live meeting produced: asked to look something up, Archie raised a consult, then re-announced that pending consult on every following turn while the room was asking other, answerable questions, then fabricated an answer to the pending question, then claimed it had received that answer from somewhere. The room was not pressing; it had moved on. A D9 chain reproduces that run-up by doing between turns exactly what production does — appending room utterances, calling the model with the real assembly (accumulated transcript plus the `<consults>` block, where a pending consult renders literally as `A: (no answer yet)`), parsing the reply with the real parser, and appending **only the spoken half** as `Archie: ...`, never the `CHAT:` line and never the `PM:` line, mirroring `noteOwnAnswer(answer.speech)`. A literal `<think>` block is deliberately not on that exclusion list: production takes its reasoning off a channel of its own now and strips nothing from the content channel, so such a block is text the room heard, and the next turn has to be conditioned on what the room heard. `D9a` (English) and `D9b` (Russian, and a meeting of its own rather than a translation) hold a consult pending across three turns whose answers are sitting in the transcript, a fourth where the room comes back to the original question, and a fifth that challenges the provenance of whatever was just said; `D9c` resolves the consult mid-chain and measures whether the answer is delivered in the agent's own words without naming who or what supplied it.

D9 writes no new detectors, deliberately. Each turn declares `as` — one existing kind or an array of them — and is graded by the same `gradeDefect` through a per-turn pseudo-case carrying that kind plus whatever fields it reads (`subject` for D6/D7, `must` for D4, `detail` for D3), with the failures unioned. Every detector reached that way has been validated across 180 stored result rows; a new one would not be. One semantic in that wiring is load-bearing and easy to get quietly wrong: the pseudo-case's `transcript` — what `fabricationCheck` and `leakCheck` treat as *sourced* — holds the room's utterances only, never Archie's own turns. If the agent invents a value at turn 3, its own line enters the model's input at turn 4, and counting that line as a source would make the same invention look sourced from then on, masking the precise failure the fixture exists to catch. The model-facing transcript is a different string and does contain those lines, because the model has to see what it said.

Two turns are graded differently from the plan this suite was written to, and both departures are recorded in `tcases.mjs` next to the turn: the turn where the room asks the pending question *directly* is graded D7 alone rather than D6+D7 (D6 measures an **unprompted** re-announcement, and when the room asks, some form of "no word yet" is the only honest answer available — `no-update-yet` and `ill-let-you-know-when` would both fail a reply that is behaving perfectly, which is also why `dcases.mjs` grades `D7a-en-readme-pressed` as D7 only), and D9c's delivery turn carries `D4` alongside `D5`/`D8` because `gradeDefect` reads `must` under `kind === 'D4'` and nowhere else, so a `must` without it would have been a silently dead assertion.

Ten files here run under the repo's own `npm test` (vitest, `tools/**/*.test.ts`), and all ten exist because an instrument nobody tested has already produced confidently wrong conclusions in this directory. `unbacked-promise.test.ts` asserts both halves of the promise detector — every phrasing that must fire and every phrasing that must not — in English and in Russian. `user-message.test.ts` pins the request assembly byte-for-byte against the hand-written copy it replaced. `turn-chain.test.ts` drives the whole D9 chain machinery against a **stub transport**: canned replies, zero model calls, and therefore zero cost — a re-announcement at turn 2 must produce a `REPETITION` fail at turn 2, a clean chain must produce zero fails, a fabrication at turn 4 must be caught at turn 4 *and again at turn 5 when the model repeats it*, and the `CHAT:`/`PM:` exclusions must hold while a literal `<think>` block does the opposite — graded as speech, filed into the next turn as speech, and failed three times over, for the tag, the markdown and the machinery leak inside it. The room-only-transcript rule above is proved by a different test than that repeat, and the distinction is worth keeping straight: turns 4 and 5 are graded D7, and `assertedAnswerCheck` never reads the pseudo-case's transcript at all, so that pair would catch the repeat whatever the transcript held. The rule's own test overrides those two turns to `D2` — `fabricationCheck` is the detector that does read it — and pairs the result with a counterfactual that re-grades the same turn-5 reply against a transcript carrying Archie's own turn-4 line and watches the failure vanish. The Russian half is not optional in any of them. Three detectors in `defect.mjs` (`assertedAnswerCheck`, `PROVENANCE_CLAIM_RU`, and `pendingNagCheck`'s subject-anchored tier) silently never fired on Russian input for an unknown period because JS's `\b` and `\w` are ASCII-only, and in all three cases the only thing that caught it was executing the regex against an ordinary Russian phrasing — the third of them was still being described in a comment as *working* while `Я смотрю таблицу в ClickHouse.` produced no hit at all. `long-transcript.test.ts` is the fourth, and it exists because the inertness of ~490 lines of filler cannot be established by reading them: it asserts the sizes, the byte-identity of the three variants, that every `must` regex matches the supplying line and nothing else in the transcript, that a faithful reply grades completely clean and a reply that never found the answer fails once per fact, and that the Russian `must` groups fire on eight ordinary Russian phrasings — bounded with `(?<!\p{L})`/`(?!\p{L})` under `u`, with the ban on `\b` and `\w` asserted rather than left as a convention. `context-arm.test.ts` is the fifth, and two of its assertions matter more than the rest. It pins the bare arm's byte-identity to the two-argument call every stored row was collected under, for every case in both suites — the arm is additive precisely so that corpus stays comparable, and "additive" is a claim about bytes. The second pins the same claim from the other side: `full` is asserted to be the bare bytes plus one fixed suffix, per case, rather than a set of tags that merely turn out to be present, so a block that started rendering per-case would fail rather than pass quietly. A third group of assertions used to live here and is gone with its subject — the derived `<situation>` verdict, its family table, the contradiction check that refused a verdict the fixture denied, and the four mis-derivations that check was tested against. What is left is one arm's worth of context and the inertness of it. The rest of the file asserts that the ~8,700-character pinned context is inert (nothing `fabricationCheck` would read as an invented value, and zero collisions with any fixture's `must`/`detail`/`subject` regexes), which is not something ~8,700 characters of plausible prose can be established to be by reading them. `rate-limit.test.ts` is the sixth: it drives the whole retry path against a stubbed `fetch` on a driven clock — a 429 then a success producing a row that grades, `Retry-After` honoured as a floor, a 400 failing on its first attempt, both caps binding independently of each other, and jitter asserted as a spread rather than a value. `POOL` moving a *driver's* real concurrency was asserted here too and no longer can be: the triage driver was the only one whose runner pools and whose transport is injectable, and production removed the call it measured. What is left is `poolSize`'s own coverage plus the pair asserting that each driver's hardcoded constant is gone and its fallback is the value every stored run used. Every wait in it is fake-timer time, so the 75-second cap is exercised in milliseconds and nothing is billed. `sample-accounting.test.ts` is the seventh, and the fixture at its centre is the campaign that prompted this file's accounting: 111 rows with 32 lost to the TPM limit, which must come out as `79/111 rows graded` under a banner, never as a table of rates. It also pins the two mistakes on the other side of that line — an errored row must not be counted as a failing reply by `quality.mjs`'s pass count, and a chain that ended early on a transport error must not be counted as a chain that failed. `pending-nag.test.ts` is the eighth, and it exists because the Russian half of `pendingNagCheck` reported clean on a defect it could not see: `D6c-ru-weather` produced the same unprompted re-announcement its English twin fails on — *"но как только получу ответ по репозиторию, сразу скажу и то, и другое"* — and passed, because `STALL_GENERIC_RU` had no counterpart to `ill-let-you-know-when`. A false negative in the instrument is worse than a failing case, so this file pins both halves of every Russian entry: the observed phrasing and its variants firing, honest declines and a genuinely-arrived answer staying silent, and the D6/D7 split asserted from both sides — the same words are a re-announcement on a D6 turn and the only honest answer on a D7 turn, which is why the English tier already fires on a passing `D7a` row. It also pairs the entries by name, so the next English-only addition fails a test rather than quietly leaving Russian short, and it carries the Cyrillic-bounding check in its strongest available form: it takes the shipped regex, substitutes `\b` for every Unicode bound, and asserts the result goes dead on an ordinary Russian sentence. `untold-consult.test.ts` is the ninth, and it guards the seam between the two families that measure opposite behaviour over the same outstanding consult: the observed nag — *"I'll let you know as soon as I have that first line from the readme"*, and its Russian counterpart out of `results/defect-post-r{1,2,3}` — must fail `D6a`/`D6c` on `REPETITION` and grade **completely clean** on `D10a`/`D10c`, same words, same detector suite, one deleted transcript line between them. The rest of the file pins what makes that safe rather than lucky: `pendingNagCheck` is unreachable from a D10 row (asserted through `info.nag` being populated on one and absent on the other, not merely through the failure list), a `CHAT:` or `PM:` line does not satisfy a `mustSay` group because it does not tell a room anything, and a `SILENCE` reply fails on the protocol check alone rather than three times over for one behaviour. One of its assertions is a mutation rather than an expectation: an unsatisfiable group must make a correct reply fail, in either position, so the rest of the file cannot be passing for the wrong reason. A second mutation stood beside it until the triage gate was removed — handing the same groups over as `must` had to make `deriveVerdict` throw, which was the whole reason the field is spelled differently. Nothing derives a verdict any more, so what keeps the two names apart today is `gradeDefect` reading `must` under `kind === 'D4'` and nowhere else. The same file now also carries `internalIdLeakCheck`'s own suite, rehoused from the deleted triage file: known-bad and known-good one line apart in English and in Russian, both tiers exercised, the shipped pattern read out of `defect.mjs`'s own source and asserted free of `\b` and `\w` — and, last, an assertion that **nothing calls it**, so whoever wires it into `gradeDefect` is told by a failing test rather than by a comment. It is kept uncalled rather than deleted or wired because the id class it catches is real and unmeasured — every D6/D7/D8/D10 fixture renders an `m1c1` in front of the model — while wiring it in is a rubric widening, which this directory does deliberately and never as a side effect of a refactor. `reasoning-arm.test.ts` is the tenth, and it covers the two things in the wire adapter whose failures are *invisible* rather than loud. Reasoning that leaked into `m.text` would be graded as speech and fail rows on words no room heard; reasoning that was dropped instead of counted would report a thinking arm as thinking nothing; neither raises an error. So it asserts the reply and the reasoning are two strings, that nothing of the reasoning reaches the emitter or the parsed speech, that `reasoning_tokens` is read off the usage frame, and that "never reported" (`null`) and "none" (`0`) keep different spellings. It also pins both request bodies by their **key list and order**, not by a subset — the thinking arm's `model, max_completion_tokens, temperature, stream, messages, reasoning_effort` and the baseline's same list minus the last, with `reasoning_format` and `max_tokens` asserted absent, because a field production does not send is a request no meeting makes. And it pins the `<think>` strip, which is the one reimplementation of a function production deleted: both mid-stream verdicts, non-nesting, a streamed block removed from the reply *and* from the emitter, the arm off leaving the same reply alone and flagging the tag as spoken, a malformed closing tag flagged even under the arm — and, character by character over a whole reply, that the visible text only ever grows as a prefix, which is the property that makes streaming it safe. Every one of these runs against a stubbed `fetch` on canned frames: no model call, no cost.

`quality.mjs` runs a separate, broader 16-case suite (`cases.mjs`) covering general behaviour: narrowed questions, withdrawn questions, prompt injection (English and Russian), code-switching, when to stay silent versus when ambiguity itself is not a reason to go silent, leading with the answer, numbers spoken as words, and more.

All three suites grade mechanically — regex-based detectors in `defect.mjs` (`gradeDefect`, which `turns.mjs` reuses once per kind per turn) and `quality.mjs` (`grade`), never an LLM judge — and all of them print exactly what a detector flagged, so a rubric can be audited against the raw reply text rather than trusted blind.

`providers.mjs` is the wire adapter. It calls each provider with bare `fetch` and manual SSE parsing, deliberately not an SDK wrapper, because production (`src/voice/comprehension.ts`) does the same and this harness has to measure that exact path. It wires two providers, Anthropic and Cerebras, and eight candidates across them; the Anthropic six are comparison arms only. The Cerebras two are both `gemma-4-31b` and differ by exactly what production changed: `cerebras-gemma-4-31b-thinking` is production at HEAD — `reasoning_effort: 'medium'`, `max_completion_tokens: 2000`, and no `reasoning_format` key, because `requestBody` sends none — while `cerebras-gemma-4-31b` is the shape production sent one commit earlier, with no `reasoning_effort` field at all and the 600-token cap that was `SPEAKING_MAX_TOKENS` then. The second is kept exactly as it was rather than moved forward, because it is the baseline arm and every stored row in `results/` was collected under those bytes. Each candidate's own cap wins over a driver's argument for that reason: the difference between the two is production's, not a knob. Both adapters mirror `comprehension.ts`'s request shape exactly — same model id, same endpoint, same temperature, same message framing — so a defect measured here is a defect production would actually hit.

**The reasoning channel is parsed and never spoken.** Cerebras returns native reasoning as `choices[0].delta.reasoning`, alongside `choices[0].delta.content`, and the adapter accumulates the former into a `reasoning` string that is returned to nobody: only content reaches `m.text` and only content reaches the `SentenceEmitter`, which is what structurally keeps a thought out of a room. `usage.completion_tokens_details.reasoning_tokens` is read off the usage frame when it carries one, and left alone when it does not — so `reasoningTokens` is `0` for a candidate that asked for no reasoning and `null` for one that asked and was never told, which are different facts and must not share a spelling. Every call records the same three things on both arms: time to the first **content** token, total time, and reasoning tokens. Time-to-first-content is the comparable quantity on purpose, and the comparison is the point: an arm whose prompt asks for `<think>` tags spends its reasoning on the content channel, and an arm with native reasoning does not, so normalising that away would erase the measurement.

**`STRIP_THINK=1` is the one arm that still strips tags, and it lives on the wire.** Production stripped `<think>...</think>` out of the content channel until native reasoning landed, and does not any more, so nothing downstream of `providers.mjs` strips anything — a literal tag on the content channel is text the room hears, and is graded as such. But a prompt that *asks* for those tags is still a measurable arm (it is what production sent one commit ago), and grading its reasoning as speech would score every row of that arm on words no room was going to hear. So the strip is reimplemented in `providers.mjs` from the function `comprehension.ts` used to export, semantics included — mid-stream a partial `<thi` and an unclosed block are withheld; at the end a partial tag was never completing and is kept, while an unclosed block is discarded with everything after it — and it is applied to the stream before the emitter or the parser sees a byte. Unset is off, and an unrecognised value throws before anything is billed, for the same reason `CONTEXT_ARM` does.

`pacing.mjs` decides how hard a campaign pushes the API and what happens when the API pushes back: the `POOL` and `MIN_GAP_MS` knobs, the 429 retry policy (`Retry-After` honoured as a floor, equal-jitter exponential backoff otherwise, a cap on attempts and a cap on total wait), and the per-process tally of what actually went on the wire. `providers.mjs`'s `runCall` is its only caller for the retry and the pace; the drivers call `poolSize()` and print the tally. It exists because a campaign of 6 invocations x 37 cases at `POOL = 5` lost a third of its rows to `HTTP 429 "Tokens per minute limit exceeded"` and the harness had no retry, no backoff and no `Retry-After` handling anywhere. Every default reproduces the dispatch pattern every stored row was collected under, so nothing changes unless an environment variable says so — see "Rate limits and pacing" below.

`emitter.mjs` imports the real `parseReply`, `SentenceEmitter` and `TAIL_MARKERS` straight from `comprehension.ts` and adapts their shape to what this harness's graders consume — it used to be a hand-copied port instead, which drifted from production three times in two days (a missing `PM:` marker, missing `<think>` handling, a missing `LEAVE:` marker) before those were exported for exactly this purpose. It carries no think-stripping of its own, deliberately: production has none to import, and the one arm that needs a strip gets it on the wire, upstream of this file. Because `comprehension.ts` is TypeScript, everything that reaches it — `defect.mjs`, `quality.mjs`, `turns.mjs`, `compare.mjs`, `providers.mjs`, and now `promptio.mjs` as well — has to run under `tsx`, not plain `node`; see "Running one arm" below.

`promptio.mjs` imports the request half from the same place, for the same reason: `buildSpeakingUserMessage` is exported from `comprehension.ts`, and `userMsg()` is a call to it — replacing what this file used to carry as a hand-written "faithful port" of production's transcript framing and its `consultsBlock`. `system()` is the filled prompt and nothing else, because that is what `decideResponse` puts in the system message: one call, the whole file, no splitting and no placement switch. Three arguments and no more, because production's speaking call takes exactly three; the third, `context`, defaults to undefined for the reason the arm exists — every row already in `results/` was collected with no standing blocks, and defaulting them on would silently invalidate that corpus. `user-message.test.ts` pins the delegation byte for byte.

`context-arm.mjs` decides **how much of production's request a campaign sends**. Production's speaking call carries five blocks; until this file existed the drivers sent two of them (`defect.mjs` called `userMsg(c.transcript, c.consults)`, `quality.mjs` passed the transcript alone), so the suite could not see the effect of `<written>`, `<participants>` or `<capabilities>` at all — it measured a prompt written for a request it never sent. The fix is an arm rather than a default, because 180 stored rows were collected without those blocks and are the known-good every later run is read against: `CONTEXT_ARM=bare` is the default and is byte-identical to those rows, and `full` is selected explicitly. See "Running the full-context arm" below.

`compare.mjs` offline-regrades stored result files under one current rubric and prints a before/after table by case and by defect family, so two arms collected at different times (possibly under different versions of the detectors) are still judged fairly against each other. It regrades `turns.mjs` rows too: a chain turn is filed under `<case id>#T<n>` and its pseudo-cases are a pure function of the fixture, so a stored row re-grades from the fixture alone exactly as a single-turn row does.

`sampling.mjs` is what every report says about its own completeness: rows graded, rows dropped, the reason class of each drop, and — above a threshold — a banner saying the arm's rates must not be read. All four report sites use it (`compare.mjs`, `defect.mjs`, `quality.mjs`, `turns.mjs`), so a rate-limited campaign says so in the driver's own output while you are still watching it, not three commands later. See "Never silently short a sample" below for the threshold and its reasoning.

`campaign3.sh` runs an arm-interleaved two-arm campaign: `defect.mjs` and `quality.mjs` for arm A, then for arm B, repeated for N runs, so each pair of runs sits adjacent in time rather than one arm running to completion before the other starts.

## Why runs must be decorrelated across processes

At temperature 0, repetitions inside a single process are correlated samples — in a controlled comparison, two invocations of the same prompt and transcript produced opposite behaviour (5/5 refusals versus 8/8 answers) while the reps *inside* each of those invocations were byte-identical to each other. A run of N reps inside one process is therefore much closer to a single sample dressed up as N than to N independent draws. `campaign3.sh` exists to fix this: each arm is sampled as several separate process invocations rather than one invocation with several reps, and the two arms alternate run-by-run (A, B, A, B, ...) rather than A running to completion before B starts, because API latency and behaviour drift over a measurement window and interleaving keeps that drift from being mistaken for a difference between the arms. If you write a new script against this harness, keep both properties: separate processes per sample, and interleaved arms.

## Rate limits and pacing

The limit this harness actually hits is **tokens per minute**, not requests in flight. A 6-invocation campaign of 37 cases at `POOL = 5` — an invocation being 205,885 input tokens bare and 278,271 full, as the paced re-run of that same case set later billed it end to end — came back with 32 of 111 rows on one arm and 37 of 111 on the other carrying nothing but `HTTP 429 "Tokens per minute limit exceeded - too many tokens processed."`, and every one of those rows cost a sample.

**A 429 is now retried rather than lost.** `Retry-After` is honoured when the response carries it — as a floor, never shortened, with up to 1s of random spread on top so five pooled workers that all received the same header do not wake on the same tick — and when it does not, the fallback is exponential backoff with *equal* jitter: half the nominal delay plus a random half. Equal rather than full jitter on purpose: a draw near zero would retry straight back into a token bucket that is still empty, spend another request's worth of limit and come back 429 again. The schedule is 5s, 10s, 20s, 40s.

**Only a 429 is retried.** A 400 means the same request will fail the same way for ever, so `context_length_exceeded` or a malformed body still fails on its first attempt; retrying it five times would buy five times the wait for the identical answer. 5xx and 529-overloaded are arguably "later" too and are still not retried, because the only failure mode measured here in bulk is the TPM 429 and broadening the retryable set on speculation turns genuine breakage into slow breakage. `isRateLimited` in `pacing.mjs` is the one-line change for whoever measures a case for another status.

**It is bounded, twice.** At most 5 attempts (one plus four retries) and at most 75 seconds of total sleeping per call — both stated with their reasoning in `pacing.mjs`'s `RETRY`. The 75s is the load-bearing number: a tokens-per-minute bucket is a 60-second window, so a cap under ~60s would give up while the only thing needed was to wait the window out, and 75s is one window plus slack and no more. The two caps meet by construction (the schedule's own total reaches 75s exactly as the fifth attempt is refused), so neither is decoration. Past those bounds the row is lost — but it says so: its error carries `gave up after N attempt(s) and Xs of backoff`, and the run's accounting classes it as `rate-limit` rather than as an unexplained failure.

**Retrying does not double-count.** Each attempt is instrumented separately, so a row's `ttft`/`complete`/token counters belong to the attempt that produced it and never include the backoff or a refused attempt's numbers — which matters because this is a latency harness before it is anything else. What a retry does add is *requests*, and those are reported separately: every driver ends with a `wire:` line giving requests sent, retries, rate-limited responses, seconds slept and rows given up on. `requests` above `rows graded` is a retried run, not a double-counted one. The pre-run banner in `turns.mjs` now says **at least** N billed calls for the same reason.

**Two knobs, both defaulting to today's behaviour.** `POOL` sets the worker-pool size — 5 in `defect.mjs`, 3 in `turns.mjs` when unset, which is what every stored row was collected under (`quality.mjs` is serial by construction and has no pool). `MIN_GAP_MS` sets a floor on the gap between dispatches, defaulting to 0, i.e. no pacing at all. A malformed value for either throws before anything is billed rather than being silently ignored.

Use both, because they bound different things. A pool bounds how many requests are in flight; it only bounds the *token* rate if every request is the same size and takes the same time, and neither holds here — the six long-transcript cases carry ~8k tokens of transcript each (billed, off `inputTokens`: ~8.0k English, ~7.8k Russian) while the other 31 carry ~1.7k between them, so on the full arm five workers can have ~72k tokens or ~33k outstanding depending on which cases happen to be adjacent in the job list, and the pool refills the instant a call returns, which makes a fast model a much higher request rate than a slow one at the same nominal concurrency. A floor on the inter-dispatch gap bounds requests per minute directly (`60000 / gap`), and requests per minute times mean tokens per request is the quantity the limit is written in.

Sizing it is arithmetic, not taste. For a `defect.mjs` rep of all 41 cases on the full arm at ~338k input tokens, mean request size is ~8.2k tokens, so a limit of L tokens/minute allows about `L / 8200` requests per minute and the gap wants to be about `60000 / (L / 8200)` ms. Both figures come off the provider's own `usage` rather than a chars-per-token fit — see "What is pinned, and at what size" for the measurement and for why the fit reads about a third high here. Halve that budget if two invocations of the campaign script overlap, and remember the retry is a second line of defence, not the plan: a run that spends 40 seconds asleep per row is a run that should have been paced.

## Never silently short a sample

`compare.mjs` skipping a row that carries `error` is right — there is no reply text to re-grade, and grading it as a failure would invent a defect out of a rate limit. Doing it invisibly is what nearly produced a set of quoted findings from a table whose per-case scores were out of 1, 2 or 3 reps with nothing anywhere saying so.

So every report now states, unconditionally and before any rate: rows graded, rows dropped, and the reason class of each drop (`rate-limit`, `timeout`, `http-4xx`, `http-5xx`, `stream-error`, `unknown-case`, `other`). Unconditionally matters — a line that appears only when something is wrong teaches a reader that its absence means nothing was checked. `unknown-case` is in that list because it was the *other* silent drop: a stored row whose case id no longer exists in the fixture set was skipped with no more noise than an errored one.

Above a threshold the arm is fenced off with a full-width banner reading `INCOMPLETE SAMPLE — DO NOT READ RATES OFF THIS ARM`, printed to stderr as well as stdout so a campaign that redirects stdout to a per-run log still shows the alarm on the terminal while it is running. The threshold is **5% of an arm's rows**, plus a second trigger with no fraction attached: **any case that was attempted and produced no graded row at all**. The reasoning for both is in `sampling.mjs`'s `INCOMPLETE_FRACTION` — in short, drops here are close to missing-at-random with respect to what is being measured (a TPM 429 depends on tokens in flight, not on what the reply would have said), so the harm is a rate claiming a denominator it does not have; at 5% with 3 reps per case roughly one case in seven is scored out of 2 instead of 3, which the stated counts let a reader discount, and past that the shortfall is the headline rather than a caveat. A case with no graded row prints as ` - ` in the table, which reads as "nothing to see" rather than "silently lost", and that is worth a banner however small the overall fraction is.

Three related counts were wrong in the other direction and are fixed here: `quality.mjs` counted a transport error as a quality failure outright, and `defect.mjs`/`turns.mjs` kept an errored row in the denominator while it could never reach the numerator. All three now compute over graded rows only, and a chain that ended early on an errored turn is reported as a dropped chain rather than as a chain that failed — `runChain` stops at the error, so its later turns never happened.

## Running one arm

```
../../node_modules/.bin/tsx defect.mjs <candidate> <reps>
../../node_modules/.bin/tsx quality.mjs <candidate> <reps>
```

Run under `tsx`, not plain `node` — `emitter.mjs` imports `src/voice/comprehension.ts` directly, and plain `node` fails with `ERR_UNKNOWN_FILE_EXTENSION` on a `.ts` import. `npx tsx` also works but adds ~250-350ms of its own resolution overhead per process, which a multi-run campaign gains nothing from paying.

`<candidate>` is a key from `providers.mjs`'s `CANDIDATES` map. Eight are wired today — `haiku-4.5`, `sonnet-4.5`, `sonnet-4.6`, `sonnet-5`, `opus-5`, `opus-5-fast`, `cerebras-gemma-4-31b` and `cerebras-gemma-4-31b-thinking` — of which the last is what production runs and the one before it is what production ran until native reasoning landed; the Anthropic six are comparison arms. Useful environment variables: `PROMPT_FILE` points `promptio.mjs` at a prompt file other than the live `prompts/voice-speaking.md` (handy for testing an edit before it lands), `ARM` names the output file and shows up in the console banner (`defect.mjs` only; it defaults to `now`), and `CASE_FILTER` restricts the run to cases whose id or `kind` contains the given substring — for example `CASE_FILTER=D4d-en-owner ../../node_modules/.bin/tsx defect.mjs cerebras-gemma-4-31b 1` runs exactly one case once. `STRIP_THINK=1` removes `<think>...</think>` blocks from the content channel before anything reads it, and is for the one arm whose prompt asks for those tags — unset (the default) is what the live prompt needs, since production strips nothing and a literal tag is a defect. See `providers.mjs` above. The six long-transcript cases are each about ten times the size of everything else in the suite: they add ~59k tokens of transcript to a run whose other 31 cases carry about 3k of transcript between them, so a full `defect.mjs` rep now sends on the order of 200k input tokens rather than 140k — and the rest of that is the system prompt, paid 37 times over either way. `CASE_FILTER=D4` runs them together with the six short D4 cases they are the length control for, which is the comparison they exist for; `CASE_FILTER=-long-` runs the six alone. `CASE_FILTER=D10` runs the four untold-consult cases and nothing else — no other case's id contains that string and it is no other family's `kind` — which is the filter to use when the thing being checked is whether the prompt volunteers a pending lookup the room has not been told about; note that `CASE_FILTER=D1` now selects those four alongside the four D1 contamination cases, since the filter matches on `id.includes()` as well as on `kind`. `CONTEXT_ARM` selects how much of production's request each case is sent with, and is documented in its own section below. There used to be a third switch here, `ARCHIE_VOICE_PROMPT_PLACEMENT`, choosing which half of the request the prompt's guidance rode in; production removed the experiment and its assembler with it, so both arms of it are gone from this harness and from the `.env` that documented it. `POOL` and `MIN_GAP_MS` set the concurrency and the floor on the gap between dispatches; both default to what every stored run used and are documented in "Rate limits and pacing" below, which is also where the retry behaviour and the campaign settings for a large run live. Results land in `results/defect-<arm>[-<context arm>]-<candidate>.json` and `results/quality[-<context arm>]-<candidate>.json` respectively; both directories are gitignored scratch, not something to commit.

## Running the full-context arm

```
CONTEXT_ARM=full ARM=<label> ../../node_modules/.bin/tsx defect.mjs <candidate> <reps>
CONTEXT_ARM=full ../../node_modules/.bin/tsx quality.mjs <candidate> <reps>
```

Production's speaking call sends five blocks — `<transcript>`, `<consults>`, `<written>`, `<participants>` and `<capabilities>`. The default arm sends the first two. `CONTEXT_ARM=full` adds the rest.

**There were three arms, and there are now two.** A sixth block, `<situation>`, used to carry a triage gate's verdict for the turn, and `full` sent it while `full-noverdict` sent the same standing blocks with no verdict at all — production's own path whenever that gate failed, timed out or came back unreadable. The gate is gone and `buildSpeakingUserMessage` takes no verdict, so the two arms would now send byte-identical requests under two names, and a comparison between them would be reading sampling noise as a difference. They are one arm, keeping the name of the one whose bytes it still sends; `full-noverdict` is refused by name rather than quietly accepted, so a campaign script carried over from before fails instead of collecting a `full` run under a filename claiming otherwise. `quality.mjs` accepts both arms now for the same reason it used to refuse `full`: what it could not derive was a per-case verdict, and there is no verdict to derive.

**Why an arm and not a default.** The 180 stored rows in `results/defect-trim-*.json` and `results/defect-live-*.json` were collected with transcript-and-consults only, and they are the known-good every later run is compared against. Turning the new blocks on by default would leave every one of those comparisons measuring two changes at once, with nothing in the files to say so — the class of silent invalidation that has already produced two confidently wrong conclusions in this project. So `bare` stays the default and stays byte-identical (asserted, not assumed), the arm's name goes in the output filename and in every row, and an unrecognised `CONTEXT_ARM` throws before anything is billed rather than quietly collecting a bare run under a name that claims otherwise. `full` is asserted to be additive in the strongest available form — the bare bytes plus one fixed suffix, per case, over the whole suite — because "additive" is what makes the bare corpus still readable.

**The stored full-arm rows are not all the same arm, and none of them is today's.** Every stored `full` row also carried a `<situation>` verdict this harness can no longer send, so a `full` run today is a different request from any `full` run in `results/` whatever else matches. On top of that, every `full` and `full-noverdict` row in `results/` predates the capability block being re-observed, so all of them carry the 398-char hand-written five-liner instead of the 1,585-char block production actually sends: they under-represent a live turn by 1,187 characters on exactly one of the three standing blocks — about a seventh of the arm's whole bulk — and neither the row nor the filename says which generation it belongs to, because `-full` means both. The log headers do say. Each driver's banner prints `+<n> chars of standing blocks per case` before it bills anything, so `+7489` in a log header marks a run under the authored block and `+8676` marks one under the observed block. That is the cleanest discriminator there is — a row's own `inputTokens` is the other, since the observed block costs about 305 tokens a case more than the authored one — and it is why the stored logs are left exactly as collected: a banner figure is a true statement about the run that wrote it, and rewriting one would destroy the record of what was actually sent.

The case this matters most for is `D3c-ru-hash-path`, which regressed under the full arm and was never isolated past "one of the three standing blocks, or dilution". Its stored rows were collected with a `<capabilities>` block roughly a quarter the size of today's, so re-running the case now is not a re-run of that experiment — it moves one of the three suspects while testing it, and whichever way the re-run lands, it is being compared against a different arm than the one that produced the regression. Treat a full-arm run under the observed block as a new baseline rather than a continuation of the old one, and read full-against-full comparisons only within a single capability-block generation.

**The two arms.** `bare` (the default) is transcript and consults, nothing else. `full` adds the pinned standing context — the three blocks a live turn also carries. Both drivers accept both.

**What is pinned, and at what size.** Production computes all three standing blocks fresh — the roster off live join/leave events, the written channel off the task's own knowledge log, the capability summary off one model call at join — so a campaign that inherited any of it would stop being reproducible, and two runs six weeks apart would differ by more than what is being measured. `FIXED_CONTEXT` in `promptio.mjs` pins them instead, at the figures measured on a real meeting rather than at whatever reads tidily, because size is the thing under test: `<participants>` renders 99 chars against ~101 measured for four people, and `<written>` 6,955 against ~6,865 measured on a real task's `events.jsonl`. The upper ends — twelve people at ~316, a written channel at its ~24,512-char cap — are a separate arm rather than a better pin, since a run-of-the-mill meeting does not arrive with a capped knowledge log behind it.

`<capabilities>` is the exception to all of that, and it is not pinned at a measurement at all: it **is** the summariser's own observed output, 1,585 characters rendering to 1,616, over five areas of work with twenty specifics indented under them. It used to be five flat lines somebody wrote to hit a measured ~431, which stopped being what production sends the day `prompts/voice-capabilities.md` was restructured into two layers — so it is now re-observed from the real path rather than authored, and its size is simply whatever that output's size is. No ceiling is quoted for it any more: the old ~1,487 at fifteen lines was arithmetic on the flat shape, and nobody has measured a larger deployment's two-layer block.

Altogether the arm adds 8,676 chars of standing blocks to every case — measured, on the 41 cases, after the capability block grew by ~1.2k. Stored rows also carried a verdict sentence worth another 127 to 155 characters; nothing sends one now. Its token cost does not have to be estimated, because the corpus already holds the provider's own count: every stored row carries `inputTokens` straight off the response's `usage`, and `results/defect-b{1,2,3}` and `results/defect-f{1,2,3}` are the same 37 cases under `bare` and under `full` at the same 19,215-char prompt, agreeing to the token across all three reps. **Measured, not modelled:** bare 205,885 input tokens (mean 5,564 a request), full 278,271 (mean 7,521) — **+35%**, which is 1,956 tokens a case for the 7,626 chars those runs sent, i.e. 3.90 chars a token over the standing blocks and 4.32 over a whole bare request. Those two rates are the durable part; the rows they come from are not, because they predate both the observed capability block and several prompt edits.

**Projected from them, and a projection is all it is:** carry those measured rates onto today's 41 cases, today's prompt and the observed block and a bare rep lands near ~245k with a full one near ~338k — **+38%**, at a full-arm mean of ~8.2k tokens a request, which is what the pacing arithmetic in "Rate limits and pacing" and the campaign section below key off. Nothing here has billed that configuration yet, so treat the three absolutes as the right order and the two rates as the measurement; one paced full rep would replace them with counts, and its own rows would say so.

**Do not re-derive any of this from `approxTokens`.** The chars-per-token fit in `long-transcripts.mjs` was fitted on transcripts and says so; applied to a whole request it overstates the billed count by about a third — 378,938 against the 278,271 actually billed for that same full rep. The ~319k / ~419k pair this section used to quote came by that route, and so did the ~10k mean the pacing was sized against, so the older figures ran high rather than low and the gaps derived from them were more conservative than they looked rather than less. `inputTokens` is on every stored row; use it, and keep the char figures for anything that has to hold across a prompt edit — `defect.mjs`'s banner prints one, computed off `userMsg` rather than carried as a literal, before it bills anything.

**Grading the two arms against each other.** Same two properties every campaign in this directory has to keep — separate processes per sample, and the arms interleaved run by run — with `CONTEXT_ARM` as the variable instead of `PROMPT_FILE`. The two `ARM` labels differ by prefix on purpose, so the result files can be globbed apart afterwards without a glob that matches both:

```
cd tools/voice-cases
C=cerebras-gemma-4-31b-thinking  # what production runs; cerebras-gemma-4-31b is the pre-thinking baseline
export POOL=3 MIN_GAP_MS=2000 # <=30 requests/min at ~8.2k tokens each; see "Rate limits and pacing"
mkdir -p logs results
for i in 1 2 3; do
  for ctx in bare full; do
    [[ $ctx == bare ]] && L=b$i || L=f$i
    CONTEXT_ARM=$ctx ARM=$L ../../node_modules/.bin/tsx defect.mjs $C 1 > logs/defect-$ctx-r$i.log 2>&1
  done
  echo "run $i of 3 done (both arms)"
done
BARE=$(cd results && ls defect-b*-$C.json | paste -sd, -)
FULL=$(cd results && ls defect-f*-full-$C.json | paste -sd, -)
../../node_modules/.bin/tsx compare.mjs bare=$BARE full=$FULL
```

Six invocations of 41 cases is 246 billed calls at roughly 1.75M input tokens all told, ~58% of it the full arm's. There used to be a third arm to add here — `full-noverdict`, separating "the standing blocks changed the reply" from "the verdict sentence changed the reply" — and there is no verdict sentence any more, so the loop above is the whole comparison. **This is the campaign that got rate limited**, run at `POOL=5` with no gap: it came back with 32 of 111 rows on the bare arm and 37 of 111 on the full arm carrying nothing but `HTTP 429`. The pacing above is why the loop now exports two variables. The arithmetic: 41 cases at ~338k input tokens per full invocation is ~8.2k tokens a request, so `MIN_GAP_MS=2000` offers at most 30 requests — about 247k tokens — a minute, and `POOL=3` keeps at most ~25k tokens in flight. That costs about 75 seconds a run in dispatch alone, so budget 8-10 minutes for the six. Widen the gap (3000ms is ~165k tokens/minute) if a run still reports rate-limit drops, and remember the account's budget is shared: two overlapping campaigns halve it. These figures are smaller than the ones this section used to carry, and the correction is worth understanding before anyone loosens a gap on the strength of it: the old ~10k mean came from the chars-per-token fit rather than from billed usage, so the gaps sized against it were already more conservative than they claimed. The capability block growing pushed in the other direction but by less. Neither knob above was chosen by this arithmetic anyway — `POOL=3` and `MIN_GAP_MS=2000` are what stopped the 429s in practice, and the arithmetic is here to size the next limit, not to re-open those two.

## Running the multi-turn suite

```
ARM=<name> ../../node_modules/.bin/tsx turns.mjs <candidate> <reps>
```

Same environment variables as `defect.mjs` (`PROMPT_FILE`, `ARM`, `CASE_FILTER` — `CASE_FILTER` matches on the chain id here, since a chain has no single `kind`). Results land in `results/turns-<arm>-<candidate>.json`, one row per turn, in the same shape `defect.mjs` writes. The banner prints the number of billed model calls the invocation is about to make before it makes any of them: **turns x cases x reps**, in the banner's own words, which is 15 calls for one rep of all three chains (6 + 6 + 3).

Two properties of this driver are worth knowing before you use it. Turns inside a chain are serial by construction — each one's request contains the previous one's reply — so a rep is a whole chain re-run, not a re-run of one call, and the cost scales in turns rather than in cases. And the model transport is injectable (`runChain` takes its `call` as an argument), which is what lets `turn-chain.test.ts` exercise the entire chain against canned replies for free. If you write anything new against this harness, keep that seam: a driver that can only be tested by paying for it does not get tested.

**Reps inside one process are near-worthless as evidence, and this is more true of a chain, not less.** At temperature 0 a loop of N reps in a single process is much closer to one sample dressed up as N than to N independent draws (see the section above), and a chain compounds it: every turn after the first is conditioned on a reply drawn from the same correlated distribution, so a whole chain can lock into one behaviour and repeat it. Any real D9 campaign must sample arms as separate, interleaved process invocations, exactly as `campaign3.sh` already does for the single-turn suites — `for i in 1 2 3; do for arm in before after; do ARM=$arm-r$i PROMPT_FILE=... tsx turns.mjs <candidate> 1; done; done` is the shape, and the accumulated `results/turns-*.json` files then go to `compare.mjs` together.

## Running a two-arm campaign

```
./campaign3.sh <candidate> <runs> <armA-name> <armA-prompt-file> <armB-name> <armB-prompt-file>
```

For example, `./campaign3.sh cerebras-gemma-4-31b 5 before /tmp/voice-speaking.before.md after ../../prompts/voice-speaking.md` runs 5 interleaved runs of each arm against Cerebras. Per-run logs land in `logs/defect-<arm>-r<n>.log` and `logs/quality-<arm>-r<n>.log`; per-run quality result JSON is renamed to `results/quality-<arm>-r<n>.json` after each run so successive runs of the same arm do not overwrite each other (`defect.mjs` already names its own output by arm, so no rename is needed there). Once every run has finished, feed the accumulated `results/defect-*.json` files to `compare.mjs` to get a single before/after table. Pacing is inherited by every run, so `POOL=3 MIN_GAP_MS=1500 ./campaign3.sh ...` paces the whole campaign; the script itself sets neither, and the retry in `providers.mjs` applies to every call it makes. Read each run's closing `sample ...` line before reading the table: a run that lost rows to a 429 says so there, and `compare.mjs` will say it again per arm.

**`campaign3.sh` varies the prompt and holds the candidate fixed, which is not always enough.** A change that moves the *request* as well as the prompt needs a candidate per arm, and the native-reasoning change was one: arm A is the prompt that asks for `<think>` tags against the pre-thinking body, arm B is the live prompt against the body production sends now. `campaign-native-think.sh` is that campaign, written out rather than parameterised because it also carries the one switch that belongs to arm A alone (`STRIP_THINK=1`), and a shared flag on a two-arm script is the kind of thing that silently ends up on both. It keeps both standing properties — a process per rep, arms alternating run by run — and is the shape to copy for the next comparison that moves more than the prompt.

**Reps decorrelated across processes can still come back identical, and that is a result, not a failure.** In the native-reasoning campaign all 41 cases were byte-identical across the three separate processes, on both arms — so three reps carried exactly as much evidence as one, and the spread on every per-family rate was zero. The precaution is still right (a correlated sample is invisible until you look, and this same model has produced opposite behaviour across two invocations before), but a run whose reps agree to the byte must be read as **n=1**, and a single case moving between arms must not be read as an effect until its family moves with it.

## Keys

`ANTHROPIC_API_KEY` is read by `providers.mjs` from the **main checkout's** `.env` (`/Users/khmelev/Projects/swc/archie-hq/.env`), not from whichever worktree the harness happens to be running in — this matches how the harness has always resolved this key. `CEREBRAS_API_KEY` is resolved the same way: the main checkout's `.env` wins if it holds the key, and this checkout's own `.env` is the fallback, which is where a worktree-local key such as this one is more likely to actually live, since a worktree does not generally carry its own copy of shared repo secrets. A checkout's `.env` always wins over the ambient environment, so a live campaign resolves its key exactly as it always has and a stale exported value cannot silently redirect one; `process.env` is consulted only where the throw used to be, which is what lets `rate-limit.test.ts` exercise the transport against a stubbed `fetch` with no secrets on disk. Neither function invents a key from nowhere — both throw a clear error naming exactly which file(s) were checked if the key is missing from all of them and from the environment. Nothing in this harness ever prints a key value; if you add logging, keep it that way.

## What this harness deliberately does not keep

No prompt-variant snapshots live in this directory — `compare.mjs` and `campaign3.sh` both expect you to point `PROMPT_FILE` / `COMPARE_PROMPTS` at whatever variant you are testing, saved wherever you like outside this directory, rather than accumulating `voice-speaking.SOMENAME.md` files here. `results/` and `logs/` are run output, gitignored, and safe to delete at any time — nothing in this harness reads its own past output except `compare.mjs`, and only when you name the files explicitly on its command line.
