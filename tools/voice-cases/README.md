# voice-cases

A prompt-regression harness for `prompts/voice-speaking.md` — the system prompt that decides what Archie says out loud in a voice meeting and what it posts to chat instead.

## What it measures

`defect.mjs` runs a 41-case suite (`dcases.mjs`) targeting nine specific defects the prompt has previously shipped with, or could plausibly ship with next: D1 contamination (the transcript brushes against a worked example's topic and the reply leaks that example's identifiers as if they were fact), D2 fabrication (the transcript has no dates/times/ids/figures at all, and the reply invents some anyway), D3 spoken-detail leakage (a hash, path, URL, ticket id or version number reaches the room's ears instead of the chat line), D4 owner's-name-from-transcript (the answer is sitting a line or two up in the conversation, asked in Russian, with an English control for each case), D5 machinery-leak (the transcript holds a genuine unknown that tempts a PM consult, and the spoken half names who or what Archie asks rather than just promising to find out), D6 pending-nag (a PM consult was already acknowledged once, and a later, unrelated turn gets the pending lookup re-announced anyway instead of a plain answer to what was actually asked), D7 insistence-fabrication (pressed directly for that same unanswered consult's value, the reply asserts a specific open-ended answer — a title, a name, a sentence — that nothing sourced, the same defect D2 measures but shaped as prose rather than a number or hash D2's harvester would catch), D8 provenance-denial (asked point-blank whether an earlier answer was real or invented, the reply claims a source that never existed instead of admitting the answer was not sourced), and D10 untold-consult (the same outstanding consult with the acknowledgement **deleted** from the transcript, which is the state production reaches whenever a turn is abandoned before a byte of audio plays: `routeConsult` runs in `answerRoom`'s `finally` however the turn ended, while the transcript receives only what the sink confirms, so the question is out and the room was never told — and the graded behaviour is therefore the exact inverse of D6's, since the reply *must* volunteer the pending lookup rather than suppress it). D6/D7/D8 reconstruct one real live-meeting incident as three prefixes of the same expanding transcript; see the family comment above `DCASES` in `dcases.mjs` for the full incident. D10 is that same incident's first prefix with Archie's own acknowledgement taken out, so that the suite can reach the state the code reaches routinely and D6's fixtures never present, and it has its own family comment further down that file. Each family has Russian and/or English cases so a failure can be told apart from a language-specific gap.

One further defect is measured across families rather than as a family of its own: **a promise of future work with nothing behind it.** The prompt tells this voice to say it will find something out, and gives it exactly one way to make that true — a trailing `PM:` line — so "let me check the logs and I'll get back to you in a second", with no `PM:` line and no consult already in flight, promises an action nobody is taking. `unbackedPromiseCheck` recognises the grammatical act of that commitment (a first-person forward commitment to obtain information) in English and Russian, anchored on grammar rather than vocabulary for the same reason `assertedAnswerCheck` is; `gradeDefect` grades it as a hard failure on D2 only — the fabrication family, where a fabricated future *action* belongs, and where `D2f-invited-promise` exists to measure the distinction rather than to ban the promise — and records it as advisory information on every other family, so the fail definitions the stored result rows were collected under stay intact. `compare.mjs` prints the advisory half.

Six of those 41 cases (`D4g`-`D4l`, built by `long-transcripts.mjs`) are the only ones in this harness that measure **production's real transcript length**. Every other fixture here holds 10 to 30 lines, because the speaking window was three minutes wide when they were written; it is now the whole meeting, bounded by a three-hour backstop, and `TRANSCRIPT_WINDOW_MS` in `meeting.ts` measures real transcript logs at 8,000-10,400 tokens per hour. So the rest of the suite measures the short-transcript case while production runs the long one — and the risk that opens is specific: more context can make a model *worse at finding an answer that is present*, and worse in a way that depends on where the answer sits (Liu et al., "Lost in the Middle": up to a 22-point drop between a fact at the start of a 20k+ token input and the same fact in the middle). The six are therefore two triples rather than two cases — the same question, the same answer and the same ~490-line meeting, with the supplying line near the start, at 49% depth, and four lines above the question — because "does it cope with length" and "does position matter" are different measurements and one case cannot tell them apart. English and Russian are mirrors here, as `D4a`↔`D4d` already are, and are matched on tokens rather than on lines (~9.5k and ~10.2k respectively; Russian costs about 2.43 chars per token against English's 3.17). The filler is hand-written meeting talk rather than generated boilerplate, and its inertness is asserted mechanically by `long-transcript.test.ts` rather than by reading: every `must` regex matches the one supplying line and finds zero matches in the other 489, no near-miss term appears in the filler at all, the three variants are byte-identical apart from the index of one line, and no worked-example identifier is anywhere in the transcript (one would silently disarm the contamination check, since `leakCheck` excuses anything the transcript already contains).

`turns.mjs` runs a second, **multi-turn** suite: `tcases.mjs`'s three `kind: 'D9'` cases, each a chain of turns rather than a single snapshot. Every case in `dcases.mjs` hands the model one transcript and grades one reply, which means none of them can reproduce a failure that only emerges once the agent's *own* prior turns are part of its input — and that is exactly the shape a live meeting produced: asked to look something up, Archie raised a consult, then re-announced that pending consult on every following turn while the room was asking other, answerable questions, then fabricated an answer to the pending question, then claimed it had received that answer from somewhere. The room was not pressing; it had moved on. A D9 chain reproduces that run-up by doing between turns exactly what production does — appending room utterances, calling the model with the real assembly (accumulated transcript plus the `<consults>` block, where a pending consult renders literally as `A: (no answer yet)`), parsing the reply with the real parser, and appending **only the spoken half** as `Archie: ...`, never the `CHAT:` line, never the `PM:` line, never `<think>` content, mirroring `noteOwnAnswer(answer.speech)`. `D9a` (English) and `D9b` (Russian, and a meeting of its own rather than a translation) hold a consult pending across three turns whose answers are sitting in the transcript, a fourth where the room comes back to the original question, and a fifth that challenges the provenance of whatever was just said; `D9c` resolves the consult mid-chain and measures whether the answer is delivered in the agent's own words without naming who or what supplied it.

D9 writes no new detectors, deliberately. Each turn declares `as` — one existing kind or an array of them — and is graded by the same `gradeDefect` through a per-turn pseudo-case carrying that kind plus whatever fields it reads (`subject` for D6/D7, `must` for D4, `detail` for D3), with the failures unioned. Every detector reached that way has been validated across 180 stored result rows; a new one would not be. One semantic in that wiring is load-bearing and easy to get quietly wrong: the pseudo-case's `transcript` — what `fabricationCheck` and `leakCheck` treat as *sourced* — holds the room's utterances only, never Archie's own turns. If the agent invents a value at turn 3, its own line enters the model's input at turn 4, and counting that line as a source would make the same invention look sourced from then on, masking the precise failure the fixture exists to catch. The model-facing transcript is a different string and does contain those lines, because the model has to see what it said.

Two turns are graded differently from the plan this suite was written to, and both departures are recorded in `tcases.mjs` next to the turn: the turn where the room asks the pending question *directly* is graded D7 alone rather than D6+D7 (D6 measures an **unprompted** re-announcement, and when the room asks, some form of "no word yet" is the only honest answer available — `no-update-yet` and `ill-let-you-know-when` would both fail a reply that is behaving perfectly, which is also why `dcases.mjs` grades `D7a-en-readme-pressed` as D7 only), and D9c's delivery turn carries `D4` alongside `D5`/`D8` because `gradeDefect` reads `must` under `kind === 'D4'` and nowhere else, so a `must` without it would have been a silently dead assertion.

Ten files here run under the repo's own `npm test` (vitest, `tools/**/*.test.ts`), and all ten exist because an instrument nobody tested has already produced confidently wrong conclusions in this directory. `unbacked-promise.test.ts` asserts both halves of the promise detector — every phrasing that must fire and every phrasing that must not — in English and in Russian. `user-message.test.ts` pins the request assembly byte-for-byte against the hand-written copy it replaced. `turn-chain.test.ts` drives the whole D9 chain machinery against a **stub transport**: canned replies, zero model calls, and therefore zero cost — a re-announcement at turn 2 must produce a `REPETITION` fail at turn 2, a clean chain must produce zero fails, a fabrication at turn 4 must be caught at turn 4 *and again at turn 5 when the model repeats it*, and the `CHAT:`/`PM:`/`<think>` exclusions must hold. The room-only-transcript rule above is proved by a different test than that repeat, and the distinction is worth keeping straight: turns 4 and 5 are graded D7, and `assertedAnswerCheck` never reads the pseudo-case's transcript at all, so that pair would catch the repeat whatever the transcript held. The rule's own test overrides those two turns to `D2` — `fabricationCheck` is the detector that does read it — and pairs the result with a counterfactual that re-grades the same turn-5 reply against a transcript carrying Archie's own turn-4 line and watches the failure vanish. The Russian half is not optional in any of them. Three detectors in `defect.mjs` (`assertedAnswerCheck`, `PROVENANCE_CLAIM_RU`, and `pendingNagCheck`'s subject-anchored tier) silently never fired on Russian input for an unknown period because JS's `\b` and `\w` are ASCII-only, and in all three cases the only thing that caught it was executing the regex against an ordinary Russian phrasing — the third of them was still being described in a comment as *working* while `Я смотрю таблицу в ClickHouse.` produced no hit at all. `long-transcript.test.ts` is the fourth, and it exists because the inertness of ~490 lines of filler cannot be established by reading them: it asserts the sizes, the byte-identity of the three variants, that every `must` regex matches the supplying line and nothing else in the transcript, that a faithful reply grades completely clean and a reply that never found the answer fails once per fact, and that the Russian `must` groups fire on eight ordinary Russian phrasings — bounded with `(?<!\p{L})`/`(?!\p{L})` under `u`, with the ban on `\b` and `\w` asserted rather than left as a convention. `triage.test.ts` is the fifth: it drives the whole triage arm against canned verdicts at zero cost, and cross-checks this harness's copies of production's triage constants against `comprehension.ts`'s own source. Four of its suites were added with the context arm and the two preamble checks, and each of them exists because of something this harness scored **clean** while a real meeting failed on it. The bare arm's byte-identity is pinned per case *through the driver* rather than through the builder, because the defect was in the driver: `triage.mjs` called `triageUserMsg` with two arguments and no arm wiring at all, so no triage row had ever carried `<capabilities>` and every stored row ran the no-list branch of the prompt. Both preamble checks are asserted to fire on the real incident's own two sentences — `"Let me check with the PM."` and a preamble that read the capability list out — and asserted **silent on the four preambles the last real run actually produced** (`results/triage-tgfix-r{1,2,3}`, three reps, identical in all three), because two of those four restate the question at length, which is what holding the floor looks like, and a check that cannot tell restating from answering fails a gate that is behaving perfectly. The addressed-language derivation is pinned against all sixteen single-language fixtures' declared `ru` and asserted to differ on exactly the one mixed case — and separately on `Дмитрий: Archie?`, which is the adversarial minimum: seven Cyrillic letters of name against six Latin ones of utterance, so a rule that measured the raw line would read 0.54 Cyrillic and call a short English address Russian. Both preamble checks, the arm wiring, the per-arm expectation, the guard tying the capability groups to the pinned list, and the Cyrillic bounding were mutation-checked one at a time: fifteen mutations, each caught by a named test. A later suite does the same for `internalIdLeakCheck`, the id half of `MACHINERY`: known-bad and known-good stated one line apart in English and in Russian, both tiers exercised, the shipped pattern read out of `defect.mjs`'s own source and asserted free of `\b` and `\w`, and the failure graded **through the driver** as well as through the detector, because a check that is never called grades everything clean and no unit test of the check can see that. `context-arm.test.ts` is the sixth, and four of its assertions matter more than the rest. It pins the bare arm's byte-identity to the two-argument call every stored row was collected under, for every case in both suites — the arm is additive precisely so that corpus stays comparable, and "additive" is a claim about bytes. And it pins `D6a-en-weather` to `elsewhere` **by name**, because the obvious derivation would hand that fixture the sentence that causes the defect it exists to catch: it has a README consult outstanding while the room asks about the weather, so an unguarded "unanswered consult means `pending`" rule would end its message, one line above generation, with "you have already sent what you have just been asked onward, and nothing has come back yet" — which from there reads close to an instruction to say *I am still looking into the readme*. The third and fourth were added after `FAMILY_VERDICT.D1` shipped a `room` verdict on a family built to supply nothing, which cost two fixtures three runs of silence: the corrected verdict of at least one case in **every** family is now written out by id rather than looped over the table the derivation itself reads — the pinned set is asserted to cover every family, so a tenth fails the test until one of its cases is pinned too — and the contradiction check is tested from both sides, silent on all 37 fixtures under all three arms and firing on each of the four contradictions it names, every one of them built by mis-deriving a real fixture rather than a mock. The rest of the file asserts that the ~8,700-character pinned context is inert (nothing `fabricationCheck` would read as an invented value, and zero collisions with any fixture's `must`/`detail`/`subject` regexes), which is not something ~8,700 characters of plausible prose can be established to be by reading them. `rate-limit.test.ts` is the seventh: it drives the whole retry path against a stubbed `fetch` on a driven clock — a 429 then a success producing a row that grades, `Retry-After` honoured as a floor, a 400 failing on its first attempt, both caps binding independently of each other, jitter asserted as a spread rather than a value, and `POOL` moving a driver's real concurrency. Every wait in it is fake-timer time, so the 75-second cap is exercised in milliseconds and nothing is billed. `sample-accounting.test.ts` is the eighth, and the fixture at its centre is the campaign that prompted this file's accounting: 111 rows with 32 lost to the TPM limit, which must come out as `79/111 rows graded` under a banner, never as a table of rates. It also pins the two mistakes on the other side of that line — an errored row must not be counted as a failing reply by `quality.mjs`'s pass count, and a chain that ended early on a transport error must not be counted as a chain that failed. `pending-nag.test.ts` is the ninth, and it exists because the Russian half of `pendingNagCheck` reported clean on a defect it could not see: `D6c-ru-weather` produced the same unprompted re-announcement its English twin fails on — *"но как только получу ответ по репозиторию, сразу скажу и то, и другое"* — and passed, because `STALL_GENERIC_RU` had no counterpart to `ill-let-you-know-when`. A false negative in the instrument is worse than a failing case, so this file pins both halves of every Russian entry: the observed phrasing and its variants firing, honest declines and a genuinely-arrived answer staying silent, and the D6/D7 split asserted from both sides — the same words are a re-announcement on a D6 turn and the only honest answer on a D7 turn, which is why the English tier already fires on a passing `D7a` row. It also pairs the entries by name, so the next English-only addition fails a test rather than quietly leaving Russian short, and it carries the Cyrillic-bounding check in its strongest available form: it takes the shipped regex, substitutes `\b` for every Unicode bound, and asserts the result goes dead on an ordinary Russian sentence. `untold-consult.test.ts` is the tenth, and it guards the seam between the two families that measure opposite behaviour over the same outstanding consult: the observed nag — *"I'll let you know as soon as I have that first line from the readme"*, and its Russian counterpart out of `results/defect-post-r{1,2,3}` — must fail `D6a`/`D6c` on `REPETITION` and grade **completely clean** on `D10a`/`D10c`, same words, same detector suite, one deleted transcript line between them. The rest of the file pins what makes that safe rather than lucky: `pendingNagCheck` is unreachable from a D10 row (asserted through `info.nag` being populated on one and absent on the other, not merely through the failure list), a `CHAT:` or `PM:` line does not satisfy a `mustSay` group because it does not tell a room anything, a `SILENCE` reply fails on the protocol check alone rather than three times over for one behaviour, and the four fixtures' derived verdicts are pinned by id. Two of its assertions are mutations rather than expectations: handing the same groups over as `must` must make `deriveVerdict` throw — which is the whole reason the field is spelled differently — and an unsatisfiable group must make a correct reply fail, in either position, so the rest of the file cannot be passing for the wrong reason.

`quality.mjs` runs a separate, broader 16-case suite (`cases.mjs`) covering general behaviour: narrowed questions, withdrawn questions, prompt injection (English and Russian), code-switching, when to stay silent versus when ambiguity itself is not a reason to go silent, leading with the answer, numbers spoken as words, and more.

All three suites grade mechanically — regex-based detectors in `defect.mjs` (`gradeDefect`, which `turns.mjs` reuses once per kind per turn) and `quality.mjs` (`grade`), never an LLM judge — and all of them print exactly what a detector flagged, so a rubric can be audited against the raw reply text rather than trusted blind.

`providers.mjs` is the wire adapter. It calls each provider with bare `fetch` and manual SSE parsing, deliberately not an SDK wrapper, because production (`src/voice/comprehension.ts`) does the same and this harness has to measure that exact path. It wires two providers, Anthropic and Cerebras, and seven candidates across them; the one production actually runs is `cerebras-gemma-4-31b` (Cerebras `gemma-4-31b`); the Anthropic candidates are comparison arms only. That adapter mirrors `comprehension.ts`'s request shape exactly — same model id, same endpoint, same temperature, same message framing — so a defect measured here is a defect production would actually hit.

`pacing.mjs` decides how hard a campaign pushes the API and what happens when the API pushes back: the `POOL` and `MIN_GAP_MS` knobs, the 429 retry policy (`Retry-After` honoured as a floor, equal-jitter exponential backoff otherwise, a cap on attempts and a cap on total wait), and the per-process tally of what actually went on the wire. `providers.mjs`'s `runCall` is its only caller for the retry and the pace; the drivers call `poolSize()` and print the tally. It exists because a campaign of 6 invocations x 37 cases at `POOL = 5` lost a third of its rows to `HTTP 429 "Tokens per minute limit exceeded"` and the harness had no retry, no backoff and no `Retry-After` handling anywhere. Every default reproduces the dispatch pattern every stored row was collected under, so nothing changes unless an environment variable says so — see "Rate limits and pacing" below.

`emitter.mjs` imports the real `parseReply`, `SentenceEmitter`, `stripThinkBlocks` and `TAIL_MARKERS` straight from `comprehension.ts` and adapts their shape to what this harness's graders consume — it used to be a hand-copied port instead, which drifted from production three times in two days (a missing `PM:` marker, missing `<think>` handling, a missing `LEAVE:` marker) before those four were exported for exactly this purpose. Because `comprehension.ts` is TypeScript, everything that reaches it — `defect.mjs`, `quality.mjs`, `turns.mjs`, `compare.mjs`, `providers.mjs`, and now `promptio.mjs` as well — has to run under `tsx`, not plain `node`; see "Running one arm" below.

`promptio.mjs` imports the request half from the same place, for the same reason: `assembleSpeakingRequest` is exported from `comprehension.ts`, and both `system()` and `userMsg()` take their half from it — replacing what this file used to carry as a hand-written "faithful port" of production's transcript framing and its `consultsBlock`. Because both halves come from the one production assembler, the harness sends the same bytes as a live meeting under **either** placement arm; `user-message.test.ts` asserts that identity for both. `userMsg()`'s fourth argument is this turn's triage verdict, which production runs the gate to get and then hands to the speaking call as a `<situation>` block of one sentence; it defaults to undefined for the same reason `context` does — every row already in `results/` was collected with no such block — and a case measuring a turn that follows a verdict passes it. The gate's own request never carries it, which is what `triageUserMsg()` is for.

`context-arm.mjs` decides **how much of production's request a campaign sends**. Production's speaking call carries six blocks; until this file existed the drivers sent two of them (`defect.mjs` called `userMsg(c.transcript, c.consults)`, `quality.mjs` passed the transcript alone), so the suite could not see the effect of `<written>`, `<participants>`, `<capabilities>` or the per-turn `<situation>` at all — it measured a prompt written for a request it never sent. The fix is an arm rather than a default, because 180 stored rows were collected without those blocks and are the known-good every later run is read against: `CONTEXT_ARM=bare` is the default and is byte-identical to those rows, and `full` / `full-noverdict` are selected explicitly. See "Running the full-context arm" below.

`compare.mjs` offline-regrades stored result files under one current rubric and prints a before/after table by case and by defect family, so two arms collected at different times (possibly under different versions of the detectors) are still judged fairly against each other. It regrades `turns.mjs` rows too: a chain turn is filed under `<case id>#T<n>` and its pseudo-cases are a pure function of the fixture, so a stored row re-grades from the fixture alone exactly as a single-turn row does.

`sampling.mjs` is what every report says about its own completeness: rows graded, rows dropped, the reason class of each drop, and — above a threshold — a banner saying the arm's rates must not be read. All five report sites use it (`compare.mjs`, `defect.mjs`, `quality.mjs`, `turns.mjs`, `triage.mjs`), so a rate-limited campaign says so in the driver's own output while you are still watching it, not three commands later. See "Never silently short a sample" below for the threshold and its reasoning.

`campaign3.sh` runs an arm-interleaved two-arm campaign: `defect.mjs` and `quality.mjs` for arm A, then for arm B, repeated for N runs, so each pair of runs sits adjacent in time rather than one arm running to completion before the other starts.

## Why runs must be decorrelated across processes

At temperature 0, repetitions inside a single process are correlated samples — in a controlled comparison, two invocations of the same prompt and transcript produced opposite behaviour (5/5 refusals versus 8/8 answers) while the reps *inside* each of those invocations were byte-identical to each other. A run of N reps inside one process is therefore much closer to a single sample dressed up as N than to N independent draws. `campaign3.sh` exists to fix this: each arm is sampled as several separate process invocations rather than one invocation with several reps, and the two arms alternate run-by-run (A, B, A, B, ...) rather than A running to completion before B starts, because API latency and behaviour drift over a measurement window and interleaving keeps that drift from being mistaken for a difference between the arms. If you write a new script against this harness, keep both properties: separate processes per sample, and interleaved arms.

## Rate limits and pacing

The limit this harness actually hits is **tokens per minute**, not requests in flight. A 6-invocation campaign of 37 cases at `POOL = 5` — an invocation being 205,885 input tokens bare and 278,271 full, as the paced re-run of that same case set later billed it end to end — came back with 32 of 111 rows on one arm and 37 of 111 on the other carrying nothing but `HTTP 429 "Tokens per minute limit exceeded - too many tokens processed."`, and every one of those rows cost a sample.

**A 429 is now retried rather than lost.** `Retry-After` is honoured when the response carries it — as a floor, never shortened, with up to 1s of random spread on top so five pooled workers that all received the same header do not wake on the same tick — and when it does not, the fallback is exponential backoff with *equal* jitter: half the nominal delay plus a random half. Equal rather than full jitter on purpose: a draw near zero would retry straight back into a token bucket that is still empty, spend another request's worth of limit and come back 429 again. The schedule is 5s, 10s, 20s, 40s.

**Only a 429 is retried.** A 400 means the same request will fail the same way for ever, so `context_length_exceeded` or a malformed body still fails on its first attempt; retrying it five times would buy five times the wait for the identical answer. 5xx and 529-overloaded are arguably "later" too and are still not retried, because the only failure mode measured here in bulk is the TPM 429 and broadening the retryable set on speculation turns genuine breakage into slow breakage. `isRateLimited` in `pacing.mjs` is the one-line change for whoever measures a case for another status.

**It is bounded, twice.** At most 5 attempts (one plus four retries) and at most 75 seconds of total sleeping per call — both stated with their reasoning in `pacing.mjs`'s `RETRY`. The 75s is the load-bearing number: a tokens-per-minute bucket is a 60-second window, so a cap under ~60s would give up while the only thing needed was to wait the window out, and 75s is one window plus slack and no more. The two caps meet by construction (the schedule's own total reaches 75s exactly as the fifth attempt is refused), so neither is decoration. Past those bounds the row is lost — but it says so: its error carries `gave up after N attempt(s) and Xs of backoff`, and the run's accounting classes it as `rate-limit` rather than as an unexplained failure.

**Retrying does not double-count.** Each attempt is instrumented separately, so a row's `ttft`/`complete`/token counters belong to the attempt that produced it and never include the backoff or a refused attempt's numbers — which matters because this is a latency harness before it is anything else. What a retry does add is *requests*, and those are reported separately: every driver ends with a `wire:` line giving requests sent, retries, rate-limited responses, seconds slept and rows given up on. `requests` above `rows graded` is a retried run, not a double-counted one. The pre-run banners in `turns.mjs` and `triage.mjs` now say **at least** N billed calls for the same reason.

**Two knobs, both defaulting to today's behaviour.** `POOL` sets the worker-pool size — 5 in `defect.mjs`, 3 in `turns.mjs`, 4 in `triage.mjs` when unset, which is what every stored row was collected under (`quality.mjs` is serial by construction and has no pool). `MIN_GAP_MS` sets a floor on the gap between dispatches, defaulting to 0, i.e. no pacing at all. A malformed value for either throws before anything is billed rather than being silently ignored.

Use both, because they bound different things. A pool bounds how many requests are in flight; it only bounds the *token* rate if every request is the same size and takes the same time, and neither holds here — the six long-transcript cases carry ~8k tokens of transcript each (billed, off `inputTokens`: ~8.0k English, ~7.8k Russian) while the other 31 carry ~1.7k between them, so on the full arm five workers can have ~72k tokens or ~33k outstanding depending on which cases happen to be adjacent in the job list, and the pool refills the instant a call returns, which makes a fast model a much higher request rate than a slow one at the same nominal concurrency. A floor on the inter-dispatch gap bounds requests per minute directly (`60000 / gap`), and requests per minute times mean tokens per request is the quantity the limit is written in.

Sizing it is arithmetic, not taste. For a `defect.mjs` rep of all 41 cases on the full arm at ~338k input tokens, mean request size is ~8.2k tokens, so a limit of L tokens/minute allows about `L / 8200` requests per minute and the gap wants to be about `60000 / (L / 8200)` ms. Both figures come off the provider's own `usage` rather than a chars-per-token fit — see "What is pinned, and at what size" for the measurement and for why the fit reads about a third high here. Halve that budget if two invocations of the campaign script overlap, and remember the retry is a second line of defence, not the plan: a run that spends 40 seconds asleep per row is a run that should have been paced.

## Never silently short a sample

`compare.mjs` skipping a row that carries `error` is right — there is no reply text to re-grade, and grading it as a failure would invent a defect out of a rate limit. Doing it invisibly is what nearly produced a set of quoted findings from a table whose per-case scores were out of 1, 2 or 3 reps with nothing anywhere saying so.

So every report now states, unconditionally and before any rate: rows graded, rows dropped, and the reason class of each drop (`rate-limit`, `timeout`, `http-4xx`, `http-5xx`, `stream-error`, `unknown-case`, `other`). Unconditionally matters — a line that appears only when something is wrong teaches a reader that its absence means nothing was checked. `unknown-case` is in that list because it was the *other* silent drop: a stored row whose case id no longer exists in the fixture set was skipped with no more noise than an errored one.

Above a threshold the arm is fenced off with a full-width banner reading `INCOMPLETE SAMPLE — DO NOT READ RATES OFF THIS ARM`, printed to stderr as well as stdout so a campaign that redirects stdout to a per-run log still shows the alarm on the terminal while it is running. The threshold is **5% of an arm's rows**, plus a second trigger with no fraction attached: **any case that was attempted and produced no graded row at all**. The reasoning for both is in `sampling.mjs`'s `INCOMPLETE_FRACTION` — in short, drops here are close to missing-at-random with respect to what is being measured (a TPM 429 depends on tokens in flight, not on what the reply would have said), so the harm is a rate claiming a denominator it does not have; at 5% with 3 reps per case roughly one case in seven is scored out of 2 instead of 3, which the stated counts let a reader discount, and past that the shortfall is the headline rather than a caveat. A case with no graded row prints as ` - ` in the table, which reads as "nothing to see" rather than "silently lost", and that is worth a banner however small the overall fraction is.

Three related counts were wrong in the other direction and are fixed here: `quality.mjs` counted a transport error as a quality failure outright, and `defect.mjs`/`turns.mjs` kept an errored row in the denominator while it could never reach the numerator. All three now compute over graded rows only, and a chain that ended early on an errored turn is reported as a dropped chain rather than as a chain that failed — `runChain` stops at the error, so its later turns never happened.

## Running one arm

```
../../node_modules/.bin/tsx defect.mjs <candidate> <reps>
../../node_modules/.bin/tsx quality.mjs <candidate> <reps>
```

Run under `tsx`, not plain `node` — `emitter.mjs` imports `src/voice/comprehension.ts` directly, and plain `node` fails with `ERR_UNKNOWN_FILE_EXTENSION` on a `.ts` import. `npx tsx` also works but adds ~250-350ms of its own resolution overhead per process, which a multi-run campaign gains nothing from paying.

`<candidate>` is a key from `providers.mjs`'s `CANDIDATES` map. Seven are wired today — `haiku-4.5`, `sonnet-4.5`, `sonnet-4.6`, `sonnet-5`, `opus-5`, `opus-5-fast` and `cerebras-gemma-4-31b` — of which only the last is what production runs; the rest are comparison arms. Useful environment variables: `PROMPT_FILE` points `promptio.mjs` at a prompt file other than the live `prompts/voice-speaking.md` (handy for testing an edit before it lands), `ARM` names the output file and shows up in the console banner (`defect.mjs` only; it defaults to `now`), and `CASE_FILTER` restricts the run to cases whose id or `kind` contains the given substring — for example `CASE_FILTER=D4d-en-owner ../../node_modules/.bin/tsx defect.mjs cerebras-gemma-4-31b 1` runs exactly one case once. `ARCHIE_VOICE_PROMPT_PLACEMENT` selects which half of the request the prompt's guidance rides in: unset or `guidance-first` is what production sends (the whole prompt as the system message, data in the user message), and `data-first` sends only the prompt's opening statement of role as the system message and moves the guidance to the end of the user message, after every data block. It is read by production's own assembler, not by this harness, so both arms are the bytes a live meeting would send — see `SpeakingPlacement` in `comprehension.ts` for why that experiment exists and what its result is not allowed to be confounded with. Pair it with `ARM` so the two arms land in different result files: `ARM=data-first ARCHIE_VOICE_PROMPT_PLACEMENT=data-first ... tsx defect.mjs cerebras-gemma-4-31b 1`. The six long-transcript cases are each about ten times the size of everything else in the suite: they add ~59k tokens of transcript to a run whose other 31 cases carry about 3k of transcript between them, so a full `defect.mjs` rep now sends on the order of 200k input tokens rather than 140k — and the rest of that is the system prompt, paid 37 times over either way. `CASE_FILTER=D4` runs them together with the six short D4 cases they are the length control for, which is the comparison they exist for; `CASE_FILTER=-long-` runs the six alone. `CASE_FILTER=D10` runs the four untold-consult cases and nothing else — no other case's id contains that string and it is no other family's `kind` — which is the filter to use when the thing being checked is whether the prompt volunteers a pending lookup the room has not been told about; note that `CASE_FILTER=D1` now selects those four alongside the four D1 contamination cases, since the filter matches on `id.includes()` as well as on `kind`. `CONTEXT_ARM` selects how much of production's request each case is sent with, and is documented in its own section below. `POOL` and `MIN_GAP_MS` set the concurrency and the floor on the gap between dispatches; both default to what every stored run used and are documented in "Rate limits and pacing" below, which is also where the retry behaviour and the campaign settings for a large run live. Results land in `results/defect-<arm>[-<context arm>]-<candidate>.json` and `results/quality[-<context arm>]-<candidate>.json` respectively; both directories are gitignored scratch, not something to commit.

## Running the full-context arm

```
CONTEXT_ARM=full ARM=<label> ../../node_modules/.bin/tsx defect.mjs <candidate> <reps>
CONTEXT_ARM=full-noverdict ARM=<label> ../../node_modules/.bin/tsx defect.mjs <candidate> <reps>
CONTEXT_ARM=full-noverdict ../../node_modules/.bin/tsx quality.mjs <candidate> <reps>
```

Production's speaking call sends six blocks — `<transcript>`, `<consults>`, `<written>`, `<participants>`, `<capabilities>`, and a `<situation>` carrying the triage gate's verdict for this turn. The default arm sends the first two. `CONTEXT_ARM` adds the rest.

**Why an arm and not a default.** The 180 stored rows in `results/defect-trim-*.json` and `results/defect-live-*.json` were collected with transcript-and-consults only, and they are the known-good every later run is compared against. Turning the new blocks on by default would leave every one of those comparisons measuring two changes at once, with nothing in the files to say so — the class of silent invalidation that has already produced two confidently wrong conclusions in this project. So `bare` stays the default and stays byte-identical (asserted, not assumed), the arm's name goes in the output filename and in every row, and an unrecognised `CONTEXT_ARM` throws before anything is billed rather than quietly collecting a bare run under a name that claims otherwise.

**The stored full-arm rows are not all the same arm.** Every `full` and `full-noverdict` row in `results/` predates the capability block being re-observed, so all of them carry the 398-char hand-written five-liner instead of the 1,585-char block production actually sends: they under-represent a live turn by 1,187 characters on exactly one of the three standing blocks — about a seventh of the arm's whole bulk — and neither the row nor the filename says which generation it belongs to, because `-full` means both. The log headers do say. Each driver's banner prints `+<n> chars of standing blocks per case` before it bills anything, so `+7489` in a log header marks a run under the authored block and `+8676` marks one under the observed block. That is the cleanest discriminator there is — a row's own `inputTokens` is the other, since the observed block costs about 305 tokens a case more than the authored one — and it is why the stored logs are left exactly as collected: a banner figure is a true statement about the run that wrote it, and rewriting one would destroy the record of what was actually sent.

The case this matters most for is `D3c-ru-hash-path`, which regressed under the full arm and was never isolated past "one of the three standing blocks, or dilution". Its stored rows were collected with a `<capabilities>` block roughly a quarter the size of today's, so re-running the case now is not a re-run of that experiment — it moves one of the three suspects while testing it, and whichever way the re-run lands, it is being compared against a different arm than the one that produced the regression. Treat a full-arm run under the observed block as a new baseline rather than a continuation of the old one, and read full-against-full comparisons only within a single capability-block generation.

**The three arms.** `bare` (the default) is transcript and consults, nothing else. `full` adds the pinned standing context and a per-case `<situation>` verdict. `full-noverdict` adds the same standing context with no verdict at all — not a control but an arm in its own right, because `runTriageGate` returns `null` on every call that fails, times out on its deadline or comes back unreadable, and `null` renders no block whatsoever. That is production's path on every degraded turn. `quality.mjs` accepts `bare` and `full-noverdict` and rejects `full`: `cases.mjs` declares no consults and no defect family, so there is nothing there to derive a verdict from, and inventing one in the driver is the one thing this arm exists not to do.

**What is pinned, and at what size.** Production computes all three standing blocks fresh — the roster off live join/leave events, the written channel off the task's own knowledge log, the capability summary off one model call at join — so a campaign that inherited any of it would stop being reproducible, and two runs six weeks apart would differ by more than what is being measured. `FIXED_CONTEXT` in `promptio.mjs` pins them instead, at the figures measured on a real meeting rather than at whatever reads tidily, because size is the thing under test: `<participants>` renders 99 chars against ~101 measured for four people, and `<written>` 6,955 against ~6,865 measured on a real task's `events.jsonl`. The upper ends — twelve people at ~316, a written channel at its ~24,512-char cap — are a separate arm rather than a better pin, since a run-of-the-mill meeting does not arrive with a capped knowledge log behind it.

`<capabilities>` is the exception to all of that, and it is not pinned at a measurement at all: it **is** the summariser's own observed output, 1,585 characters rendering to 1,616, over five areas of work with twenty specifics indented under them. It used to be five flat lines somebody wrote to hit a measured ~431, which stopped being what production sends the day `prompts/voice-capabilities.md` was restructured into two layers — so it is now re-observed from the real path rather than authored, and its size is simply whatever that output's size is. No ceiling is quoted for it any more: the old ~1,487 at fifteen lines was arithmetic on the flat shape, and nobody has measured a larger deployment's two-layer block.

Altogether the arm adds 8,676 chars of standing blocks to every case, and 8,803 to 8,831 with the verdict sentence — measured, on the 41 cases, after the capability block grew by ~1.2k. Its token cost does not have to be estimated, because the corpus already holds the provider's own count: every stored row carries `inputTokens` straight off the response's `usage`, and `results/defect-b{1,2,3}` and `results/defect-f{1,2,3}` are the same 37 cases under `bare` and under `full` at the same 19,215-char prompt, agreeing to the token across all three reps. **Measured, not modelled:** bare 205,885 input tokens (mean 5,564 a request), full 278,271 (mean 7,521) — **+35%**, which is 1,956 tokens a case for the 7,626 chars those runs sent, i.e. 3.90 chars a token over the standing blocks and 4.32 over a whole bare request. Those two rates are the durable part; the rows they come from are not, because they predate both the observed capability block and several prompt edits.

**Projected from them, and a projection is all it is:** carry those measured rates onto today's 41 cases, today's prompt and the observed block and a bare rep lands near ~245k with a full one near ~338k — **+38%**, at a full-arm mean of ~8.2k tokens a request, which is what the pacing arithmetic in "Rate limits and pacing" and the campaign section below key off. Nothing here has billed that configuration yet, so treat the three absolutes as the right order and the two rates as the measurement; one paced full rep would replace them with counts, and its own rows would say so.

**Do not re-derive any of this from `approxTokens`.** The chars-per-token fit in `long-transcripts.mjs` was fitted on transcripts and says so; applied to a whole request it overstates the billed count by about a third — 378,938 against the 278,271 actually billed for that same full rep. The ~319k / ~419k pair this section used to quote came by that route, and so did the ~10k mean the pacing was sized against, so the older figures ran high rather than low and the gaps derived from them were more conservative than they looked rather than less. `inputTokens` is on every stored row; use it, and keep the char figures for anything that has to hold across a prompt edit — `defect.mjs`'s banner prints one, computed off `userMsg` rather than carried as a literal, before it bills anything.

**The verdict is derived, not hand-labelled.** `deriveVerdict` in `context-arm.mjs` reads what each fixture already declares. An outstanding consult that the turn is actually about is `pending`; an outstanding consult the turn is *not* about is `elsewhere`; otherwise the family's construction decides (`D3`/`D4` present-by-construction → `room`, `D1`/`D2`/`D5` absent-by-construction → `outside`); an unknown family throws rather than silently sending nothing. Five cases override the family rule with a `triage` field of their own and each says why beside its transcript. The distribution over the 41 cases is 19 `room`, 10 `outside`, 5 `pending`, 7 `elsewhere`, and the driver's banner prints it before it bills anything.

**The test for a family entry is where the answer has to come from, never whether the topic appears.** `D1` read `room` for three stored full-arm runs on the strength of the transcript brushing against the worked example's subject, and it was wrong: D1 is the contamination family, the identifiers are absent by construction, and `D1a`/`D1b` were the only two cases the full arm failed and the bare arm did not — 3 runs out of 3, both `PROTOCOL: SILENCE while somebody was waiting`, with the reply's own `<think>` block spending its whole budget trying to reconcile a `room` verdict with a window holding no cause. Every entry now records what an audit against its fixtures' own declarations concluded, and `verdictContradictions` refuses at derivation time — before the banner, before anything is billed — a verdict the fixture denies: `room` where an outstanding consult about this turn refutes it, `pending` where nothing is outstanding, anything but `room` where a `must` or `detail` group matching the transcript says the room supplied it, and a derived `room` with no source to point at. What is deliberately left unchecked (`outside` against `elsewhere`, `pending`'s same-question requirement, agreement with the real gate) is listed with its reasoning in that function's doc.

**Why `pending` is guarded.** The rule this would obviously have been — an unanswered consult means `pending` — is actively dangerous on `D6a-en-weather`, and that is the case the guard exists for. Full reasoning is in `deriveVerdict`'s doc and pinned by name in `context-arm.test.ts`; the short version is that the fixture has a README consult outstanding while the room asks about the weather, so `pending` would put "nothing has come back yet" one line above generation on the one fixture whose entire purpose is catching *I am still looking into the readme*.

**Grading the two arms against each other.** Same two properties every campaign in this directory has to keep — separate processes per sample, and the arms interleaved run by run — with `CONTEXT_ARM` as the variable instead of `PROMPT_FILE`. The two `ARM` labels differ by prefix on purpose, so the result files can be globbed apart afterwards without a glob that matches both:

```
cd tools/voice-cases
C=cerebras-gemma-4-31b        # or haiku-4.5; these are the two production can select
export POOL=3 MIN_GAP_MS=2000 # <=30 requests/min at ~8.2k tokens each; see "Rate limits and pacing"
mkdir -p logs results
for i in 1 2 3; do
  for ctx in bare full; do
    [[ $ctx == bare ]] && L=b$i || L=f$i
    CONTEXT_ARM=$ctx ARM=$L ../../node_modules/.bin/tsx defect.mjs $C 1 > logs/defect-$ctx-r$i.log 2>&1
  done
  echo "run $i of 3 done (both arms)"
done
BARE=$(cd results && ls defect-b*-$C.json | paste -sd, -)
FULL=$(cd results && ls defect-f*-full-$C.json | paste -sd, -)
../../node_modules/.bin/tsx compare.mjs bare=$BARE full=$FULL
```

Add a third arm by putting `full-noverdict` in the `for ctx` list with `L=n$i` and globbing `defect-n*-full-noverdict-$C.json`; that separates "the standing blocks changed the reply" from "the verdict sentence changed the reply", which one comparison cannot tell apart. Six invocations of 41 cases is 246 billed calls at roughly 1.75M input tokens all told, ~58% of it the full arm's. **This is the campaign that got rate limited**, run at `POOL=5` with no gap: it came back with 32 of 111 rows on the bare arm and 37 of 111 on the full arm carrying nothing but `HTTP 429`. The pacing above is why the loop now exports two variables. The arithmetic: 41 cases at ~338k input tokens per full invocation is ~8.2k tokens a request, so `MIN_GAP_MS=2000` offers at most 30 requests — about 247k tokens — a minute, and `POOL=3` keeps at most ~25k tokens in flight. That costs about 75 seconds a run in dispatch alone, so budget 8-10 minutes for the six. Widen the gap (3000ms is ~165k tokens/minute) if a run still reports rate-limit drops, and remember the account's budget is shared: two overlapping campaigns halve it. These figures are smaller than the ones this section used to carry, and the correction is worth understanding before anyone loosens a gap on the strength of it: the old ~10k mean came from the chars-per-token fit rather than from billed usage, so the gaps sized against it were already more conservative than they claimed. The capability block growing pushed in the other direction but by less. Neither knob above was chosen by this arithmetic anyway — `POOL=3` and `MIN_GAP_MS=2000` are what stopped the 429s in practice, and the arithmetic is here to size the next limit, not to re-open those two.

Both `ARCHIE_VOICE_PROMPT_PLACEMENT` arms work under all three context arms. `<situation>` lands in a different position in each — last of the data either way, which under `data-first` means ahead of the moved guidance rather than last in the message — and it lands there without this harness knowing the placement arms exist, because `promptio.mjs` delegates to production's own `assembleSpeakingRequest`. `context-arm.test.ts` asserts the identity for all six combinations.

## Running the multi-turn suite

```
ARM=<name> ../../node_modules/.bin/tsx turns.mjs <candidate> <reps>
```

Same environment variables as `defect.mjs` (`PROMPT_FILE`, `ARM`, `CASE_FILTER` — `CASE_FILTER` matches on the chain id here, since a chain has no single `kind`). Results land in `results/turns-<arm>-<candidate>.json`, one row per turn, in the same shape `defect.mjs` writes. The banner prints the number of billed model calls the invocation is about to make before it makes any of them: **turns x cases x reps**, in the banner's own words, which is 15 calls for one rep of all three chains (6 + 6 + 3).

Two properties of this driver are worth knowing before you use it. Turns inside a chain are serial by construction — each one's request contains the previous one's reply — so a rep is a whole chain re-run, not a re-run of one call, and the cost scales in turns rather than in cases. And the model transport is injectable (`runChain` takes its `call` as an argument), which is what lets `turn-chain.test.ts` exercise the entire chain against canned replies for free. If you write anything new against this harness, keep that seam: a driver that can only be tested by paying for it does not get tested.

**Reps inside one process are near-worthless as evidence, and this is more true of a chain, not less.** At temperature 0 a loop of N reps in a single process is much closer to one sample dressed up as N than to N independent draws (see the section above), and a chain compounds it: every turn after the first is conditioned on a reply drawn from the same correlated distribution, so a whole chain can lock into one behaviour and repeat it. Any real D9 campaign must sample arms as separate, interleaved process invocations, exactly as `campaign3.sh` already does for the single-turn suites — `for i in 1 2 3; do for arm in before after; do ARM=$arm-r$i PROMPT_FILE=... tsx turns.mjs <candidate> 1; done; done` is the shape, and the accumulated `results/turns-*.json` files then go to `compare.mjs` together.

## Running the triage arm

```
ARM=<name> ../../node_modules/.bin/tsx triage.mjs <candidate> <reps>
CONTEXT_ARM=full ARM=<name> ../../node_modules/.bin/tsx triage.mjs <candidate> <reps>
```

`triage.mjs` measures the **third** call production makes on a turn, and the only one this harness ignored until now: `prompts/voice-triage.md`, which decides where the answer has to come from (`room` / `outside` / `pending` / `elsewhere`) and answers nothing. It belongs beside the long-transcript D4 cases because its `room` verdict is the same judgement D4 grades the speaking call on — is the answer already in the transcript — made over byte-identical context, since `runTriageGate` builds its user message with the speaking call's own `buildSpeakingUserMessage`. The two can degrade with length independently: a gate that says `outside` about something the room said an hour ago sends Archie off to ask a colleague, and no amount of correctness in the speaking prompt recovers that turn.

`triage-cases.mjs` is nineteen cases in three groups. Twelve are a 2x2 of length against verdict, in both languages: the three long `room` positions, the same 490-line meeting with the answer never said (`outside`), and the existing short `D4a`/`D4d`/`D5a`/`D5b` fixtures reused by id as the length control. The verdict half is load-bearing — a gate that answered `room` unconditionally would score full marks on a room-only set. `pending` and `elsewhere` are deliberately absent as expectations: neither has anything to do with transcript length, and `pending` stays impossible by construction rather than by hope, because the only `consults` block anywhere in this set holds a consult that has been **answered** — that verdict needs a question still showing no answer. The next five vary **the request** rather than the transcript, and are described under "The capability pair" below; the last two are the id pair, under "The id in the gate's own request".

Five things are graded separately, because they have different causes: **placement** (did it put the answer where it actually is), **the deadline** (production allows this call `TRIAGE_TIMEOUT_MS` and treats anything slower as no verdict at all, running the turn exactly as it would with no gate — a property of the deployment, not of the prompt; the figure is read out of `comprehension.ts` and cross-checked by `triage.test.ts`, so it is production's number and not a target of this harness's own, and it moved from 800ms to 1500ms once the gate's latency was measured over 36 draws rather than six: three of them landed at 826, 1144 and 1156ms, all three `outside` verdicts, and an `outside` verdict carries the preamble that ends the room's silence, so discarding it made that silence longer. It is a hung-socket guard, not a latency knob. Nothing in this harness hard-codes the number any more — `PRODUCTION_TRIAGE_DEADLINE_MS` is the one copy and the drift test is what moved it), **the preamble existing at all** (on `outside` the prompt asks for one sentence to say aloud; without it the room sits in silence through a full speaking call), **its language**, and **what it says**. `TRIAGE_PROMPT_FILE` points at a variant of the triage prompt the way `PROMPT_FILE` does for the speaking one; `ARM` and `CASE_FILTER` work as they do elsewhere, and `CONTEXT_ARM` works as it does in `defect.mjs` with one arm refused. Results land in `results/triage-<arm>[-<context arm>]-<candidate>.json`. `compare.mjs` does not read them — it re-grades defect and turn rows only, and a triage file passed to it would be silently skipped; `gradeTriage` is pure and takes a stored row's `raw`, its `elapsedMs` and its `context`, so an offline two-arm regrade is a few lines away but is not wired.

### The context arm here, and the one arm this driver refuses

`CONTEXT_ARM=bare` is the default and is byte-identical to the two-argument `triageUserMsg(c.transcript, c.consults)` call the twelve stored rows were collected under — asserted per case *through the driver's own transport*, not inferred from the third parameter having a default. `CONTEXT_ARM=full` adds `promptio.mjs`'s `FIXED_CONTEXT`, the same pinned standing blocks the speaking suite's full arm sends: +8,676 characters per case — the gate's figure and the speaking suite's are the same figure, since neither request carries a `<situation>` block — and the arm's name goes in the filename.

**`full-noverdict` is refused, and throws before anything is billed.** The gate never carries a `<situation>` verdict under any arm — it is the call that *produces* one, which is why `triageUserMsg` goes to `buildSpeakingUserMessage` rather than to `assembleSpeakingRequest`. The verdict is the only thing separating `full-noverdict` from `full`, so a `full-noverdict` triage run would send byte-identical requests to a `full` one and store them under a name claiming otherwise, and a comparison between the two would be reading sampling noise as a difference. That is the same refusal `quality.mjs` makes for `full` — there, the arm it cannot derive a verdict for; here, the arm whose distinguishing feature it cannot send. A `for ctx in bare full full-noverdict` loop borrowed from the speaking campaign therefore has to drop the third value for this driver.

Note what the arm does **not** isolate: `full` sends three blocks, so strictly the capability pair varies the whole standing context rather than the list alone. What closes that mechanically is asserted rather than argued — every capability-answer group matches `<capabilities>` and matches neither `<written>` nor `<participants>`, so the list is the only block that bears on the question the pair asks. A capabilities-only arm would be a fourth arm and a second pinned context, which this harness deliberately does not keep.

### What the preamble says, and why nothing else could catch it

The preamble is spoken by `answerRoom` **before** the speaking call runs, and it never passes through `voice-speaking.md` at all — so that document's rule against voicing an internal role cannot reach it, however well the speaking suite measures that rule. `parseTriage` sanitises the string for the synthesizer (`toSpeech`), which is punctuation and markup, not a word of judgement about what it says; `voice-triage.md` states the same thing from the prompt's side: "spoken to the room exactly as written, with nothing reading it first". So two failures were invisible here by construction, and a real meeting produced both.

**`MACHINERY`** reuses `defect.mjs`'s `machineryLeakCheck`, English and Russian halves, validated across 180 stored result rows. The fit is exact rather than approximate, because the text it was written for is the same kind of text: one or two sentences bound for a room's ears, judged for naming who Archie is about to ask. A second list would be a second thing to keep bounded correctly in Cyrillic, which is the bug this directory has shipped four times. It fires on `"Let me check with the PM."` — the sentence this harness graded clean, and the one `voice-triage.md` used to name as "the exact slip this rule exists to stop" until that literal was taken out of the field template the gate fills in.

It is now joined by `internalIdLeakCheck` from the same file, under the same `MACHINERY` prefix and the same report line, because `voice-triage.md` bans both in one breath: "no agent, no role, no team, no workflow, no id out of your own workings, not even the one a question is filed under". The id class is the one entry whose source sits in the gate's own request — `consultsBlock` starts every `<consults>` entry with the id production filed that consult under (`m<meeting>c<consult>`, `nextConsultId` in meeting.ts) — so a gate holding an exchange reads ids in the very message it writes a preamble into, and `toSpeech` strips markdown rather than names. Two tiers: the ids the row itself declares, matched literally, and production's id shape as a backstop for one no row declared. Bounded with `(?<![\p{L}\p{N}])`/`(?!...)` under `u` and never `\b`, whose error here is the *other* direction — it treats `в` and `m` as equally non-word and so reports a boundary inside a word, firing on `вm1c1` where the shipped pattern correctly does not. Both halves are asserted firing and silent, in English and in Russian, in `triage.test.ts`.

**`ANSWERED`** reads the case's own `answer` field: the answer to the very question the last line asks, in the `must`-shaped form `gradeDefect` already uses. `voice-triage.md` says why it matters — "anything of the answer in the preamble is not a fuller preamble — it is the room hearing the same thing twice". Every value is a reading of something that already exists: `TGd`/`TGh` get `LONG.<lang>.must`, the two groups the long fixture already carries and which the test already asserts are absent from the `absent` transcript; the capability cases get `CAPABILITY_ANSWER`, one group per line of the pinned `<capabilities>` list, each asserted at module load to match that list. **The field is per case on purpose, and the over-reach twin is why:** `TGn`/`TGp` ask for the crash numbers, so the correct preamble there restates the question — "let me pull the crash numbers for last week" — and any list banned suite-wide would fail a reply that is behaving perfectly. A case declares what its own answer is, or declares nothing and is not checked. `TGk`/`TGl` are the second kind and not an oversight: `D5a`/`D5b` carry no `must` and no `detail` because nobody anywhere has the value, so there is no answer token in existence to ban.

Every Russian pattern in both checks is bounded with `(?<!\p{L})`/`(?!\p{L})` under `u` and never `\b`. JS's `\b` is defined over `[A-Za-z0-9_]` and therefore never bounds a Cyrillic letter at all — it sits between two characters it considers equally non-word — and that exact bug has produced four dead detectors in this directory. It is asserted two ways, the same two `pending-nag.test.ts` uses: as a ban on the characters, and by rebuilding each shipped pattern with `\b` substituted and watching it go dead on an ordinary Russian sentence.

### The capability pair

A real meeting asked *"What can you help me with?"*, the gate answered `outside` — nobody here supplied this, go and find out — and the answer was sitting in the `<capabilities>` block of the gate's own context. The preamble then delivered that answer, and the speaking call delivered it again, so the room heard the same thing twice a millisecond apart. The triage arm could not see any of it: it sent no `<capabilities>` and graded the preamble for presence and Cyrillic share only.

`TGm`/`TGo` are that turn, and they are **one case run under two arms** rather than two cases. `expect` is a map — `{ bare: 'outside', full: 'room' }` — because with the list sent the answer is in front of the gate and nothing has to be fetched, and with it absent nobody has supplied it (`voice-triage.md` allows `outside` with no list at all). Two requests, two right answers, one transcript, which is the only construction that shows the verdict tracking *the list* rather than the wording of the question. `expectedFor` throws rather than guessing when such a case is graded with no arm named, for `resolveContextArm`'s reason: a guess would grade a `full` row against the `bare` expectation and report the harness's own choice as the gate's error. Every row stores its resolved `expect` and its `context`, so a file can never be read as the other arm's.

`TGn`/`TGp` are the anti-regression twin: the same room, the same list, and a question asking for one of the things **on** it (`Archie, can you pull the crash numbers for last week?`). `voice-triage.md` draws that line itself — "Being asked for one of the things on that list is the opposite case: there it is the thing that has to be fetched, never the list" — and the twin is what keeps the widening from swallowing every question the capability list mentions. Its `expect` is a plain string: `outside` under both arms, for two different sentences of the prompt. The pair and its twin are built from one lead-in array, so "same transcript, different last line" is structural rather than a claim in a comment.

The Russian half is a full mirror rather than the pair alone, and that is one case more than was asked for. The reason is the failure mode this suite has already had: `D7b-ru-pressed` scored 0/6 while its English twin passed 6/6, and the over-reach guard is the thing most worth measuring here, so measuring it in one language only would rebuild the same gap. Six calls a rep instead of five.

### The id in the gate's own request

`TGr`/`TGs` are the only cases here that send a `<consults>` block, and that block is the whole reason they exist. `voice-triage.md`'s list of what a preamble may not name now covers ids out of Archie's own workings, and that entry is the only one whose source is in front of the gate as it writes: every `<consults>` entry is rendered starting with the id production filed that consult under. Nothing downstream removes it — `toSpeech` is punctuation and markup — so a gate that says `m2c1` out loud has said it to the room.

Both are `outside` under both arms, and two properties of the fixture are what buy that cheaply. The consult is **answered**, so a wrong `pending` is not the likely failure — and `pending` produces no preamble at all, which is the one thing these two must not lose. And it is about something else entirely, with its answer as the line the room opens with, so the question actually asked is a lookup nobody here has done: on the capability list under `full`, and still a question that can go out of this room under `bare`. Neither declares an `answer`, for `TGn`/`TGp`'s reason — nobody anywhere has the number, so the correct preamble restates the question.

This is the first thing in this directory to measure the say-aloud risk of the gate's own prompt in either direction: before the field template's `the PM` literal was removed, nobody had checked whether the gate leaked it, and nobody had checked afterwards either.

### `ru` is the room's language; the preamble's is the one Archie was addressed in

`prompts/voice-triage.md` was changed so the preamble goes in the language Archie was **addressed** in, matching `voice-speaking.md`, rather than "the language of the room". The grader's `ru` flag means the room is Russian, and it demanded Cyrillic ≥ 0.5 off it — so an all-Russian meeting whose last line addresses Archie in English would have failed a *correct* English preamble. Every existing fixture was single-language, so nothing here distinguished the two rules.

`ru` is now a report axis and nothing else: it groups the placement table so a Russian-only failure can still be seen. The preamble's language is measured off the transcript by `addressedInRussian`, on the last line, which is the addressed turn by construction. Measured rather than added as a second flag for `deriveVerdict`'s reason — a hand label that has to agree with the transcript is a label that can come to disagree with it. The speaker prefix is stripped first, and that is the whole trick rather than tidiness: `Дмитрий: Archie?` is seven Cyrillic letters of name against six Latin ones of utterance, so measuring the raw line reads 0.54 Cyrillic and calls a short English address Russian.

`TGq-ru-room-en-ask-outside` is the fixture that separates the two rules: `D5b`'s Russian room with `D5a`'s English ask, assembled out of both existing fixtures rather than retyped, so it is `TGl` with one line's language changed and nothing else. Expect `outside` with an **English** preamble. The old rule is the mutation and it is asserted in both directions: keyed on the room, this fixture's correct English preamble fails and its wrong Russian one passes.

### Running the pair

The pair needs both arms, so it needs two invocations — which is what this directory's own doctrine already requires of any arm comparison (separate processes per sample, arms interleaved run by run):

```
cd tools/voice-cases
C=cerebras-gemma-4-31b        # or haiku-4.5
export POOL=3 MIN_GAP_MS=1500 # ~6.7k tokens a request on the full arm; see "Rate limits and pacing"
mkdir -p logs results
for i in 1 2 3; do
  for ctx in bare full; do
    [[ $ctx == bare ]] && L=tb$i || L=tf$i
    CONTEXT_ARM=$ctx ARM=$L ../../node_modules/.bin/tsx triage.mjs $C 1 > logs/triage-$ctx-r$i.log 2>&1
  done
done
```

Six invocations of 19 cases is 114 billed calls, at 84,188 input tokens a bare rep — measured off `results/triage-idleak-full-set-*.json`, which is the whole nineteen — and ~126k projected for a full one, adding the arm's 8,676 chars at the 3.90 chars-a-token rate measured above. Eight of the nineteen are the long-transcript cases at ~9.0k tokens a request, of which ~7.9k is transcript; the other eleven run ~1.1k each, the triage prompt being small and paid nineteen times over either way. Mean request size is 4.4k tokens bare and ~6.7k full, which is what the `MIN_GAP_MS` above is sized against. `CASE_FILTER=caps` runs the four capability cases alone — 8 calls for a bare/full pair of reps, and the cheapest way to measure the pair and its twin, since none of the four is a long transcript; `CASE_FILTER=TGq` runs the language case alone; `CASE_FILTER=idleak` runs the two id cases alone, which is 2 calls a rep and needs only the `bare` arm, since their expectation does not move with it. Read each run's `expects=` banner line before its table: it says which verdicts that invocation graded against, and on the pair those differ by arm.

What a pass and a failure mean, per fixture. **`TGm`/`TGo` clean under both arms** is the whole claim of the prompt fix: the verdict follows the list. `room` under `bare` means the gate is answering `room` about a list it was never sent — the mirror of the D1 bug, and the reason `bare` is worth running at all. `outside` under `full` is the live incident reproduced, and it will usually come with `ANSWERED` beside it on the same row. **`TGn`/`TGp` clean** means the guard sentence holds; `room` there is the over-reach, and it is the failure to escalate — it means the widening swallowed every question the capability list mentions. **`TGq` clean** means the preamble follows the address; a `LANGUAGE` failure there means the prompt is still keyed on the room. **`TGr`/`TGs` clean** means the preamble held the floor without reading out the id sitting in its own request; a `MACHINERY` failure there naming `consult-id:` or `id-shape:` is that id spoken to the room. And a `MACHINERY` failure anywhere means a sentence naming the apparatus went to a room's ears with nothing reading it first, which is a defect in production and not only in a score.

One copy in this arm is worth knowing about. `readVerdict` in `triage.mjs` is the harness's own reader rather than production's `parseTriage`, which is not exported — the opposite of what this directory does everywhere else, and the compromise is only tolerable because `triage.test.ts` reads `comprehension.ts`'s source and asserts that the four verdict names, the deadline and the 96-token cap still match the constants over there — separator-tolerantly, since a neighbouring constant in that file is written `5_000` and a `\d+` capture would read `1_500` as `1` and then pass against nothing. Exporting `parseTriage`, exactly as `parseReply` and `buildSpeakingUserMessage` were exported for this harness, and deleting the copy, is the fix.

## Running a two-arm campaign

```
./campaign3.sh <candidate> <runs> <armA-name> <armA-prompt-file> <armB-name> <armB-prompt-file>
```

For example, `./campaign3.sh cerebras-gemma-4-31b 5 before /tmp/voice-speaking.before.md after ../../prompts/voice-speaking.md` runs 5 interleaved runs of each arm against Cerebras. Per-run logs land in `logs/defect-<arm>-r<n>.log` and `logs/quality-<arm>-r<n>.log`; per-run quality result JSON is renamed to `results/quality-<arm>-r<n>.json` after each run so successive runs of the same arm do not overwrite each other (`defect.mjs` already names its own output by arm, so no rename is needed there). Once every run has finished, feed the accumulated `results/defect-*.json` files to `compare.mjs` to get a single before/after table. Pacing is inherited by every run, so `POOL=3 MIN_GAP_MS=1500 ./campaign3.sh ...` paces the whole campaign; the script itself sets neither, and the retry in `providers.mjs` applies to every call it makes. Read each run's closing `sample ...` line before reading the table: a run that lost rows to a 429 says so there, and `compare.mjs` will say it again per arm.

## Keys

`ANTHROPIC_API_KEY` is read by `providers.mjs` from the **main checkout's** `.env` (`/Users/khmelev/Projects/swc/archie-hq/.env`), not from whichever worktree the harness happens to be running in — this matches how the harness has always resolved this key. `CEREBRAS_API_KEY` is resolved the same way: the main checkout's `.env` wins if it holds the key, and this checkout's own `.env` is the fallback, which is where a worktree-local key such as this one is more likely to actually live, since a worktree does not generally carry its own copy of shared repo secrets. A checkout's `.env` always wins over the ambient environment, so a live campaign resolves its key exactly as it always has and a stale exported value cannot silently redirect one; `process.env` is consulted only where the throw used to be, which is what lets `rate-limit.test.ts` exercise the transport against a stubbed `fetch` with no secrets on disk. Neither function invents a key from nowhere — both throw a clear error naming exactly which file(s) were checked if the key is missing from all of them and from the environment. Nothing in this harness ever prints a key value; if you add logging, keep it that way.

## What this harness deliberately does not keep

No prompt-variant snapshots live in this directory — `compare.mjs` and `campaign3.sh` both expect you to point `PROMPT_FILE` / `COMPARE_PROMPTS` at whatever variant you are testing, saved wherever you like outside this directory, rather than accumulating `voice-speaking.SOMENAME.md` files here. `results/` and `logs/` are run output, gitignored, and safe to delete at any time — nothing in this harness reads its own past output except `compare.mjs`, and only when you name the files explicitly on its command line.
